Q. No 1: ETL Strategies & Extraction [3 + 2 = 5 Points]

a. When it is appropriate to use full data refresh loading strategy? Also suggest at least two practical steps that expedite the full data refresh loading process. [3 Points]
b. Briefly explain the two most efficient immediate data extraction techniques. [2 Points]
Detailed Solution:

Part a: When to use Full Data Refresh:

  • Small to Medium Dimension Tables: Dimension tables with static or slowly changing attributes (e.g., Lookup tables, Store dimension, Date dimension, Status codes) where total volume is small (≤100k rows) and dropping/reloading is faster than row-by-row comparisons.
  • High Volatility / Massive Change Percentage: When a significant fraction of data changes per refresh cycle (>30–40% of records). Performing row-by-row delta tracking and individual update queries costs more I/O than truncating and reloading the entire table.
  • Lack of Source Delta Tracking: When legacy source systems have no update timestamps, audit columns, database triggers, or transaction log access to identify changed records.
  • Initial Load & Resynchronization: Initial warehouse populating or periodic disaster recovery resynchronization to eliminate data drift.

Two Practical Steps to Expedite Full Data Refresh:

  • Drop/Disable Secondary Indexes & Constraints: Drop secondary B-tree indexes and disable foreign key constraints before bulk loading. Inserting rows into active indexes causes severe random I/O and B-tree page splits. Rebuild indexes in bulk via parallel external sort after data insertion.
  • Direct-Path Bulk Loading: Utilize direct-path loading utilities (e.g., Oracle Direct Path / SQL*Loader, PostgreSQL COPY, MySQL LOAD DATA INFILE, Teradata FastLoad) that format data directly into database blocks above the high-water mark, bypassing the database buffer cache and undo/rollback generation.
  • NOLOGGING Mode: Set the target table/session to NOLOGGING to disable transaction redo logging, removing disk I/O bottlenecks on the transaction log.

Part b: Two Most Efficient Immediate Data Extraction Techniques:

  • 1. Log-Based Change Data Capture (CDC) / Redo Log Sniffing: An external reader daemon asynchronously reads the database engine's transaction redo log / Write-Ahead Log (WAL). It captures every INSERT, UPDATE, and DELETE with both before-and-after images without issuing any queries to the operational tables. It is considered the most efficient because it imposes zero overhead or locking on operational OLTP transactions.
  • 2. Database Triggers (Trigger-Based CDC): AFTER INSERT, AFTER UPDATE, and AFTER DELETE triggers defined on source tables write modified row keys or full records into shadow staging tables or event queues. It captures changes immediately at transaction commit time with 100% accuracy, though it introduces minor commit latency to operational transactions.
Given Scenario & Statistics for Q2 & Q3

Q. No 2: Index Access Cost Calculation [10 Points]

Calculate the total I/O cost for the Query using the following indexed access paths. Show all steps clearly.
Query: SELECT * FROM book WHERE publisher= 'Wiley' AND publishYear= '2023' AND author IN ('Inmon', 'Kimball');
a. Clustered Index access (Assume clustered index exists on Author column)
b. Static Bitmap Index access (Assume static bitmap indexes exist on Publisher, PublishYear, and Author columns separately)
Detailed Solution:
Part a: Clustered Index Access on Author Column
1. Author condition: author IN ('Inmon', 'Kimball') has selectivity = 4% + 2% = 6%.
2. Qualifying rows for Author: Q_author = 0.06 × 100,000 = 6,000 rows.
3. Index access cost: ⌈ Q_author / bfri ⌉ = ⌈ 6,000 / 546 ⌉ = 11 blocks.
4. Base table access cost:
   Because the index on Author is CLUSTERED, matching records are stored contiguously on disk!
   Base table blocks = ⌈ Q_author / bfr ⌉ = ⌈ 6,000 / 40 ⌉ = 150 blocks.
5. (In memory, the other predicates publisher='Wiley' and publishYear='2023' are evaluated on the 6,000 rows).
6. Total I/O Cost = Index Cost + Base Table Cost = 11 + 150 = 161 I/Os.
Part b: Static Bitmap Index Access
1. Size of ONE static bitmap vector:
   Bits per block = B × 8 = 8,192 × 8 = 65,536 bits.
   Blocks per vector = ⌈ rB / 65,536 ⌉ = ⌈ 100,000 / 65,536 ⌉ = 2 blocks.
2. Number of distinct indexed values queried:
   • Publisher = 'Wiley' (1 value) → 1 × 2 = 2 blocks.
   • PublishYear = '2023' (1 value) → 1 × 2 = 2 blocks.
   • Author IN ('Inmon', 'Kimball') (2 values) → 2 × 2 = 4 blocks.
3. Total Bitmap Index Access Cost = 2 + 2 + 4 = 8 blocks.
4. In-Memory Bitwise Operations:
   (Bitmap_Inmon OR Bitmap_Kimball) AND Bitmap_Wiley AND Bitmap_2023.
   Resulting matching bits = 48 qualifying rows.
5. Base table access cost:
   Since bitmaps are unclustered, each qualifying row may require 1 random block fetch.
   As Q_comb = 48 < bB = 2,500, we read only 48 blocks of base table.
   Base Table Access Cost = 48 blocks.
6. Total I/O Cost = Index Cost + Base Table Cost = 8 + 48 = 56 I/Os.

Q. No 3: Join Execution & Cost Evaluation [3 + 3 + 4 = 10 Points]

Calculate the total I/O cost to execute this Query using the following joining techniques. Show all steps clearly. Assume static bitmap indexes exist on Publisher, PublishYear, and Author columns of Book table and there is no index on BookLoan table. [3+3+4= 10]
Query: SELECT * FROM book JOIN BookLoan ON Book.BookID = BookLoan.BookID WHERE publisher= 'Wiley' AND publishYear= '2023' AND author IN ('Inmon', 'Kimball');
a. Sort Merge Join
b. Hash Join
c. Nested Loop Join (Identify the most efficient variant of NLJ in this scenario, then compute the I/O cost of that variant only.)
Detailed Solution:

Common Preliminary Step (Filter Book Table):

Using the static bitmap index from Q2b, the I/O cost to filter the Book table is 56 I/Os. The resulting filtered Book relation contains 48 records, which occupy ⌈48 / 40⌉ = 2 blocks.

Part a: Sort Merge Join (SMJ)
1. Filter Book table: 56 I/Os (Result = 48 records, 2 blocks).
2. Sort Book on BookID:
   The filtered Book relation has 2 blocks. Since 2 ≤ K = 100, it fits entirely in memory!
   Sort cost for Book = 0 disk I/O (sorted in RAM).
3. Sort BookLoan on BookID:
   BookLoan has bL = 50,000 blocks and NO index exists on BookLoan.
   It must be sorted via External Merge Sort with K = 100 blocks:
   • Pass 0 (Run creation): Reads and writes 50,000 blocks into N = ⌈50,000 / 100⌉ = 500 initial runs.
     Pass 0 I/O = 2 × 50,000 = 100,000 I/Os.
   • Merge Passes: (K - 1) = 99-way merge. Number of merge passes = ⌈log_99(500)⌉ = 2 passes.
     Pass 1: Merge 500 runs into ⌈500 / 99⌉ = 6 runs. I/O = 2 × 50,000 = 100,000 I/Os.
     Pass 2 (Final merge): Merges 6 runs directly into the join merge phase = 50,000 I/Os.
   • Total Sorting Cost for BookLoan = 100,000 + 100,000 + 50,000 = 250,000 I/Os.
4. Merge Phase: Scan sorted Book (2 blocks) + scan sorted BookLoan (50,000 blocks) = 50,002 I/Os.
5. Total SMJ Cost = 56 (filter) + 250,000 (sort BookLoan) + 2 (read Book) = 250,058 I/Os.
(If standard 2-pass external sort formula 2×bL(1 + ⌈log_(K-1)(⌈bL/K⌉)⌉) is used without pipelining final pass: Sort = 300,000 I/Os; Total = 350,058 I/Os).
Part b: Hash Join (HJ)
1. Filter Book table: 56 I/Os (Result = 48 records, 2 blocks).
2. Designate Build and Probe inputs:
   • Build Input: Filtered Book (M = 2 blocks).
   • Probe Input: BookLoan (bL = 50,000 blocks).
3. Check In-Memory Condition:
   Since M = 2 ≤ K = 100, the entire hash table fits in available memory!
   Recursive partitioning is NOT required.
4. Hashing Cost: Read build table into hash table (2 blocks) + Stream probe table (50,000 blocks).
5. Total Hash Join Cost = Filter Cost + Build Cost + Probe Cost
   = 56 + (2 + 50,000) = 50,058 I/Os.
(Note: If the 2 filtered Book blocks are retained in buffer directly after filtering, Build Cost = 0, giving 56 + 50,000 = 50,056 I/Os).
Part c: Nested Loop Join (NLJ) Variant Identification & Cost
1. Identify Most Efficient NLJ Variant:
   • Naive / Tuple NLJ: 48 × 50,000 = 2,400,000 I/Os (Extremely inefficient).
   • Index NLJ: Not applicable because problem explicitly states "there is no index on BookLoan table".
   • Most Efficient Variant: Block Nested Loop Join (BNLJ) with filtered Book as the outer table.
2. Cost Calculation for BNLJ:
   • Outer table = Filtered Book (b_outer = 2 blocks).
   • Inner table = BookLoan (b_inner = 50,000 blocks).
   • Memory allocation: (K - 2) = 98 blocks for outer chunks, 1 block inner, 1 block output.
   • Since b_outer = 2 ≤ 98, ALL 2 blocks of the outer table fit into memory simultaneously!
   • Therefore, the inner table BookLoan is scanned ONLY ONCE.
   • BNLJ Join Cost = Outer blocks + ⌈b_outer / (K-2)⌉ × Inner blocks
     = 2 + 1 × 50,000 = 50,002 I/Os.
3. Total Cost = Filter Cost of Book + BNLJ Join Cost
   = 56 + 50,002 = 50,058 I/Os.
Remarkable Observation for Exam Discussion
Notice that Hash Join (50,058 I/Os) and Block Nested Loop Join (50,058 I/Os) yield the exact same I/O cost in this scenario! This occurs because the filtered outer relation is so small (2 blocks) that it fits entirely in memory in both algorithms, enabling a single sequential stream of the 50,000-block BookLoan table. Meanwhile, Sort-Merge Join (250,058 I/Os) is 5x slower due to the heavy external sorting required for the unindexed BookLoan table.

Q1. Multi-Branch Financial DW ETL Strategy [6 Points]

You manage a data warehousing system for a financial institution that stores transaction data from multiple branches. The data warehouse is updated daily with transaction data from various branches. However, recently, there have been performance issues during data extraction/loading due to the increasing volume of data. Design an efficient extraction/loading strategy for this scenario.
a. Which extraction and loading technique do you prefer in the need to update the data warehouse with new transactions from each branch daily and why?
b. When ETL process be performed to minimize the impact on the source systems and the extraction time? Specify appropriate time window.
c. Branch A uses numeric account numbers, while Branch B uses alphanumeric customer codes as identifiers. To ensure consistency in the data warehouse, you need to restructure these keys. Explain with an example.
Detailed Solution:

Part a: Preferred Extraction and Loading Technique & Justification:

  • Extraction Technique: Incremental Extraction using Log-Based Change Data Capture (CDC):
    Why: The DW only requires daily new transaction data. Full extraction of millions of historical branch transactions causes massive network and CPU degradation. Log-based CDC asynchronously reads DBMS redo logs, capturing only new transactions with zero locking or performance degradation on operational banking transactions.
  • Loading Technique: Append / Incremental Load into Partitioned Fact Table:
    Why: Financial transactions are immutable event records (periodic data). They are strictly appended and never updated in place. Using direct-path bulk append into date-based partitions (e.g. daily partition) eliminates expensive row-by-row lookups and undo overhead.

Part b: Optimal Execution Timing & Window:

  • Execution Window: Nightly batch window between 1:00 AM and 4:00 AM.
  • Justification: During these off-peak hours, physical banking branches are closed, online ATM/banking transactions are at their minimum volume, and OLTP server CPU/disk utilization is lowest. This ensures the ETL process does not compete for resources with operational customer workloads.

Part c: Key Restructuring & Surrogate Key Resolution:

  • The Problem: Source branches have heterogeneous natural key formats (Numeric AccNo at Branch A vs. Alphanumeric CustCode at Branch B). Using operational keys directly causes type conflicts and fails to provide a single view of the customer.
  • The Solution: Surrogate Key Generation via Cross-Reference Mapping Table:
    Generate an integer sequence surrogate key Customer_SK inside the Data Warehouse. Maintain an enterprise mapping table: 
    MAPPING_TABLE (Source_Branch, Operational_Key, Customer_SK)
('Branch_A',    '10452',         5001)
('Branch_B',    'CUST-A99',      5002)
    All data warehouse fact and dimension tables store Customer_SK = 5001 as a uniform 4-byte integer foreign key, decoupling the warehouse from source operational changes.

Q2. Index Access Cost Calculations [12 Points]

Calculate the total I/O cost for the Query using the following indexing techniques. Show all steps clearly.
Query: SELECT * FROM book WHERE publisher IN (‘Pearson’, ‘Wiley’) AND publishYear IN (‘2018’, ‘2020’, ‘2022’);
a. Single index access (Assume Single indexes exist on Publisher and PublishYear columns separately)
b. Combining multiple indexes (Assume Single indexes exist on Publisher and PublishYear columns separately)
c. Composite Index access (Assume a composite index exist on Publisher and PublishYear columns, with index entry size=15 bytes)
Detailed Solution (Exact FAST Official Marking):
Part a: Single Index Access
1. Choose highest selectivity column (smallest row count):
   • Publisher (8%): 0.08 × 1M = 80,000 rows.
   • PublishYear (6%): 0.06 × 1M = 60,000 rows.
   Select PublishYear (6%).
2. Index access cost = 60,000 / 1092 = 54.94 → 55 blocks.
3. Base table access cost:
   As qualifying rows are greater than total blocks of book table (60,000 > 9,175),
   we have to read all the blocks of base table = 9,175 blocks.
4. Total Cost = Index Cost + Base Table Cost = 55 + 9,175 = 9,230 I/Os.
Part b: Combining Multiple Indexes
1. Publisher Index access cost (8% of 1M rows) = 80,000 / 1092 = 73.26 → 74 blocks.
2. PublishYear Index access cost (6% of 1M rows) = 60,000 / 1092 = 54.94 → 55 blocks.
3. Total Index access cost = 74 + 55 = 129 blocks.
4. Combined qualifying rows = 0.08 × 0.06 × 1,000,000 = 4,800 rows.
5. As 4,800 < 9,175, read 4,800 base table blocks.
6. Total Cost = Indexes Access Cost + Base Table Cost = 129 + 4,800 = 4,929 I/Os.
Part c: Composite Index Access
Order of index = (Publisher, PublishYear). Enumerate all 6 combinations of interest:
• Comb#1 (Pearson, 2018): 5% × 3% × 1M = 1,500 RIDs → ⌈1500 / 1092⌉ = 2 I/Os.
• Comb#2 (Pearson, 2020): 5% × 2% × 1M = 1,000 RIDs → ⌈1000 / 1092⌉ = 1 I/O.
• Comb#3 (Pearson, 2022): 5% × 1% × 1M = 500 RIDs → ⌈500 / 1092⌉ = 1 I/O.
• Comb#4 (Wiley, 2018): 3% × 3% × 1M = 900 RIDs → ⌈900 / 1092⌉ = 1 I/O.
• Comb#5 (Wiley, 2020): 3% × 2% × 1M = 600 RIDs → ⌈600 / 1092⌉ = 1 I/O.
• Comb#6 (Wiley, 2022): 3% × 1% × 1M = 300 RIDs → ⌈300 / 1092⌉ = 1 I/O.
Total Index access cost = 2 + 1 + 1 + 1 + 1 + 1 = 7 blocks.
Base table access cost = 4,800 blocks.
Total I/Os = 7 + 4,800 = 4,807 I/Os.

Q3. Joining Techniques Cost Calculations [12 Points]

Calculate the total I/O cost for the Query using the following joining techniques. Show all steps clearly. Assume there is a clustered index on BookID column of BookLoans table, but there is no index on BookID column of Book table.
Query: SELECT * FROM Book JOIN BookLoans ON Book.BookID = BookLoans.BookID WHERE publisher IN (‘Pearson’, ‘Wiley’) AND publishYear IN (‘2018’, ‘2020’, ‘2022’);
a. Hash Join
b. Sort Merge Join
c. Nested Loop Join (Identify the most efficient variant of NLJ in this scenario, then compute the I/O cost of that variant only.)
Detailed Solution (Exact FAST Official Marking):
Part a: Hash Join
1. Book's filter cost = 9,175 blocks (via Full Table Scan of Book).
   Qualifying Book records = 4,800 rows = 45 blocks.
2. Hashing cost:
   As the memory (K = 100 blocks) is sufficient to store build-input table (45 blocks ≤ 100),
   recursive partitioning is not required.
   Hashing cost = Read build table (45) + Read probe table BookLoans (183,487).
3. Total Cost = 9,175 + (45 + 183,487) = 192,707 I/Os.
Part b: Sort Merge Join
1. Book's filter cost = 9,175 blocks.
2. Sort Book: The 45 qualifying blocks fit in memory (45 ≤ 100) → 45 blocks read.
3. Sort BookLoans: No sorting required for BookLoans due to clustered index on joining column!
4. Merge cost = Read sorted Book (45) + Read sorted BookLoans (183,487).
5. Total Cost = 9,175 + (45) + (45 + 183,487) = 192,752 I/Os.
Part c: Nested Loop Join
1. Best NLJ Variant: Clustered NLJ (Index Nested Loop Join), as there is a clustered index existing on the joining column of BookLoans.
2. Cost Formula = Book filter cost + [Qualifying rows of outer table × (Clustered index access cost + Inner base table access cost)].
3. Here: Clustered index access cost = 1 block; Inner base table access cost = 1 block.
4. Join Cost = 4,800 × (1 + 1) = 9,600 I/Os.
5. Total Cost = Book's filter + Join Cost = 9,175 + 9,600 = 18,775 I/Os!
Why Clustered NLJ Wins Massive Marks
Hash Join and Sort-Merge Join both cost ~192,700 I/Os because they are forced to scan all 183,487 blocks of the massive 20M-row BookLoans table. In stark contrast, Clustered NLJ costs only 18,775 I/Os (over 10x faster) because it uses the clustered index on BookID to jump directly to the exact blocks holding loans for the 4,800 books!

Q1. Dimension Refresh, Extraction & Merge Strategies [10 Points]

a) Assume that 40,000 rows out of 20 million rows in Customer dimension table changes on each data refresh. Which loading strategy should you follow? Explain the reasons for your selection. Also suggest some practical steps that expedite the data loading process. [4 Points]
b) What are the two most inexpensive data extraction techniques to implement? Explain briefly why? [3 Points]
c) Explain the difference between destructive merge and constructive merge for applying data to the data warehouse repository. When do you use these modes? [3 Points]
Detailed Solution:

Part a: Loading Strategy & Expediting Steps:

  • Recommended Strategy: Incremental Load (Delta Upsert / SCD Type 1 or Type 2).
    Reason: The changed volume is only 40,000 / 20,000,000 = 0.2% of the table. A full refresh would require deleting and reinserting 20 million records, incurring gigantic unnecessary disk I/O, transaction logging, and prolonged downtime. An incremental load processes only the 0.2% delta.
  • Steps to Expedite Loading:
    1. Load the 40,000 changed rows into an unindexed staging table.
    2. Join staging with Customer dimension on natural key to separate new inserts from updates.
    3. Execute a set-based MERGE statement rather than row-by-row cursor updates.
    4. Disable non-essential secondary indexes on the target table during large inserts and rebuild them in bulk afterward.

Part b: Two Most Inexpensive Data Extraction Techniques:

  • 1. Full Table Dump (Data Dump / File Export):
    Why Inexpensive: Requires no specialized software, no third-party CDC licenses, no schema changes, and no application modifications. A standard SQL query (SELECT *) or native DBMS export utility dumps the table directly into flat files.
  • 2. Timestamp / Audit Column Incremental Query:
    Why Inexpensive: Leverages existing columns (e.g. Last_Modified_Date) already maintained by the operational application. A simple parameterized query (WHERE Last_Modified_Date > :last_refresh_time) extracts the delta without needing complex log sniffers or triggers.

Part c: Destructive vs. Constructive Merge:

  • Destructive Merge (In-Place Overwrite / SCD Type 1): Overwrites existing column values with new incoming values. Historical values are permanently destroyed.
    When to use: Correcting data entry errors (e.g., misspelled customer name, wrong phone number) or when historical tracking is not required by business users.
  • Constructive Merge (Historical Versioning / SCD Type 2): Keeps the old record intact, sets its expiration timestamp / flags it as inactive, and inserts a brand new record with updated values and a new surrogate key.
    When to use: Essential dimension attributes where preserving a point-in-time audit trail is mandatory (e.g., customer address change affecting historical regional sales reports).
