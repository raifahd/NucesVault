1Exam Blueprint & Mathematical Nomenclature

The standard variable vocabulary, rounding rules, selectivity arithmetic, and the golden law of unclustered disk access.

FAST Midterm 2 exam questions are rigorous, multi-part, and reward structured, step-by-step mathematical working. Every point deduction in past papers comes from either neglecting ceil/floor rules, miscalculating combined selectivity, or misunderstanding the difference between clustered sequential reads and unclustered random block visits. Master the nomenclature first.

Official FAST Nomenclature & Variables
Symbol Meaning Typical Units / Examples Calculation / Formula
B Data Block Size (Page Size) Bytes (e.g., 8 KB = 8,192 B; 16 KB = 16,384 B; 50 KB = 51,200 B) Given directly in problem statement
R Record Size (Base Table Row Width) Bytes (e.g., 128 B, 150 B, 200 B, 256 B, 500 B) Given directly
Ri Index Record Size (RID / Key + Pointer) Bytes (typically 8 B, 15 B, or 16 B) Given directly
r (or rS, rB, rL) Total Number of Records in Base Table Rows (e.g., 100,000; 128,000; 1,000,000; 20,000,000) Given directly
K Available Memory Buffer Size Blocks (e.g., 50 blocks, 100 blocks) Given directly
bfr Blocking Factor of Base Table Rows per block bfr = ⌊ B / R ⌋ (Always FLOOR / Integer truncation)
bfri Blocking Factor of Index Table Index entries (RIDs) per block bfri = ⌊ B / Ri ⌋ (Always FLOOR / Integer truncation)
b (or bS, bB) Total Blocks of Base Table Blocks b = ⌈ r / bfr ⌉ (Always CEILING / Round up)
bi (or bSi, bBi) Total Blocks of Full Index Blocks bi = ⌈ r / bfri ⌉ (Always CEILING / Round up)
S Selectivity of a Predicate Percentage / Fraction (e.g., 3% = 0.03) Fraction of rows satisfying condition
Q Qualifying Records for a Predicate Rows Q = S × r
Scomb Combined Selectivity (Independent AND) Fraction Scomb = S1 × S2 × S3 × ...
Qcomb Combined Qualifying Rows Rows Qcomb = Scomb × r

The Two Golden Rules of Discrete I/O

Rule 1: Floor for Capacity, Ceiling for Physical Allocation
• Records per block: bfr = ⌊ B / R ⌋ (A block cannot hold a fractional row).
• Index entries per block: bfri = ⌊ B / Ri ⌋.
• Blocks occupied by records: b = ⌈ r / bfr ⌉ (Any remaining rows demand a full disk block).
• Blocks occupied by index: bi = ⌈ r / bfri ⌉.
• Filtered rows in contiguous blocks: b_filt = ⌈ Q / bfr ⌉.
Rule 2: The Golden Cap for Unclustered Base Table Reads

When using a Secondary / Unclustered Index, qualifying RIDs point randomly all across disk blocks. Each qualifying record may require 1 random block fetch. However:

  • If Qualifying Rows < Base Table Blocks (Q < b): Base Table Access Cost = Q blocks.
  • If Qualifying Rows ≥ Base Table Blocks (Q ≥ b): Base Table Access Cost = b blocks (Cap at total base table blocks!). You cannot read more distinct physical blocks than the file actually contains!

The Danger: If Q ≥ b, using a single unclustered index costs Index Access + b > b, making it strictly worse than a Full Table Scan!

Clustered vs. Unclustered: The 100x Efficiency Gap
If an index is CLUSTERED, records with identical or consecutive keys are stored physically adjacent on disk. Therefore:
Base Table Cost (Clustered) = ⌈ Q / bfr ⌉ (Divided by blocking factor!)
In contrast, for unclustered: Base Table Cost = Q (1 I/O per row). If bfr = 64, clustered access is 64 times faster!

Key Takeaways: Topic 1

  • Always start by computing bfr = ⌊B/R⌋, bfri = ⌊B/Ri⌋, b = ⌈r/bfr⌉, and bi = ⌈r/bfri⌉.
  • For independent AND conditions, multiply percentages: Scomb = S1 × S2 × .... For IN / OR conditions on the same column, add percentages: S = S_a + S_b.
  • Unclustered base table fetch is capped at b. Clustered base table fetch is ⌈Q / bfr⌉.
  • If the query is SELECT COUNT(*) and multiple secondary indexes are combined, base table access is 0 because all required keys are resolved entirely within the index RID lists!
Practice Questions
Easy: A table has 200,000 rows. Block size B = 8 KB (8192 bytes), record size R = 256 bytes, index entry Ri = 16 bytes. What are bfr, bfri, b, and bi?

Answer:
bfr = ⌊8192 / 256⌋ = 32 rows/block.
bfri = ⌊8192 / 16⌋ = 512 entries/block.
b = ⌈200,000 / 32⌉ = 6,250 base table blocks.
bi = ⌈200,000 / 512⌉ = 391 index blocks.

Medium: For the table above, a query on an unclustered secondary index matches 8,000 rows. What is the base table access cost? What if it matches 4,000 rows?

Answer:
• Case 1 (8,000 rows): Since Q = 8,000 > b = 6,250, the worst-case random I/O cannot exceed reading every block in the table. Base table access = 6,250 blocks.
• Case 2 (4,000 rows): Since Q = 4,000 < b = 6,250, base table access = 4,000 blocks.

Hard: If the index in Case 1 (8,000 rows) were CLUSTERED instead of unclustered, what would the base table access cost be?

Answer:
Because records are physically clustered together on disk, base table blocks read = ⌈Q / bfr⌉ = ⌈8,000 / 32⌉ = 250 blocks!
Comparing 250 blocks (clustered) to 6,250 blocks (unclustered) demonstrates a 25x performance improvement.

2ETL Architecture & Engineering

Extraction categories, CDC mechanisms, transformation types, surrogate key mapping, bulk load acceleration, and merge strategies.

Extraction, Transformation, and Loading (ETL) consumes up to 70% of data warehouse engineering effort. In FAST exams, theoretical questions test your understanding of source data characteristics, immediate vs. periodic extraction, key restructuring, and bulk load optimization protocols.

1. Source Operational Data Categories

1. Transient Data (Volatile / State-Oriented)

Data that is updated or overwritten in-place in the operational database as business transactions occur. Only the current state is preserved; previous historical states are destroyed.

Examples: Current customer credit limit, current account balance, product stock on hand, customer active phone number.

2. Periodic / Event Data (Historical / Append-Only)

Data generated by operational business events that are appended sequentially and never overwritten. Each record carries a natural business timestamp and is immutable.

Examples: ATM cash withdrawal transactions, POS retail checkout logs, web server clickstreams, airline boarding records.

2. Data Extraction Strategies

Technique Mechanism OLTP Impact Classification & Best Used When
Log-Based CDC (Sniffing Redo Logs) Reads database transaction logs (WAL/redo logs) asynchronously outside the DBMS engine. Zero / Negligible Most efficient immediate technique. High-volume, 24/7 OLTP systems where operational degradation cannot be tolerated.
Database Triggers AFTER INSERT/UPDATE/DELETE triggers capture delta keys into shadow staging tables. Moderate (Commits slowed) Immediate technique. Useful when DBMS transaction logs are proprietary or inaccessible, but requires schema changes.
Full Table Dump (SELECT *) Full query / utility dump of source tables into flat files or staging area. High during extraction Most inexpensive to implement. Small tables, initial data warehouse load, or legacy files with no timestamp support.
Timestamp / Audit Columns Query filters on WHERE Last_Updated > :last_etl_time. Low to Moderate Inexpensive incremental technique. Standard operational schemas that already maintain reliable update timestamps.
Exam Question Trap: "Two Most Efficient Immediate" vs. "Two Most Inexpensive"
Past papers repeatedly test this exact distinction:
  • Two Most Efficient Immediate Techniques: (1) Log-Based CDC (asynchronous, zero OLTP impact), and (2) Trigger-Based CDC (event-driven, instant capture).
  • Two Most Inexpensive Techniques to Implement: (1) Full Table Dump / File Export (no code changes, zero CDC tool cost, simple scripts), and (2) Timestamp/Status Column Incremental Query (uses native application columns with no specialized infrastructure).

3. Major Transformation Tasks (4 Core Types)

1. Format & Data Type Conversion

Converts heterogeneous operational data formats into a uniform warehouse standard.

Example: Converting strings "12/05/2023" and "2023.05.12" to standard ISO date DATE '2023-05-12', or converting currency strings "$1,200.50" to DECIMAL(10,2).

2. Data Standardization & Cleansing

Reconciling disparate codes, resolving abbreviations, and trimming noise across source branches.

Example: Harmonizing gender codes '1', 'M', 'Male' into a single canonical code 'M'.

3. Key Restructuring & Surrogate Keys

Replacing disparate operational natural keys with warehouse-managed integer surrogate keys.

Example: Branch A uses numeric AccNo = 10452 while Branch B uses alphanumeric CustCode = 'CUST-A99'. The warehouse assigns unified surrogate keys Customer_SK = 5001 and 5002 via a Cross-Reference Mapping Table.

4. Aggregation & Summarization

Pre-computing granular transaction records into summary metrics for DSS performance.

Example: Summing millions of individual POS item checkout records into daily branch sales summary rows (BranchID, Date, TotalRevenue).

Entity Identification Problem in Data Integration
Definition: Occurs when the same real-world entity (e.g., a customer or product) is represented across disparate source databases by different natural keys, varying schemas, or slight spelling variations (e.g., "John Smith" at Branch A vs. "J. Smith" at Branch B), OR when different entities share the same identifier in separate systems.
Resolution Protocol:
  1. Establish a Master Data Management (MDM) framework with fuzzy matching / record linkage (Levenshtein distance, Soundex, address matching).
  2. Create an Enterprise Cross-Reference Mapping Table: (Source_System_ID, Source_Natural_Key, Enterprise_Surrogate_Key).
  3. Always join dimensional references in the DW using the Surrogate Key rather than natural keys.

4. Data Loading Strategies & Acceleration Protocol

Dimension Full Data Refresh Incremental Data Loading
Operation Truncates base table entirely and reloads all rows from scratch. Identifies deltas and applies INSERTS, UPDATES, or SCD Type 2 versions.
When Appropriate 1. Small dimension tables (e.g., Status, Department, Date).
2. High volatility where >30–40% of rows change per refresh.
3. Source systems lacking delta tracking mechanisms.
4. Initial DW load or full disaster resynchronization. 		1. Massive fact tables (millions/billions of rows).
2. Large dimensions with low daily change rates (e.g., 40k changes out of 20M rows = 0.2%).
I/O & Time Cost Proportional to full table volume O(Total Rows). Proportional to delta volume O(Changed Rows).
High-Yield Exam Protocol: Steps to Expedite Bulk Loading

5 Practical Steps to Accelerate Data Loading

  1. Drop or Disable Secondary Indexes & Foreign Key Constraints: Maintaining B-tree indexes row-by-row during bulk load causes massive random I/O and tree rebalancing. Drop them, load data contiguously, and rebuild indexes in bulk.
  2. Direct-Path Bulk Loading: Use direct-path load utilities (e.g., Oracle Direct Path, PostgreSQL COPY, MySQL LOAD DATA INFILE, Teradata FastLoad) that write directly to formatted data blocks on disk above the high-water mark, bypassing the database buffer cache.
  3. NOLOGGING / Minimal Logging: Set table/session to NOLOGGING to disable transaction undo/redo logging for the bulk append, eliminating transaction log disk bottlenecks.
  4. Parallel & Partition-Level Loading: Partition tables (by date/region) and split input data into independent files loaded simultaneously by concurrent threads directly into discrete table partitions.
  5. Staging Tables with Set-Based Operations: Stage incoming records in an unindexed staging table, then execute a single set-based MERGE or partition-swap rather than cursor-based row-by-row iterations.

5. Destructive Merge vs. Constructive Merge

Feature Destructive Merge (In-Place Overwrite / SCD Type 1) Constructive Merge (Versioning / SCD Type 2)
Mechanism Overwrites existing attribute values with incoming new values in-place. Closes current record (End_Date = Current_Date, Is_Current = 'N') and inserts a new row with a new surrogate key.
Historical Tracking No history preserved (Old values permanently lost). Complete history preserved (Full temporal audit trail).
Storage Impact Zero storage growth (Row count remains constant). Table grows monotonically with every change.
When to Use Correcting erroneous data, spelling errors, or when history has zero business significance. Core business attributes where point-in-time analytical correctness matters (e.g., customer address change affecting regional sales reporting).

Key Takeaways: Topic 2

  • Transient data represents current state and is overwritten; periodic data represents historical events and is append-only.
  • Log-based CDC is the most efficient immediate extraction method because it is non-intrusive and creates zero OLTP overhead.
  • Surrogate keys decouple the warehouse from operational schema chaos and resolve the entity identification problem via cross-reference mapping tables.
  • For small tables or high change rates (>30%), use Full Refresh; for large tables with low change rates (<5%), use Incremental Load.
  • Accelerate loading by dropping indexes, using direct-path loaders, enabling NOLOGGING, and loading partitions in parallel.
Practice Questions
Easy: When should the daily ETL batch process be executed for a retail banking system?

Answer: During the off-peak nightly batch window (typically 1:00 AM – 4:00 AM) when physical bank branches are closed, online transaction volumes are minimal, and operational source database CPU/I/O utilization is lowest.

Medium: Assume 40,000 rows out of 20 million rows in a Customer dimension table change each day. Which loading strategy should be used and why?

Answer: Use an Incremental Loading strategy (Delta Upsert / SCD Type 1/2). The changed rows represent only 40,000 / 20,000,000 = 0.2% of the table. A full refresh would needlessly read and write 19.96 million unchanged rows, wasting enormous I/O and processing time.

Hard: Why does dropping secondary indexes before a bulk load and rebuilding them afterward result in fewer total I/Os than inserting with indexes active?

Answer: Inserting records with active indexes causes random I/O and frequent B-tree page splits for every single inserted row. If N rows are inserted into I indexes, the database performs O(N × I) random leaf lookups and block writes. By dropping indexes, records are written contiguously in sequential blocks. Rebuilding indexes in bulk afterward uses high-speed external sorting and sequential bulk-tree construction, achieving optimal 100% leaf packing with purely sequential I/O.

3Join Techniques & Cost Modeling

Nested Loop variants, Sort-Merge Join, Hash Join, the in-memory threshold condition, and Graefe's Duality.

Join performance in DSS environments is fundamentally different from OLTP. OLTP queries retrieve isolated single records using index lookups, while DSS analytical queries join tables with millions of records. Understanding exactly how buffer memory K affects I/O cost is essential for the exam.

1. The Nested Loop Join (NLJ) Family

Let Outer Relation = R1 (r1 records, b1 blocks), Inner Relation = R2 (r2 records, b2 blocks), and Available Buffer Memory = K blocks.

1. Naive / Tuple NLJ

For each record in R1, scan the entire table R2.

Cost = b1 + (r1 × b2)

Worst possible algorithm for DSS. Causes massive repeated disk thrashing.

2. Block Nested Loop (BNLJ)

Allocate K - 2 buffer blocks to hold a chunk of R1. Scan R2 once per chunk.

Cost = b1 + ⌈b1 / (K-2)⌉ × b2

If b1 ≤ K - 2, cost = b1 + b2 (Inner scanned only ONCE!).

3. Index / Clustered NLJ

For each qualifying record of R1, lookup matching keys in R2 via index.

Cost = b1 + Q1 × (Cost_idx + Cost_data)

Extremely fast when Q1 is small and R2 has a clustered index on join key.

2. Sort-Merge Join (SMJ)

Sort-Merge Join sorts both relations on the join attribute, then merges the sorted streams sequentially in a single pass.

Sort-Merge Join Cost Formula
Total Cost = Cost(Filter Outer) + Cost(Sort R1) + Cost(Sort R2) + Cost(Merge Streams)
Where:
  • Sorting Cost: If relation R fits in memory (b ≤ K), Sorting Cost = 0 disk I/O (sorted in RAM).
  • If relation R exceeds memory (b > K), external merge sort is required:
    • Pass 0 (Run Generation): Reads b blocks and writes b blocks into ⌈b / K⌉ sorted runs = 2 × b I/Os.
    • Merge Passes: ⌈logK-1(N)⌉ passes, each pass reading and writing b blocks = 2 × b I/Os per pass.
  • Clustered / Pre-sorted Optimization: If a relation has a clustered index on the join attribute, it is already sorted on disk! Sorting cost = 0 I/O.
  • Merge Phase Cost: Reading both sorted relations once = b1 + b2 blocks.

3. Hash Join (HJ) & The In-Memory Condition

Hash Join designates the smaller relation as the Build Input (R) and the larger relation as the Probe Input (S).

The In-Memory Hash Join Condition (FAST Exam Favorite)
Check if the filtered build relation blocks fit in available memory:
Condition: b_build ≤ K

• If Condition Holds (b_build ≤ K):
  1. Read build relation into memory and construct in-memory hash table: b_build I/Os.
  2. Stream probe relation once through memory, hashing join keys and matching buckets: b_probe I/Os.
  3. Total Hash Join Cost = b_build + b_probe (Partitioning is NOT required!).

• If Condition Fails (b_build > K): Grace / Partitioned Hash Join
  Both relations must be partitioned into B - 1 matching hash buckets on disk, then joined partition by partition.
  Total Cost = Partition Phase (2 × b1 + 2 × b2) + Join Phase (b1 + b2) = 3 × (b1 + b2).

4. Graefe's Divide-and-Conquer Duality

Goetz Graefe established that Sort-Merge Join and Hash Join are duals of the same divide-and-conquer strategy:

Dimension Sort-Merge Join (SMJ) Hash Join (HJ)
Division Mechanism Divides by value range (creates ordered runs). Divides by hash value (creates unordered hash buckets).
Memory Sensitivity Robust to memory fluctuations; graceful degradation across merge passes. Sensitive to memory sizing; severe penalty if bucket exceeds memory (bucket spill).
Data Skew Handles non-uniform key distributions gracefully. Vulnerable to hash bucket skew (hash collisions on frequent values).
Output Characteristics Output is sorted on join key (ideal for downstream ORDER BY or GROUP BY). Output is completely unordered.
Non-Equi Joins Supports inequality joins (<, >, ≤, ≥). Only supports equi-joins ( = ).

Key Takeaways: Topic 3

  • Always identify the Build table (the smaller relation after filtering) and Probe table (the larger relation).
  • Check memory: if b_build ≤ K, Hash Join executes in a single pass with cost = b_build + b_probe.
  • If the inner table has a clustered index on the join key, Index/Clustered NLJ is often vastly superior to both SMJ and Hash Join because it reads only the specific matching blocks of the inner table rather than scanning the entire multi-gigabyte table.
  • In Sort-Merge Join, a clustered index on the join attribute eliminates the sorting phase entirely (0 sort I/O).
Practice Questions
Easy: When is Sort-Merge Join preferred over Hash Join in data warehouse queries?

Answer: (1) When either or both inputs are already sorted or clustered on the join key, (2) when the query contains an explicit downstream ORDER BY or GROUP BY on the join key, or (3) for non-equi joins (e.g. range joins).

Medium: Table A has 45 blocks after filtering. Table B has 180,000 blocks. Memory K = 100 blocks. Compute the I/O cost of Hash Join.

Answer:
1. Build table = Table A (45 blocks); Probe table = Table B (180,000 blocks).
2. Memory check: b_build = 45 ≤ K = 100. Build table fits entirely in memory!
3. Build cost = 45 blocks read.
4. Probe cost = 180,000 blocks read.
5. Total Hash Join Cost = 45 + 180,000 = 180,045 blocks.

Hard: In the scenario above, what if Table B has a clustered index on the join key, Table A has 4800 qualifying rows, and each key in Table A matches 1 block in Table B? What is the cost of Clustered NLJ?

Answer:
Clustered NLJ cost = Cost(Read A) + Q_A × (Cost_idx + Cost_data).
With 1 index block read + 1 data block read per qualifying row:
Cost = 45 + 4800 × (1 + 1) = 45 + 9600 = 9,645 blocks!
Clustered NLJ is over 18 times faster than Hash Join (9,645 vs. 180,045 blocks) because it avoids scanning the 180,000 blocks of Table B!

4Indexing Techniques & Access Paths Masterclass

Mechanics and exact step-by-step I/O formulas for FTS, Single, Combined, Dynamic Bitmap, Static Bitmap, Composite, and Clustered Indexes.

FAST exam problems present a base table with several attributes, selectivities, and a complex multi-predicate query. You are asked to compute the exact I/O cost under 6 to 7 different indexing strategies. Below is the foolproof mathematical guide for every single technique.

1. Full Table Scan (FTS)

Scans every physical block in the base table sequentially. Always the baseline benchmark.

I/O Cost = b   (Where b = ⌈r / bfr⌉)

2. Single Indexing

Select the highest selectivity attribute (the one with the lowest percentage / smallest number of qualifying rows Q).

Single Index Access Cost Formula
1. Select attribute with minimum qualifying rows: Q = min(Q1, Q2, ...).
2. Index access cost: Cost_idx = ⌈ Q / bfri ⌉.
3. Base table access cost:
    • If Q ≥ b: Base Table Cost = b (Capped at full table blocks!).
    • If Q < b: Base Table Cost = Q.
4. Total Cost = Cost_idx + Base Table Cost.

3. Combining Multiple Indexes (RID List ANDing)

The DBMS accesses multiple independent single-column indexes, retrieves their matching RID lists, and intersects them in memory via boolean bitwise AND / set intersection before touching the base table.

Combining Multiple Indexes Cost Formula
1. For each indexed attribute i in WHERE clause:
    Cost_idx_i = ⌈ Q_i / bfri ⌉.
2. Total Index Access Cost = ∑ (Cost_idx_i).
3. Combined qualifying rows: Q_comb = S_comb × r.
4. Base table access cost = min(Q_comb, b).
5. Total Cost = ∑ (Cost_idx_i) + min(Q_comb, b).
Special Rule: For SELECT COUNT(*), Base table cost = 0!

4. Dynamic Bitmap Indexes

Traditional B-tree index RIDs are converted on the fly in memory into transient bitmap vectors. Fast bitwise operations (AND/OR) are performed in CPU cache.

Dynamic Bitmap Cost Equivalence
Because the index entries are retrieved from disk as standard B-tree RIDs, the disk I/O cost of Dynamic Bitmap Indexing is identical to Combining Multiple Indexes:
Total Cost = ∑ (Cost_idx_i) + min(Q_comb, b).

5. Static Bitmap Indexes

Pre-computed bit vectors stored permanently on disk for low-cardinality attributes. Each bit corresponds to one record position in the base table (1 = match, 0 = no match).

Static Bitmap Index Cost Formula
1. Bits per block = B × 8 bits.
2. Blocks per single bitmap vector = ⌈ r / (B × 8) ⌉.
3. Count distinct indexed values queried: e.g., Dept IN ('CS', 'EE') = 2 values.
4. Total Index Access Cost = (Total Distinct Values Queried) × ⌈ r / (B × 8) ⌉.
5. In memory: Perform bitwise OR between values of same column, then bitwise AND across different columns.
6. Base table access cost = min(Q_comb, b).
7. Total Cost = Total Index Access Cost + min(Q_comb, b).

6. Composite Index

A multi-column B-tree index on (Col1, Col2, Col3). Index entries contain the concatenated keys plus the RID. Size of entry is given as Ri.

Composite Index Cost Formula
1. Enumerate all active Cartesian combinations of interest specified in the query.
    Example: publisher IN ('P', 'W') AND year IN (2018, 2020) yields 4 combinations: (P, 2018), (P, 2020), (W, 2018), (W, 2020).
2. For each combination j:
    • Qualifying rows: Q_combo_j = S_col1 × S_col2 × r.
    • Index blocks read: ⌈ Q_combo_j / bfri ⌉.
    • Base table blocks read: Q_combo_j (or combined fetch).
3. Total Cost = ∑ ⌈ Q_combo_j / bfri ⌉ + Q_comb.

7. Clustered Index

The base table records are physically ordered and stored on disk in the sequence of the indexed column.

Clustered Index Cost Formula
Assume clustered index is on the best selectivity column (or specified column) with qualifying rows Q.
1. Index access cost: Cost_idx = ⌈ Q / bfri ⌉.
2. Base table access cost: Because matching records are contiguous on disk:
    Base Table Cost = ⌈ Q / bfr ⌉   (Divided by base blocking factor!)
3. Remaining WHERE predicates are evaluated in memory on the fetched records.
4. Total Cost = ⌈ Q / bfri ⌉ + ⌈ Q / bfr ⌉.

Key Takeaways: Topic 4

  • Single Index: Only practical when selectivity is tiny (<2%). If Q ≥ b, access cost exceeds FTS!
  • Combining Multiple Indexes: Reads index blocks for all predicates, intersects in RAM, then visits only Qcomb base blocks.
  • Static Bitmap: Unmatched for low-cardinality attributes. Cost per value is just ⌈r / (B × 8)⌉ blocks.
  • Composite Index: Optimal for fixed conjunctions, but requires reading index entries for each Cartesian combination.
  • Clustered Index: Drastically slashes base table reads from Q down to ⌈Q / bfr⌉.
Practice Questions
Easy: Table has 1,280,000 rows. Block size B = 50 KB = 51,200 bytes. How many blocks does ONE static bitmap vector require?

Answer:
Bits per block = 51,200 × 8 = 409,600 bits.
Blocks per vector = ⌈1,280,000 / 409,600⌉ = ⌈3.125⌉ = 4 blocks.

Medium: For a query with 3 conditions, Single Index costs 6,416 blocks, while Combining Multiple Indexes costs 3,664 blocks. Why does combining multiple indexes perform better even though it accesses 3 index trees?

Answer: Because the single index has individual selectivity Q = 51,200 > b = 6,400, forcing the engine to read all 6,400 base blocks. In contrast, combining multiple indexes intersects the RID lists in memory, shrinking the qualifying records down to Qcomb = 3,380 rows. The base table reads drop from 6,400 to 3,380 blocks, which easily overcomes the minor overhead of reading 284 index blocks.

Hard: A query evaluates SELECT COUNT(*) with 3 conditions where combining multiple indexes accesses 4, 8, and 19 index blocks. Combined qualifying rows = 35. What is the total I/O cost?

Answer:
Total Index access = 4 + 8 + 19 = 31 blocks.
Because the query is SELECT COUNT(*), no base table attributes are needed. The count of surviving RIDs after in-memory intersection directly yields the answer. Base table access = 0 blocks.
Total I/O = 31 + 0 = 31 blocks!

3. Top 10 Exam Traps & How to Avoid Them

Trap 1: Forgetting the Q ≥ b Cap

When computing unclustered single index access, students often write Total = 4 + 3840 = 3844. Wrong! The base table only has 2,000 blocks, so you can never read 3,840 distinct blocks. It caps at b = 2000, giving 2004.

Trap 2: Bits per Block in Static Bitmaps

Remember that block size B is in bytes, but each bitmap entry is 1 bit! You must multiply by 8: Bits per block = B × 8. Omitting the × 8 makes your bitmap 8 times too large!

Trap 3: Base Reads for COUNT(*)

If a query asks for SELECT COUNT(*) and multiple secondary indexes exist, base table access is 0! RIDs can be counted directly after in-memory intersection without fetching base records.

Trap 4: Forgetting the Outer Filter Cost in Joins

When joining Table A and Table B where Table A has a WHERE filter, the total join cost MUST include the cost to filter Table A first: Total = Filter(A) + Join_Cost!

Trap 5: Clustered Index on Join Key

If the inner table has a clustered index on the join key (e.g. BookLoans.BookID), Sort-Merge Join requires 0 sort I/O for that table because it is already sorted on disk!

Trap 6: In-Memory Hash Join Check

Always state the memory condition: b_build ≤ K. If the filtered outer table occupies 45 blocks and K = 100, explicitly write: "Since 45 ≤ 100, the hash table fits entirely in memory; recursive partitioning is not required."

Trap 7: Combining OR vs. AND Selectivity

For independent AND conditions: S = S1 × S2. For OR / IN conditions on the same attribute: S = S1 + S2. Never multiply OR percentages!

Trap 8: Floor vs. Ceil Misapplication

Remember: bfr = ⌊B/R⌋ (Floor). bfri = ⌊B/Ri⌋ (Floor). But block allocation is ALWAYS ⌈r / bfr⌉ (Ceiling)!

Trap 9: Two Inexpensive vs. Two Efficient Extraction

If asked for the two most inexpensive extraction methods: Full Table Dumps and Timestamp-based queries. If asked for the two most efficient immediate: Log-based CDC and Triggers.

Trap 10: Clustered Base Access Formula

In a clustered index, base table access is ⌈Q / bfr⌉, NOT Q! If Q = 6,000 and bfr = 40, base access is 150 blocks, not 6,000.
