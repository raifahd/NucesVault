1OLTP vs DSS vs DW

Lab 01 — Understanding the two worlds of data systems

Every database serves a purpose. OLTP (Online Transaction Processing) keeps day-to-day business running; a DSS/DW (Decision Support System / Data Warehouse) helps managers decide. They are built differently on purpose.

Definition
OLTP: Optimised for high-speed, row-level INSERT/UPDATE/DELETE operations. One transaction at a time. Normalised schema to protect consistency.
Definition
DSS / Data Warehouse: Optimised for aggregation across millions of rows. Read-heavy, historical. Answers "Which region drove the most revenue this quarter?"

Key Comparison

DimensionOLTPDSS / DW
Primary operationINSERT / UPDATE / DELETESELECT + GROUP BY / aggregates
Query typePoint lookup — "Order 104512?"Aggregation — "Revenue by region?"
Schema styleNormalised (3NF)Denormalised star/snowflake
Data currencyCurrent (real-time)Historical (periodic loads)
Typical usersClerks, operational staffManagers, analysts, BI tools
Rows per query1–10 rowsMillions of rows
Performance concernWrite throughput, concurrencyRead speed, aggregation performance

Role of DW/BI in Decision-Making

  • Single source of truth — one consistent version of business data across systems
  • Historical context — compare this quarter to last year
  • Cross-system integration — sales + inventory + HR in one place
  • Self-service analytics — managers answer questions without IT involvement
Example

CampusCart: Two Query Worlds

-- OLTP: point lookup — retrieve one specific order
SELECT * FROM lab01.campuscart_sales WHERE order_id = 104250;

-- DSS: aggregation across 7,800 rows
SELECT date_trunc('month', order_date) AS month,
       category,
       SUM(net_revenue_pkr) AS net_revenue
FROM   lab01.campuscart_sales
WHERE  order_status <> 'Cancelled'
GROUP  BY 1, 2
ORDER  BY 1, net_revenue DESC;
Exam Tip
EXPLAIN ANALYZE: OLTP point-lookup → Index Scan (fast, few rows). DSS aggregate → Sequential Scan + HashAggregate (scans everything). You may be asked to identify which is OLTP vs DSS from the plan.

Key Takeaways

  • OLTP = fast writes, current data, normalised, point lookups
  • DSS = fast reads, historical, aggregation, millions of rows
  • DW is the foundation for BI — consolidates, cleans, and stores history
  • Same dataset → very different query patterns depending on the question
Practice Questions
Easy: Give two differences between OLTP and DSS systems.

Answer: (1) OLTP is optimised for INSERT/UPDATE/DELETE on individual rows; DSS is optimised for SELECT aggregations across millions of rows. (2) OLTP stores current data; DSS stores historical data over time.

Medium: "Which product category had the highest return count last month?" — OLTP or DSS query? Why?

Answer: DSS. It scans all order rows for last month, filters by order_status='Returned', groups by category, and counts — a classic aggregation query, not a point lookup.

Hard: Why is running DSS queries directly on an OLTP production database problematic?

Answer: DSS queries do full-table scans and hold locks for long durations, competing with the constant INSERT/UPDATE stream on OLTP — causing lock contention, degraded write performance, and slower response for operational users. The normalised schema also requires many joins, making analytical queries slow. A separate DW with denormalised schema and read-only access eliminates these problems.

2PostgreSQL Basics

Lab 01 — DDL: databases, schemas, tables, data types, PKs, FKs

PostgreSQL organises objects in a three-level hierarchy: Database → Schema → Table. Schemas are namespaces — lab01 and lab03 can coexist in the same database without name conflicts.

Example

Complete Lab Setup Workflow

-- 1. Create schema (namespace)
CREATE SCHEMA IF NOT EXISTS lab01;

-- 2. Create table inside schema
CREATE TABLE lab01.campuscart_sales (
    order_id          INT,
    order_date        DATE,
    customer_id       INT,
    customer_segment  TEXT,
    product_id        INT,
    product_name      TEXT,
    category          TEXT,
    region_id         TEXT,
    channel           TEXT,
    quantity          INT,
    unit_price_pkr    NUMERIC(12,2),   -- NUMERIC for money, never FLOAT!
    discount_pct      INT,
    order_status      TEXT,
    gross_revenue_pkr NUMERIC(14,2),
    net_revenue_pkr   NUMERIC(14,2)
);

-- 3. Manual insert
INSERT INTO lab01.campuscart_sales (order_id, order_date, category, net_revenue_pkr)
VALUES (9999, '2025-03-15', 'Electronics', 4500.00);

-- 4. Import CSV: pgAdmin → right-click table → Import/Export Data
--    Settings: Header=Yes, Delimiter=comma, Encoding=UTF-8

Primary Keys & Foreign Keys

Definition
Primary Key (PK): Uniquely identifies every row. Cannot be NULL. Example: order_id INT PRIMARY KEY.
Definition
Foreign Key (FK): References the PK of another table. Enforces referential integrity — prevents orphan rows. Example: product_id INT REFERENCES products(product_id).
Example

PK + FK in Practice

CREATE TABLE products (
    product_id   INT PRIMARY KEY,
    product_name TEXT,
    category     TEXT
);

CREATE TABLE order_items (
    line_id    INT PRIMARY KEY,
    order_id   INT,
    product_id INT REFERENCES products(product_id),  -- FK
    quantity   INT
);
Common Mistake
Confusing schemas and databases. A schema is a namespace inside one database (like a folder). A database is a separate server-level container. Labs use one database + multiple schemas.

Key Takeaways

  • Hierarchy: CREATE DATABASE → CREATE SCHEMA → CREATE TABLE
  • Use NUMERIC(p,s) for money — never FLOAT (causes rounding errors)
  • PKs enforce uniqueness; FKs enforce referential integrity
  • Import CSVs: pgAdmin → right-click table → Import/Export Data
Practice Questions
Easy: What is a schema in PostgreSQL?

Answer: A namespace/container within a database that groups related tables. Example: lab03 for normalised tables and lab03_report for reporting tables — both in the same database, logically separated.

Medium: Write DDL for a Customers table: customer_id, name, segment, registration_date.

Answer:

CREATE TABLE customers (
    customer_id       INT PRIMARY KEY,
    name              TEXT,
    segment           TEXT,
    registration_date DATE
);

Hard: order_items has a FK on product_id. Developer tries to INSERT a row with product_id=999 that doesn't exist in products. What happens?

Answer: PostgreSQL raises a foreign key violation error and rejects the INSERT. The FK constraint verifies product_id=999 exists in products before allowing the row — referential integrity enforcement. Fix: insert the product first, or the FK is wrongly pointing to the wrong table.

3Analytical SQL

Labs 01 & 04 — SELECT, aggregations, GROUP BY, HAVING, JOINs, Top-N, trend analysis

Mental model for analytical SQL: filter rows → group rows → aggregate → filter groups → sort/present. This maps exactly to: WHERE → GROUP BY → aggregate functions → HAVING → ORDER BY.

Example

All Clauses Together — The Complete Query

SELECT
    category,
    channel,
    COUNT(*)                  AS order_count,
    SUM(net_revenue_pkr)      AS total_revenue,
    AVG(net_revenue_pkr)      AS avg_revenue,
    MIN(net_revenue_pkr)      AS min_revenue,
    MAX(net_revenue_pkr)      AS max_revenue
FROM   lab01.campuscart_sales
WHERE  order_status = 'Completed'          -- row-level filter (BEFORE grouping)
GROUP  BY category, channel                -- collapse rows into groups
HAVING SUM(net_revenue_pkr) > 1000000     -- group-level filter (AFTER aggregation)
ORDER  BY total_revenue DESC               -- sort output
LIMIT  5;                                  -- top-N

Key Clauses Reference

ClausePurposeKey Rule
WHEREFilter rows before groupingCannot reference aggregate functions
GROUP BYCollapse rows by distinct valuesEvery non-aggregate in SELECT must be here
HAVINGFilter groups after aggregationUse when condition involves SUM, COUNT, etc.
ORDER BYSort resultDESC = largest first; ASC = default
DISTINCTRemove duplicate rowsSELECT DISTINCT category FROM …
LIMITReturn only N rowsUse AFTER ORDER BY for Top-N

Top-N Queries

Example
-- ALWAYS aggregate first, THEN limit
SELECT product_name, category,
       SUM(net_revenue_pkr) AS total_revenue
FROM   lab01.campuscart_sales
WHERE  order_status = 'Completed'
GROUP  BY product_name, category
ORDER  BY total_revenue DESC
LIMIT  5;   -- Top 5 products

Trend Analysis (Monthly)

Example
-- date_trunc truncates date to given precision
SELECT date_trunc('month', order_date) AS month,
       SUM(net_revenue_pkr)            AS monthly_revenue,
       COUNT(DISTINCT order_id)        AS orders
FROM   lab01.campuscart_sales
WHERE  order_status <> 'Cancelled'
GROUP  BY 1          -- "1" refers to first SELECT column
ORDER  BY 1;         -- chronological order

JOINs

Definition
INNER JOIN: Returns only rows where the condition matches in both tables. Unmatched rows excluded from both sides.
Definition
LEFT JOIN: Returns ALL rows from the left table + matched rows from the right. Unmatched right-side columns are NULL. Use for orphan detection.
Example

INNER JOIN vs LEFT JOIN + Orphan Detection

-- INNER JOIN: only items with a matching product
SELECT oi.line_id, p.product_name, oi.quantity
FROM   order_items oi
INNER JOIN products p ON oi.product_id = p.product_id;

-- LEFT JOIN: all items; NULL product_name = orphan
SELECT oi.line_id, p.product_name
FROM   order_items oi
LEFT  JOIN products p ON oi.product_id = p.product_id;

-- Orphan detection pattern:
SELECT oi.line_id
FROM   order_items oi
LEFT  JOIN products p ON oi.product_id = p.product_id
WHERE  p.product_id IS NULL;   -- these items have no matching product
Exam Tip — HAVING vs WHERE
The #1 exam trap. Use WHERE order_status = 'Completed' (row filter). Use HAVING SUM(revenue) > 1000000 (group filter). You cannot write WHERE SUM(...) > ... — it's a syntax error.
Common Mistake
Top-N before aggregating. Always: GROUP BY → ORDER BY DESC → LIMIT. If LIMIT comes before GROUP BY, you get raw top rows, not the top aggregated groups.

Key Takeaways

  • Execution order: WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
  • SUM, AVG, COUNT, MIN, MAX — collapse multiple rows into one value per group
  • INNER JOIN = intersection only; LEFT JOIN = all left + matched right (NULLs for misses)
  • Top-N = GROUP BY + ORDER BY DESC + LIMIT — always this order
  • Trend: date_trunc('month', date_col) groups all days in a month together
Practice Questions
Easy: Write a query for total net revenue and order count per channel, completed orders only.

Answer:

SELECT channel,
       SUM(net_revenue_pkr) AS total_revenue,
       COUNT(*)             AS order_lines
FROM   lab01.campuscart_sales
WHERE  order_status = 'Completed'
GROUP  BY channel
ORDER  BY total_revenue DESC;

Medium: Return customer segments where avg order-line revenue exceeds PKR 5,000, completed orders only.

Answer:

SELECT customer_segment,
       AVG(net_revenue_pkr) AS avg_revenue
FROM   lab01.campuscart_sales
WHERE  order_status = 'Completed'
GROUP  BY customer_segment
HAVING AVG(net_revenue_pkr) > 5000
ORDER  BY avg_revenue DESC;

Hard: Top 3 region+category combinations by net revenue, only combinations with more than 100 orders.

Answer:

SELECT region_name, category,
       SUM(net_revenue_pkr) AS total_revenue,
       COUNT(*)             AS order_count
FROM   lab01.campuscart_sales
WHERE  order_status <> 'Cancelled'
GROUP  BY region_name, category
HAVING COUNT(*) > 100
ORDER  BY total_revenue DESC
LIMIT  3;

Definition
Power Query: The ETL layer inside Power BI. Apply transformations (change types, rename columns, filter rows, remove duplicates) before data enters the model. All steps auto-replay on refresh.

Definition

Practice Questions
Easy: What is a slicer? How does it differ from the Filters pane?

Answer: A slicer is an on-canvas visual element users click to interactively filter page visuals. The Filters pane is behind-the-scenes — developers set static/dynamic filters there. Slicers are user-facing and always visible; Filters pane entries can be hidden.

Medium: Power BI won't create a 1:* relationship between Products[product_id] and Sales[product_id]. Likely cause and fix?

Answer: Products table has duplicate product_id values (or NULLs). Fix: Power Query → Remove Duplicates on product_id, or investigate the source. The "1" side must have unique, non-null keys.

Hard: What is "filter context" in Power BI? How does the same measure show different values in a card vs a bar chart?

Answer: Filter context = the set of active filters Power BI applies when evaluating a measure. In a card with no slicers, all rows are visible → grand total. In a bar chart with Category on the axis, each bar creates its own filter context ("Electronics only", "Stationery only", etc.) — the same SUM formula evaluates only those rows. The formula is identical; the data it sees changes with context.

5Normalization & Denormalization

Lab 03 — Logical vs physical models, 3NF, pre-join, column replication, pre-aggregation

Normalization reduces redundancy and prevents inconsistency. Denormalization deliberately adds redundancy for analytical performance. Both are valid — the key is knowing when to use each.

Definition
Logical Data Model: Describes what data exists — entities, attributes, relationships, and business rules. Technology-independent ERD with PKs, FKs, and cardinalities.
Definition
Physical Data Model: Describes how data is stored — actual table names, column types, indexes, and constraints for a specific DBMS (PostgreSQL). Translates the logical model into runnable DDL.

Why Normalize? The Three Anomalies

A wide flat table (like the CampusCart CSV) stores product name, category, region name on thousands of rows — creating:

  • Update anomaly: Rename "Electronics" → must update thousands of rows. Miss one → inconsistency.
  • Insert anomaly: Can't add a product without also having a sale.
  • Delete anomaly: Delete the last sale of a product → lose the product's details forever.
Example

Lab 03: Normalised Schema (3NF)

CREATE TABLE lab03.regions (
    region_id TEXT PRIMARY KEY, region_name TEXT);

CREATE TABLE lab03.customers (
    customer_id INT PRIMARY KEY,
    customer_name TEXT, customer_segment TEXT);

CREATE TABLE lab03.products (
    product_id INT PRIMARY KEY,
    product_name TEXT, category TEXT, brand TEXT);

CREATE TABLE lab03.orders (
    order_id INT PRIMARY KEY,
    order_date DATE,
    customer_id INT REFERENCES lab03.customers(customer_id),
    region_id   TEXT REFERENCES lab03.regions(region_id),
    channel TEXT, payment_method TEXT, order_status TEXT);

CREATE TABLE lab03.order_items (
    line_id INT PRIMARY KEY,
    order_id   INT REFERENCES lab03.orders(order_id),
    product_id INT REFERENCES lab03.products(product_id),
    quantity INT, unit_price_pkr NUMERIC(12,2),
    discount_pct INT, net_revenue_pkr NUMERIC(14,2));

-- Load dimensions from flat source using DISTINCT
INSERT INTO lab03.regions
SELECT DISTINCT region_id, region_name FROM lab03.raw_sales_flat;

INSERT INTO lab03.customers
SELECT DISTINCT customer_id, customer_name, customer_segment
FROM   lab03.raw_sales_flat;

Three Denormalization Strategies

Definition
1. Pre-Join Denormalization: Materialise all joins into one wide reporting table. Query reads one table instead of 4–5 joins at runtime. Trade-off: data duplication, must refresh when sources change.
Example
CREATE SCHEMA lab03_report;

CREATE TABLE lab03_report.sales_prejoined AS
SELECT oi.line_id, o.order_id, o.order_date,
       c.customer_segment, r.region_name,
       p.product_name, p.category, p.brand,
       o.channel, oi.quantity, oi.net_revenue_pkr
FROM   lab03.order_items oi
JOIN   lab03.orders    o ON oi.order_id   = o.order_id
JOIN   lab03.customers c ON o.customer_id = c.customer_id
JOIN   lab03.regions   r ON o.region_id   = r.region_id
JOIN   lab03.products  p ON oi.product_id = p.product_id;
Definition
2. Column Replication / Movement: Copy frequently-filtered attributes (e.g., customer_segment, region_name) into another table (Orders) to avoid joins at query time. Risk: stale if master changes.
Definition
3. Pre-Aggregation: Compute and store summary totals in advance. Repetitive executive dashboards hit a tiny summary table instead of millions of detail rows.
Example
CREATE TABLE lab03_report.monthly_region_category AS
SELECT DATE_TRUNC('month', o.order_date) AS reporting_month,
       r.region_name, p.category,
       SUM(oi.net_revenue_pkr)    AS total_net_revenue,
       SUM(oi.quantity)           AS total_quantity,
       COUNT(DISTINCT o.order_id) AS distinct_orders
FROM   lab03.order_items oi
JOIN   lab03.orders   o ON oi.order_id  = o.order_id
JOIN   lab03.regions  r ON o.region_id  = r.region_id
JOIN   lab03.products p ON oi.product_id= p.product_id
WHERE  o.order_status = 'Completed'
GROUP  BY 1, 2, 3;
-- Result: tiny table (12 mo × N regions × M categories) — instant queries

Design Selection Guide

WorkloadBest DesignReason
Live order updates, frequent writesNormalised (3NF)Updates one place, no anomalies
Executive repeating dashboardPre-AggregatedTiny summary table, instant
Analyst exploring raw detailPre-JoinedOne fat table, no joins needed
Region rename must be consistentNormalisedChange one row in Regions table

Key Takeaways

  • Logical = what data (ERD, tech-agnostic); Physical = how stored (DDL for a specific DBMS)
  • Normalization eliminates redundancy → prevents update/insert/delete anomalies
  • Pre-join: one fat table, no runtime joins — good for exploratory analysis
  • Column replication: copies attributes for fast filtering — risk is staleness
  • Pre-aggregation: tiny summary table for repetitive reporting — fastest for dashboards
Practice Questions
Easy: What is an update anomaly? Example using a flat sales table.

Answer: Changing one logical fact requires updating many rows. Example: renaming region "East Lahore" in a flat table requires updating 2,000 rows. Miss 500 → inconsistency. A normalised model stores it once in Regions — one row to update.

Medium: Compare pre-join denormalization and pre-aggregation. When would you use each?

Answer: Pre-join creates a wide table at detail grain (all attributes joined). Use for exploratory analysis needing raw rows with many attributes. Pre-aggregation computes totals at summary grain. Use for repetitive executive dashboards querying the same GROUP BY daily. Pre-aggregation is faster for summaries; pre-join is more flexible but still holds all detail.

Hard: Developer copies region_name into Orders table (column replication). "North Zone" is later renamed to "Northern Zone" in Regions. What problem arises?

Answer: Orders still shows "North Zone" while Regions shows "Northern Zone". Reports querying Orders get the old name; reports joining Regions get the new name — inconsistency. A normalised design stores only region_id in Orders and joins to Regions for the name. One update to Regions propagates everywhere automatically.

6Dimensional Modeling

Lab 05 — Star schema, fact/dimension tables, grain, measures, natural/surrogate keys

Dimensional modeling organises data for analytics. It answers: "What happened, when, where, by whom, involving what?" The result is a star schema — one central fact table surrounded by dimension tables.

Definition
Business Process: The analytical subject being modelled. One fact table per business process. Examples: Sales Transactions, Inventory Snapshots, Promotions.
Definition
Grain: Precise description of what one row in the fact table represents. Must be declared BEFORE building anything else. Example: "One row in FactSales = one order-line item for one product."
Definition
Fact Table: Central table. Contains numeric measures (quantities, revenues) + FK references to dimensions. Millions of rows, narrow columns.
Definition
Dimension Table: Describes context — who, what, where, when. Contains descriptive attributes. Thousands of rows, wide columns. Examples: DimDate, DimProduct, DimCustomer.

Measures: Additivity

Natural Keys vs Surrogate Keys

Definition
Natural Key (Business Key): Identifier from source system — e.g., customer_code = "C0042". May change, may not be unique across multiple sources.
Definition
Surrogate Key: Meaningless integer generated by the warehouse — e.g., customer_key = 117. Never changes. Insulates DW from source changes. Required for versioning (SCD).

Why Surrogate Keys? (3 Reasons to Know)

  1. Source independence: Source can renumber business keys — surrogate stays stable in DW
  2. History/versioning: When a customer changes segment, a new surrogate key is issued; old facts keep the old key
  3. Multi-source integration: Two systems both using product_code "P100" for different products — surrogates disambiguate

Definition
Degenerate Dimension: A business identifier (like order_id) stored directly in the fact table with no separate dimension table. It has no descriptive attributes worth a full dimension.
Exam Tip
Grain first, always. Before any DDL, write: "One row in FactSales represents ___." This determines what FKs, measures, and key strategy you need. Changing grain mid-design means redesigning everything.

Key Takeaways

  • Design order: Business Process → Grain → Dimensions → Facts
  • Fact table = measures + FK surrogate keys (many rows, narrow)
  • Dimension table = descriptive context (fewer rows, wide)
  • Natural key = source identifier; Surrogate key = warehouse integer, never changes
  • Star schema: one fact + dimensions connecting directly — simple joins for BI tools
Practice Questions
Easy: What is the grain of a fact table and why must it be declared first?

Answer: The grain is a precise statement of what one row represents (e.g., "one order-line item"). It must be declared first because it determines which measures belong, which dimensions connect, and how many rows the table has. Changing the grain mid-design forces a complete redesign.

Medium: Why is unit_price_pkr non-additive? How do you compute a correct overall average price?

Answer: SUM(unit_price_pkr) across rows is meaningless — it adds selling prices for different products. Correct weighted average: SUM(net_revenue_pkr) / SUM(quantity). The numerator and denominator are both additive; dividing them gives the correct average price.

Hard: Two source systems both use customer_code "C100" for completely different customers. How does a surrogate key solve this?

Answer: The ETL tags source keys with their origin (e.g., "SysA-C100" vs "SysB-C100") before loading as business keys in the dimension. Each gets a unique surrogate (e.g., customer_key 412 and 873). The fact table stores only surrogates, so the two different "C100" customers are unambiguously separate — even though their raw business keys look identical.

ROLLUP — Hierarchical Subtotals

ROLLUP(A, B, C) generates subtotals by progressively removing columns from the right: (A,B,C), (A,B), (A), () — the grand total. 4 levels for 3 dimensions.

Example

Product Hierarchy Rollup: Region → Category → Product

SELECT
    CASE WHEN GROUPING(r.region_name) = 1 THEN 'ALL REGIONS'
         ELSE r.region_name END  AS region,
    CASE WHEN GROUPING(p.category)    = 1 THEN 'ALL CATEGORIES'
         ELSE p.category END     AS category,
    CASE WHEN GROUPING(p.product_name)= 1 THEN 'ALL PRODUCTS'
         ELSE p.product_name END AS product,
    SUM(fs.net_revenue_pkr)      AS net_revenue
FROM   lab04.fact_sales fs
JOIN   lab04.dim_product p ON fs.product_id = p.product_id
JOIN   lab04.dim_region  r ON fs.region_id  = r.region_id
GROUP  BY ROLLUP(r.region_name, p.category, p.product_name)
ORDER  BY r.region_name NULLS LAST, p.category NULLS LAST;
-- Rows: product-level | category subtotals | region subtotals | grand total
Definition
GROUPING(column): Returns 1 when the column was removed by ROLLUP/CUBE (subtotal row), and 0 for normal detail rows. Use with CASE to replace NULL labels with "ALL REGIONS", etc.

Time Hierarchy Rollup

Example
SELECT d.year, d.quarter, d.month,
       SUM(fs.net_revenue_pkr) AS revenue
FROM   lab04.fact_sales fs
JOIN   lab04.dim_date d ON fs.date_key = d.date_key
GROUP  BY ROLLUP(d.year, d.quarter, d.month)
ORDER  BY d.year NULLS LAST, d.quarter NULLS LAST, d.month NULLS LAST;
-- Output: monthly detail → quarter subtotals → year subtotals → grand total

CUBE — All Combinations

CUBE(A, B, C) generates ALL possible subtotal combinations: 2³ = 8 grouping sets. Adding one dimension doubles the combinations.

Example

Two-Dimensional Cube: Region × Channel

SELECT
    COALESCE(r.region_name, 'ALL REGIONS') AS region,
    COALESCE(fs.channel,    'ALL CHANNELS') AS channel,
    SUM(fs.net_revenue_pkr)                AS revenue
FROM   lab04.fact_sales fs
JOIN   lab04.dim_region r ON fs.region_id = r.region_id
GROUP  BY CUBE(r.region_name, fs.channel)
ORDER  BY r.region_name NULLS LAST, fs.channel NULLS LAST;
-- Includes: Region+Channel detail | Region-only subtotals |
--           Channel-only subtotals | Grand total (both NULL)
Dimensions in CUBEGrouping Sets Generated
2 (A, B)2² = 4
3 (A, B, C)2³ = 8
4 (A, B, C, D)2⁴ = 16
Common Mistake — ROLLUP vs CUBE
ROLLUP follows one strict hierarchy (A → B → C → total) — use for time or product hierarchies. CUBE generates every possible combination — use when there's no natural hierarchy and you want all subtotals (region × channel × category).

Key Takeaways

  • ROLAP: query star directly | MOLAP: pre-computed cubes | HOLAP: both | DOLAP: local desktop
  • ROLLUP(A,B,C) → 4 subtotal levels: (A,B,C), (A,B), (A), () — hierarchical
  • CUBE(A,B,C) → 2³ = 8 grouping sets — all combinations
  • GROUPING(col) = 1 → subtotal row, = 0 → normal detail row
  • Adding one dimension to CUBE doubles the subtotal combinations
Practice Questions
Easy: What is the difference between ROLLUP and CUBE?

Answer: ROLLUP generates subtotals along a single hierarchy — progressively removing columns right to left (detail → subtotal → total). CUBE generates subtotals for ALL possible combinations of listed columns. ROLLUP is for hierarchies (Year-Quarter-Month); CUBE is for cross-dimensional analysis where every combination matters.

Medium: CUBE on (Region, Channel, Category) produces how many grouping sets?

Answer: 2³ = 8: (R,Ch,Cat), (R,Ch), (R,Cat), (Ch,Cat), (R), (Ch), (Cat), () = grand total.

Hard: Explain HOLAP and when you'd choose it over pure ROLAP.

Answer: HOLAP keeps detailed fact data in relational tables (ROLAP layer) for ad-hoc queries, while pre-computing frequently-used summaries in materialised aggregate tables (MOLAP layer). Choose HOLAP when: most user queries are repetitive and standard (use pre-computed tables for speed), but analysts occasionally need raw detail (use the relational star). Pure ROLAP is slower for repetitive queries; pure MOLAP can't answer unexpected detail-level questions.

Easy: What is the purpose of a staging schema in a DW pipeline?

Answer: Staging is a landing zone for raw source data, preserved as-is without transformation. 2. Analytical SQL & Window Functions Cheatsheet (Labs 01 & 02)

Analytical SQL avoids multiple correlated subqueries by computing ranking, running totals, and period-over-period differences across partitioned subsets of data in a single scan.

Function / Clause Syntax Example Behavior on Ties & Use Case
ROW_NUMBER() ROW_NUMBER() OVER (PARTITION BY category ORDER BY sales DESC) Always unique: 1, 2, 3, 4. Used to deduplicate or grab Top-1 per group.
RANK() RANK() OVER (ORDER BY score DESC) Ties get equal rank, skips ranks: 1, 2, 2, 4. Used for competition ranking.
DENSE_RANK() DENSE_RANK() OVER (ORDER BY score DESC) Ties get equal rank, no gaps: 1, 2, 2, 3. Ideal for financial tiers.
LAG() / LEAD() LAG(revenue, 1) OVER (PARTITION BY dept ORDER BY month_id) Fetches previous / next row value. Essential for Month-over-Month (MoM) growth: (rev - lag)/lag.
SUM() OVER (...) SUM(rev) OVER (ORDER BY dt ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) Computes cumulative running total from beginning of partition up to current row.
Frame Specification Warning: ROWS vs RANGE
ROWS BETWEEN operates on exact physical row offsets (e.g. exactly 2 preceding physical rows).
RANGE BETWEEN operates on logical value intervals of the ORDER BY column (default if omitted: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which treats duplicate order values identically). For moving averages over time with missing dates, physical ROWS will skip calendar months!

3. Normalization (3NF) vs Physical Denormalization (Labs 03 & 04)

Normalization reduces redundancy to protect write integrity; physical denormalization intentionally introduces controlled redundancy to eliminate expensive relational JOINs during decision support queries.

Normal Form Core Requirement Eliminated Anomaly
1NF (Atomic Values) Atomic columns (no arrays or comma-delimited values); primary key identified; no repeating groups. Prevents multi-value parsing errors and undefined row addresses.
2NF (No Partial Dependency) Must be in 1NF + every non-key column depends on the entire candidate key (not just part of a composite key). Prevents storing order attributes repeatedly for every line item.
3NF (No Transitive Dependency) Must be in 2NF + non-key columns cannot depend on other non-key columns ($A o B o C$). Prevents city/region data duplication across millions of customer records.
3 Denormalization Techniques for Analytical DSS
  • Pre-join Denormalization: Merging parent table (e.g., orders) into child table (e.g., order_items) into a single wide flat table. Benefit: Zero JOINs at query time. Trade-off: High storage redundancy.
  • Column Replication / Movement: Copying frequently filtered descriptive columns (e.g., category_name) into the fact table or intermediate lookup table to satisfy 90% of queries without touching the dimension.
  • Pre-aggregation: Building dedicated summary tables (e.g., agg_monthly_sales) storing pre-calculated SUM(sales) and COUNT(orders) per month.

4. Dimensional Modeling & Kimball Architecture (Labs 04 & 05)

Kimball dimensional modeling centers around business processes. Every design follows four disciplined steps:

  1. Select the Business Process: E.g., Retail Sales, Order Fulfillment, Inventory Snapshot, Exam Attendance.
  2. Declare the Grain: Specify exactly what one single row in the fact table represents before selecting any columns.
  3. Identify Dimensions: The contextual descriptors (Who, What, Where, When, Why, How).
  4. Identify Facts & Measures: The quantitative numeric metrics generated at that precise grain.
Measure Type Definition & Rule Classic Examples
Fully Additive Can be summed across all dimensional hierarchies (time, store, customer, product). quantity_sold, sales_amount, discount_cost
Semi-Additive Can be summed across some dimensions (e.g. store, product), but never across time. Use ending value or average over time. account_balance, inventory_quantity_on_hand, headcount
Non-Additive Cannot be meaningfully summed across any dimension. Must be calculated as a ratio of components. unit_price, profit_margin_pct, tax_rate
Surrogate Keys vs Natural Keys
Never use source natural/business keys as Primary Keys or Foreign Keys in the DW.
  • Immunity: Protects DW when source systems change their format or reuse keys.
  • Multi-source Integration: Resolves key collisions when Branch A and Branch B both have Customer ID 101.
  • Historical Tracking (SCD Type 2): A customer who moves has one business key but multiple surrogate key rows for each address revision.
  • Performance: Joins on compact 4-byte or 8-byte integers are orders of magnitude faster than compound text strings.
  • Unknown Members: Allows inserting a placeholder row with key -1 for orphan records.

Master Self-Assessment Questions
Question 1: Why is an integer surrogate key superior to a UUID or natural text code in fact tables?

Answer: (1) Storage: Integer surrogate keys use 4 bytes (or 8 bytes for bigint), whereas natural string codes or UUIDs consume 16–36 bytes per row. In a 50-million row fact table with 6 foreign keys, this saves tens of gigabytes of RAM. (2) Join Performance: CPU integer comparison is hardware-accelerated and fits neatly into L1/L2 CPU caches. (3) Isolation: If the source system renames a customer code or recycles an ID, the warehouse history remains intact.

Question 2: In a monthly sales report with CUBE(Region, Category, Year), how many grouping combinations are generated?

Answer: For $N = 3$ dimensions in CUBE, the number of grouping sets is $2^N = 2^3 = 8$ distinct combinations: (Region, Category, Year), (Region, Category), (Region, Year), (Category, Year), (Region), (Category), (Year), and () [grand total]. For ROLLUP, it would only be $3 + 1 = 4$ levels.

Question 3: If an ETL load finishes with zero errors, what two reconciliation queries MUST be run before sign-off?

Answer: (1) Row Count Reconciliation: SELECT COUNT(*) FROM staging.stg_orders must match SELECT COUNT(*) FROM dw.fact_sales (or match expected filtered valid rows). (2) Measure Sum Reconciliation: SELECT SUM(amount) FROM staging.stg_orders must equal SELECT SUM(amount) FROM dw.fact_sales down to the exact cent. Verifying row count alone misses join fan-out bugs or column mapping mismatches.

Problem 1: Multi-Source Surrogate Key Fan-Out Disaster (ETL & SQL)

Scenario: You are loading order data from two regional branches (North and South) into a centralized data warehouse. The staging table staging.stg_orders contains exactly 50,000 transactions totaling $4,500,000. When the ETL query executes:

INSERT INTO dw.fact_sales (date_key, customer_key, product_key, revenue)
SELECT 
    d.date_key,
    c.customer_key,
    p.product_key,
    s.revenue
FROM staging.stg_orders s
JOIN dw.dim_customer c ON s.customer_id = c.customer_id
JOIN dw.dim_product  p ON s.product_id  = p.product_id
JOIN dw.dim_date     d ON s.order_date  = d.calendar_date;

The resulting dw.fact_sales contains 68,400 rows and total revenue of $6,120,000! Furthermore, 1,200 orders from new customers completely vanished from the warehouse.

The Tricky Exam Pitfall
Why did row count expand AND some rows disappear?
  1. Key Collision / Fan-out: Both branches assigned local customer IDs starting from 1 (e.g. North branch had Customer #101, and South branch also had Customer #101). When loaded into dw.dim_customer without the branch prefix, multiple rows exist with customer_id = '101'. The JOIN produces an $M imes N$ Cartesian multiplication (fan-out)!
  2. Inner Join Dropping Orphans: INNER JOIN silently discarded 1,200 orders because their customer IDs were not yet present in dim_customer.
Full Model Solution & Fix

Step 1: Diagnostic Queries

-- Detect duplicate business keys causing fan-out
SELECT customer_id, COUNT(*) 
FROM dw.dim_customer 
GROUP BY customer_id 
HAVING COUNT(*) > 1;

-- Detect orphan orders missing in dimension
SELECT COUNT(*) 
FROM staging.stg_orders s
LEFT JOIN dw.dim_customer c ON s.customer_id = c.customer_id
WHERE c.customer_key IS NULL;

Step 2: Correct DDL and ETL Load Query

-- Fix DimCustomer: compound natural key (branch_id + customer_id)
ALTER TABLE dw.dim_customer ADD COLUMN IF NOT EXISTS branch_id VARCHAR(10);
ALTER TABLE dw.dim_customer DROP CONSTRAINT IF EXISTS uq_cust_bk;
ALTER TABLE dw.dim_customer ADD CONSTRAINT uq_cust_bk UNIQUE (branch_id, customer_id);

-- Insert Unknown Member fallback
INSERT INTO dw.dim_customer (customer_key, branch_id, customer_id, customer_name)
VALUES (-1, 'SYS', 'UNKNOWN', 'Unknown Customer')
ON CONFLICT (customer_key) DO NOTHING;

-- Production ETL: LEFT JOIN with COALESCE to fallback key -1
INSERT INTO dw.fact_sales (date_key, customer_key, product_key, revenue)
SELECT 
    COALESCE(d.date_key, -1) AS date_key,
    COALESCE(c.customer_key, -1) AS customer_key,
    COALESCE(p.product_key, -1) AS product_key,
    s.revenue
FROM staging.stg_orders s
LEFT JOIN dw.dim_customer c 
    ON s.customer_id = c.customer_id AND s.branch_id = c.branch_id
LEFT JOIN dw.dim_product p 
    ON s.product_id = p.product_id
LEFT JOIN dw.dim_date d 
    ON s.order_date = d.calendar_date;

Step 3: Verification Reconciliation

-- Verify row count matches staging exactly (50,000)
SELECT 
    (SELECT COUNT(*) FROM staging.stg_orders) AS stg_rows,
    (SELECT COUNT(*) FROM dw.fact_sales) AS fact_rows;

-- Verify exact revenue match ($4,500,000)
SELECT 
    (SELECT SUM(revenue) FROM staging.stg_orders) AS stg_revenue,
    (SELECT SUM(revenue) FROM dw.fact_sales) AS fact_revenue;

Problem 2: OLAP CUBE Bitmask Decoding & Clean Subtotal Labeling

Scenario: You are asked to write a single PostgreSQL query across FactSales, DimChannel, DimCategory, and DimDate that produces all 8 multidimensional cross-tabulations using CUBE(channel_name, category_name, sale_year). However, the raw data contains legitimate NULL values in channel_name for direct over-the-counter walk-in transactions.

The Tricky Exam Pitfall
If you write COALESCE(channel_name, 'All Channels'), walk-in customers with actual NULL channel values will be falsely displayed as "All Channels" subtotal rows! You MUST use the GROUPING() function to differentiate real data NULLs from OLAP subtotal rows.
Full Model Solution
SELECT 
    -- 1. Dynamic label using GROUPING() to avoid clobbering real NULLs
    CASE 
        WHEN GROUPING(ch.channel_name) = 1 THEN '== ALL CHANNELS =='
        WHEN ch.channel_name IS NULL       THEN '[Walk-in / Direct]'
        ELSE ch.channel_name 
    END AS channel_display,

    CASE 
        WHEN GROUPING(cat.category_name) = 1 THEN '== ALL CATEGORIES =='
        ELSE cat.category_name 
    END AS category_display,

    CASE 
        WHEN GROUPING(d.year) = 1 THEN '== ALL YEARS =='
        ELSE d.year::TEXT 
    END AS year_display,

    -- 2. Bitmask Level ID: 4*G(ch) + 2*G(cat) + 1*G(year)
    (GROUPING(ch.channel_name) * 4 + 
     GROUPING(cat.category_name) * 2 + 
     GROUPING(d.year) * 1) AS grouping_bitmask,

    -- 3. Human readable aggregation tier description
    CASE (GROUPING(ch.channel_name)*4 + GROUPING(cat.category_name)*2 + GROUPING(d.year)*1)
        WHEN 0 THEN 'Detailed: Channel x Category x Year'
        WHEN 1 THEN 'Subtotal: Channel x Category'
        WHEN 2 THEN 'Subtotal: Channel x Year'
        WHEN 3 THEN 'Subtotal: Channel Only'
        WHEN 4 THEN 'Subtotal: Category x Year'
        WHEN 5 THEN 'Subtotal: Category Only'
        WHEN 6 THEN 'Subtotal: Year Only'
        WHEN 7 THEN 'GRAND TOTAL: All Sales'
    END AS aggregation_level,

    COUNT(*) AS transaction_count,
    SUM(f.revenue) AS total_revenue
FROM dw.fact_sales f
LEFT JOIN dw.dim_channel  ch  ON f.channel_key = ch.channel_key
LEFT JOIN dw.dim_category cat ON f.category_key = cat.category_key
LEFT JOIN dw.dim_date     d   ON f.date_key = d.date_key
GROUP BY CUBE(ch.channel_name, cat.category_name, d.year)
ORDER BY grouping_bitmask ASC, total_revenue DESC;

Problem 3: Semi-Additive Inventory Balances & Month-End Reporting

Scenario: A retail chain tracks daily warehouse inventory in fact_daily_inventory. The table stores (date_key, store_key, product_key, on_hand_qty, unit_cost). A junior developer writes the following query to report monthly inventory value per store:

-- BROKEN QUERY
SELECT 
    d.year, d.month, f.store_key,
    SUM(f.on_hand_qty) AS total_units,
    SUM(f.unit_cost) AS total_cost
FROM dw.fact_daily_inventory f
JOIN dw.dim_date d ON f.date_key = d.date_key
GROUP BY d.year, d.month, f.store_key;
The Tricky Exam Pitfall
  1. on_hand_qty is a semi-additive measure. Summing 30 daily balances calculates 30 times the inventory actually present in the warehouse! You must report the balance from the last recorded calendar day of each month.
  2. unit_cost is non-additive. Summing prices makes no financial sense. Total inventory value must be computed row-by-row as on_hand_qty * unit_cost.
  3. Some stores close on Sundays or public holidays, so the last day with an inventory record may be the 29th or 30th rather than the 31st.
Full Model Solution
WITH ranked_daily_snapshots AS (
    SELECT 
        d.year,
        d.month,
        f.store_key,
        f.product_key,
        f.on_hand_qty,
        f.unit_cost,
        (f.on_hand_qty * f.unit_cost) AS inventory_valuation,
        -- Rank dates descending within each store, product, and month
        ROW_NUMBER() OVER (
            PARTITION BY d.year, d.month, f.store_key, f.product_key
            ORDER BY d.calendar_date DESC
        ) AS rank_in_month
    FROM dw.fact_daily_inventory f
    JOIN dw.dim_date d ON f.date_key = d.date_key
)
SELECT 
    year,
    month,
    s.store_name,
    COUNT(DISTINCT product_key) AS distinct_products_stocked,
    SUM(on_hand_qty) AS month_end_units_on_hand,
    SUM(inventory_valuation) AS total_month_end_inventory_value
FROM ranked_daily_snapshots r
JOIN dw.dim_store s ON r.store_key = s.store_key
WHERE rank_in_month = 1 -- Strictly take the latest recorded day of the month
GROUP BY year, month, s.store_name
ORDER BY year, month, total_month_end_inventory_value DESC;

Problem 4: Sparse Time-Series & Window Framing: ROWS vs RANGE

Scenario: You are tasked with calculating a 3-Month Rolling Average Revenue for every product category across 2024. Certain niche product categories have zero sales in some months (no rows exist in the sales table for those months).

The Tricky Exam Pitfall
If you write AVG(rev) OVER (PARTITION BY cat ORDER BY month_id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), the window counts 3 physical records. If Category 'Winter Gear' had sales in January, February, and November (9 months gap), the average for November will incorrectly use January and February!
Full Model Solution (Dense Calendar Spine)
-- Step 1: Generate a continuous monthly calendar spine crossed with all categories
WITH all_months AS (
    SELECT GENERATE_SERIES('2024-01-01'::DATE, '2024-12-01'::DATE, '1 month'::INTERVAL)::DATE AS month_start
),
all_categories AS (
    SELECT category_key, category_name FROM dw.dim_category
),
month_category_spine AS (
    SELECT m.month_start, c.category_key, c.category_name
    FROM all_months m
    CROSS JOIN all_categories c
),
-- Step 2: Aggregate actual sales per month per category
actual_monthly_sales AS (
    SELECT 
        d.month_start_date AS month_start,
        f.category_key,
        SUM(f.revenue) AS monthly_revenue
    FROM dw.fact_sales f
    JOIN dw.dim_date d ON f.date_key = d.date_key
    WHERE d.year = 2024
    GROUP BY d.month_start_date, f.category_key
),
-- Step 3: Combine spine with actual sales, imputing missing months with 0.00
dense_monthly_data AS (
    SELECT 
        s.month_start,
        s.category_key,
        s.category_name,
        COALESCE(a.monthly_revenue, 0.00) AS clean_revenue
    FROM month_category_spine s
    LEFT JOIN actual_monthly_sales a 
        ON s.month_start = a.month_start AND s.category_key = a.category_key
)
-- Step 4: Window rolling average across true consecutive calendar months
SELECT 
    month_start,
    category_name,
    clean_revenue,
    ROUND(
        AVG(clean_revenue) OVER (
            PARTITION BY category_key 
            ORDER BY month_start 
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        ), 2
    ) AS rolling_3_month_avg_revenue,
    DENSE_RANK() OVER (
        PARTITION BY month_start 
        ORDER BY clean_revenue DESC
    ) AS monthly_category_rank
FROM dense_monthly_data
ORDER BY category_name, month_start;

Problem 5: 3NF Operational Schema Transformation to Kimball Star Schema

Scenario: You are given an operational database in 3NF containing 6 tables: orders (order_id, order_num, order_date, customer_id, order_status), order_items (line_id, order_id, product_id, qty, unit_price, discount), customers (customer_id, name, city_id), cities (city_id, city_name, state_id), states (state_id, state_name, country), and products (product_id, name, category_id).

Design a production-ready Kimball Star Schema in PostgreSQL. Where do order_num and order_status go?

Kimball Design Insight: Degenerate Dimensions
order_num and order_status are Degenerate Dimensions. They do not belong in a separate dimension table because they have no attributes other than themselves. Instead, store them directly in the fact table. This allows grouping line items back to their original invoice without an unnecessary dimension JOIN!
Full Model Solution (PostgreSQL DDL & Load)
-- Dimension 1: Conformed Customer (Denormalized with City & State)
CREATE TABLE dw.dim_customer (
    customer_key BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  VARCHAR(50) NOT NULL UNIQUE,
    customer_name VARCHAR(150) NOT NULL,
    city_name    VARCHAR(100),
    state_name   VARCHAR(100),
    country      VARCHAR(50)
);

-- Dimension 2: Product
CREATE TABLE dw.dim_product (
    product_key  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id   VARCHAR(50) NOT NULL UNIQUE,
    product_name VARCHAR(150) NOT NULL,
    category_name VARCHAR(100)
);

-- Fact Table: Grain = One individual line item per order
CREATE TABLE dw.fact_sales_order_item (
    sales_item_key  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    -- Foreign Keys to Dimensions
    date_key        INTEGER NOT NULL REFERENCES dw.dim_date(date_key),
    customer_key    BIGINT  NOT NULL REFERENCES dw.dim_customer(customer_key),
    product_key     BIGINT  NOT NULL REFERENCES dw.dim_product(product_key),
    -- Degenerate Dimensions (stored directly in fact)
    order_num       VARCHAR(50) NOT NULL,
    order_status    VARCHAR(30) NOT NULL,
    -- Additive Measures
    quantity        INTEGER NOT NULL,
    unit_price      NUMERIC(12,2) NOT NULL,
    discount_amount NUMERIC(12,2) NOT NULL,
    extended_sales_amount NUMERIC(12,2) NOT NULL -- (qty * unit_price) - discount
);

-- ETL Transformation Query
INSERT INTO dw.fact_sales_order_item (
    date_key, customer_key, product_key, order_num, order_status,
    quantity, unit_price, discount_amount, extended_sales_amount
)
SELECT 
    TO_CHAR(o.order_date, 'YYYYMMDD')::INTEGER,
    c.customer_key,
    p.product_key,
    o.order_num,
    o.order_status,
    oi.qty,
    oi.unit_price,
    oi.discount,
    (oi.qty * oi.unit_price) - oi.discount
FROM operational.order_items oi
JOIN operational.orders o ON oi.order_id = o.order_id
JOIN dw.dim_customer c ON o.customer_id = c.customer_id
JOIN dw.dim_product p ON oi.product_id = p.product_id;

Problem 6: Power BI DAX Context Transition & Parent Category Ratios

Scenario: In Power BI, an analyst creates a matrix visual displaying Division, Category, and Total Sales. They want to calculate Percentage of Parent Division Sales (i.e. each category's share of its parent division, summing to 100% within each division). Their first attempt:

-- BROKEN DAX
% of Division Sales = 
DIVIDE(
    [Total Sales], 
    CALCULATE([Total Sales], ALL(DimProduct[Category]))
)

This works until the user adds a slicer on DimProduct[Brand], after which the parent total becomes incorrect. Why?

DAX Context Transition Mechanics
ALL(DimProduct[Category]) only removes the filter on the Category column, leaving all other columns (such as Brand or Subcategory) active. To reliably compute a percentage of the parent division, you must remove filters on everything inside the division while preserving the filter on Division.
Full Model Solution (Robust DAX Measure)
-- 1. Base Measure
Total Sales = SUM(FactSales[ExtendedSalesAmount])

-- 2. Division Level Denominator
Division Sales = 
CALCULATE(
    [Total Sales],
    ALLEXCEPT(DimProduct, DimProduct[Division])
)

-- 3. Robust Percentage Share with Zero Protection
Category % of Division = 
DIVIDE(
    [Total Sales],
    [Division Sales],
    0 -- Fallback if denominator is 0
)

-- 4. Dynamic Percentage of Selected Total (Respecting all external visual filters)
Category % of Selected = 
DIVIDE(
    [Total Sales],
    CALCULATE([Total Sales], ALLSELECTED(DimProduct[Category])),
    0
)

Problem 7: Auditing Non-Events with Factless Fact Tables (Attendance)

Scenario: FAST-NU administers midterm lab exams. The academic audit committee needs to know:

  1. How many registered students actually attended each exam session?
  2. Which specific students registered for an exam but failed to show up (absentee list)?

Explain why a standard transactional sales-style fact table cannot record this, and provide the Star Schema DDL and SQL query.

Why Factless Fact Tables Are Required
Standard transaction fact tables record events that occurred (e.g. attendance scanned). They do not generate records for things that did not happen. To track absentees, you need two tables:
  1. Coverage Fact Table (Eligibility/Registration): A factless table defining who was scheduled to attend.
  2. Event Fact Table (Attendance): A factless table recording who actually showed up.
Full Model Solution (PostgreSQL Schema & Anti-Join)
-- 1. Factless Fact: Exam Registration (Coverage Matrix)
CREATE TABLE dw.fact_exam_registration (
    student_key BIGINT REFERENCES dw.dim_student(student_key),
    course_key  BIGINT REFERENCES dw.dim_course(course_key),
    exam_key    BIGINT REFERENCES dw.dim_exam(exam_key),
    PRIMARY KEY (student_key, course_key, exam_key)
);

-- 2. Factless Fact: Exam Attendance (Actual Events)
CREATE TABLE dw.fact_exam_attendance (
    student_key     BIGINT REFERENCES dw.dim_student(student_key),
    exam_key        BIGINT REFERENCES dw.dim_exam(exam_key),
    check_in_time   TIMESTAMP NOT NULL,
    lab_station_id  VARCHAR(20),
    PRIMARY KEY (student_key, exam_key)
);

-- 3. Audit Query: Find Absentees (Registered but Zero Attendance)
SELECT 
    s.roll_number,
    s.student_name,
    c.course_code,
    e.exam_title,
    e.exam_date
FROM dw.fact_exam_registration reg
JOIN dw.dim_student s ON reg.student_key = s.student_key
JOIN dw.dim_course  c ON reg.course_key  = c.course_key
JOIN dw.dim_exam    e ON reg.exam_key    = e.exam_key
-- Anti-Join: Check if attendance record is missing
LEFT JOIN dw.fact_exam_attendance att 
    ON reg.student_key = att.student_key AND reg.exam_key = att.exam_key
WHERE att.student_key IS NULL -- No attendance scan found
ORDER BY c.course_code, s.roll_number;

Problem 8: Slowly Changing Dimensions (SCD Type 1 vs Type 2) Historical Corruption

Scenario: Customer Ali lived in Lahore during 2024 and purchased $100,000 worth of equipment. On January 1, 2025, Ali moved to Karachi and purchased $15,000 worth of goods.

The company data warehouse implemented SCD Type 1 (overwrite in place). When the Regional Vice President runs the annual review for 2024 regional sales, what will the report show, and why is this a critical audit failure?

The SCD Type 1 Historical Corruption Trap
In SCD Type 1, updating Ali's city from Lahore to Karachi overwrites the existing row. Because the 2024 fact rows point to Ali's surrogate key, joining to dim_customer will retroactively attribute all $100,000 of 2024 sales to Karachi! Lahore loses $100,000 and Karachi falsely gains $100,000. Historical financial truth is destroyed.
Full Model Solution (SCD Type 2 Point-in-Time Join)
-- SCD Type 2 Table Structure
CREATE TABLE dw.dim_customer_scd2 (
    customer_key    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id     VARCHAR(50) NOT NULL, -- Business Key
    customer_name   VARCHAR(150),
    city            VARCHAR(100),
    effective_date  DATE NOT NULL,
    expiry_date     DATE NOT NULL, -- '9999-12-31' if current
    is_current      BOOLEAN NOT NULL
);

-- Ali's Historical Records in DimCustomer:
-- Row 1: key=101, id='C01', city='Lahore',  effective='2024-01-01', expiry='2024-12-31', is_current=FALSE
-- Row 2: key=205, id='C01', city='Karachi', effective='2025-01-01', expiry='9999-12-31', is_current=TRUE

-- Point-in-Time ETL Fact Loading Query:
INSERT INTO dw.fact_sales (date_key, customer_key, revenue)
SELECT 
    d.date_key,
    c.customer_key, -- Resolves to 101 for 2024 orders, and 205 for 2025 orders!
    stg.revenue
FROM staging.stg_orders stg
JOIN dw.dim_date d ON stg.order_date = d.calendar_date
JOIN dw.dim_customer_scd2 c 
    ON stg.customer_id = c.customer_id
   AND stg.order_date >= c.effective_date 
   AND stg.order_date <= c.expiry_date;

Top 5 Golden Rules for Acing the DW&BI Lab Midterm

  • Always Qualify Natural Keys: Combine natural keys with branch/system IDs to prevent duplicate fan-out in fact table joins.
  • Verify Grain First: State the physical grain in plain English before drafting any DDL or choosing foreign keys.
  • Watch Window Frames: Never use ROWS BETWEEN for calendar time-series without a continuous date spine.
  • Protect Against Divide-by-Zero: In DAX, always wrap division in DIVIDE(num, denom, 0) rather than using bare forward slashes /.
  • Differentiate Real NULLs from OLAP Subtotals: Use GROUPING() inside CASE statements when performing CUBE or ROLLUP.
Extra High-Difficulty Practice Questions
Question 1: Why does a fact table with an accumulating snapshot grain require frequent UPDATE operations, violating the "append-only" warehouse rule?

Answer: An Accumulating Snapshot Fact Table models a predictable pipeline or lifecycle with distinct milestones (e.g., Order Placed → Payment Received → Item Picked → Shipped → Delivered). Each milestone corresponds to a separate date foreign key in the same row. As the order advances through its lifecycle over days or weeks, the same fact row must be updated to populate newly achieved milestone dates and durations. This is the only legitimate exception to the append-only rule in dimensional warehouses.

Question 2: What is a conformed dimension, and why is it required when drilling across multiple fact tables?

Answer: A conformed dimension is a single dimension table (or consistent subset) that means the exact same thing across multiple disparate business processes (e.g. DimCustomer or DimDate shared between FactSales and FactSupportTickets). It enables "drill-across" queries where results from two separate star schemas are combined and compared along the conformed dimension attributes (e.g., comparing sales revenue vs support ticket volume per customer).

Question 3: If an ETL load inserts fact rows with surrogate key -1, how does a BI dashboard report these transactions?

Answer: Because the dimension table contains a designated record with surrogate key -1, business key 'UNKNOWN', and descriptive attributes like '[Unassigned / Missing Data]', the BI visual displays these transactions grouped under '[Unassigned / Missing Data]' instead of dropping them or throwing database foreign key constraint errors. This preserves financial revenue totals while alerting data quality engineers to investigate the source data.
