    Module 1 — Introduction to Data Warehousing

    1What is a Data Warehouse?

    The big picture — what DW is, why it exists, and how it differs from operational systems

    Imagine your company has dozens of separate databases — one for sales, one for HR, one for inventory, one for payroll. Each speaks a different language, uses a different format, and lives on different hardware. A Data Warehouse (DW) is the solution: it pulls all that scattered data together, cleans it up, and makes it available for strategic decision-making. Think of it as the “one source of truth” for the whole organisation.

    Definition
    Data Warehouse: A complete repository of corporate data extracted from transaction systems that is available for ad-hoc access by “knowledge workers.” It is an information environment that provides an integrated, consistent, and historical view of enterprise data optimised for decision-support queries — without hindering day-to-day operational systems.

    Key Characteristics

    • Provides an integrated and total view of the enterprise
    • Makes current and historical data easily available for decision-making
    • Enables decision-support transactions without hindering operational systems
    • Renders the organisation’s information consistent
    • Presents a flexible, interactive source of strategic information

    DW is an Environment, Not a Product

    A DW is not a piece of software you buy off the shelf. It is a computing environment — an assemblage of hardware, software, people, and processes built around the needs of the decision-maker. It blends: data acquisition, data modelling, data cleaning, metadata management, storage management, and application tools.

    Operational Systems vs Data Warehouse

    Dimension Operational (OLTP) Data Warehouse (DSS)
    Purpose Run the business (“making the wheels turn”) Analyse the business (“watching the wheels turn”)
    Data Content Current values Archived, derived, summarised
    Data Structure Optimised for transactions Optimised for complex queries
    Access Frequency High (many small reads/writes) Lower (few, complex reads)
    Updates Continuous, real-time Periodic / batch
    Schema 3NF (normalised) Star/snowflake (denormalised)
    Users Clerks, front-line staff Analysts, executives, knowledge workers
    Pro Tip
    Exam anchor: Remember the one-liners from the slides — “Operational systems run the business; DW gives insight into how to improve the business.” Examiners love these contrasts.
    Common Mistake
    DW ≠ a product, ≠ just a big database. Students often describe it as “a large relational database.” It is specifically an environment designed for decision-support, with its own schema styles (star/snowflake), ETL processes, and metadata layer.
    Why was the data warehouse concept born? What problem does it solve?

    Organisations suffer from “data glut, knowledge scarcity” — they are drowning in data spread across siloed operational systems, yet executives cannot easily extract strategic insights. Earlier solutions (ad-hoc reports, EIS) all failed because they could not scale or stay consistent. DW was designed as a decision-support environment that consolidates, cleans, and makes all that data consistently accessible without disrupting daily operations.

    What does “7x24 availability” mean in a DW context, and why does it matter?

    Initially DW systems often start with a 6x12 (6 days, 12 hours) availability requirement, but they quickly evolve toward a 7x24 (always-on) goal as business users demand round-the-clock analytics access. This raises significant infrastructure challenges around batch update windows, hardware redundancy, and maintenance scheduling.

    Hard: What are the tradeoffs of using a denormalised star schema instead of 3NF in a DW?

    Pros: Dramatically faster analytical queries — fewer joins, simpler query plans, better use of columnar storage or bitmap indexes. Cons: Data redundancy (storage cost), more complex ETL to maintain consistency, and updates are harder (though DW data is mostly read-only). The tradeoff is almost always worth it in a DW because query performance is king, and writes happen in batch.

    Key Takeaways

    • A DW is an environment for strategic information — not a single product
    • It consolidates data from many sources into one integrated, consistent view
    • Operational systems (OLTP) run the business; DW (DSS) analyses and improves it
    • DW uses denormalised schemas (star/snowflake) optimised for complex queries
    • DW runs separately from operational systems and is refreshed via periodic batch loads

    2Source Data Types

    Where the data comes from — production, internal, archived, and external sources

    Before data lands in a warehouse it must come from somewhere. The DW draws from four broad categories of source data. Each brings its own characteristics and challenges. Understanding these is the first step in designing a realistic ETL strategy.

    Definition
    Source Data: The raw input to the data warehouse pipeline — all data that will be extracted, transformed, and loaded into the warehouse. Sources can be internal or external, and can be current or historical.

    1 — Production Data

    Data generated by the organisation’s operational (OLTP) systems — ERP, CRM, POS, banking transaction systems. This is typically the richest and most important source.

    Common Mistake
    Major Issue: Disparity. Production systems across an enterprise almost never speak the same language. Different DBMS vendors (Oracle, SQL Server, MySQL), different data formats (CSV, XML, proprietary binary), different hardware/OS platforms, and different field naming conventions (“CUST_ID” vs “CustomerNo”). Integrating all of this is one of the hardest problems in DW design.

    2 — Internal Data

    Data from “private” sources within the organisation that are not part of formal operational systems: spreadsheets, local Access databases, Word documents with embedded tables, scanned records.

    Pro Tip
    Major Issues: (a) Selecting what internal data is worth including — not all of it is relevant or reliable; (b) Deciding whether to incorporate it at all, since informal data may have quality and consistency problems requiring significant cleansing effort.

    3 — Archived Data

    Historical backup data from operational systems — old transaction records, year-end snapshots, legacy system exports. This is your only window into the organisation’s past before the DW existed.

    Pro Tip
    Major Issue: How much archived data to include. The further back you go, the older and potentially less compatible the formats (magnetic tape archives from the 1990s). Restoring and converting old formats is expensive; balance historical depth against cost and feasibility.

    4 — External Data

    Data purchased or obtained from third-party vendors, agencies, or public sources: Nielsen market research, census demographics, weather feeds, competitor benchmarks, economic indicators.

    Pro Tip
    Major Issues: (a) Selecting relevant external datasets; (b) Integrating external data with internal data — reconciling different keys, geographies, time granularities, and naming conventions.

    Side-by-Side Comparison

    Source Type Origin Key Challenge Example
    Production Operational systems (OLTP) Disparity — different formats, platforms, interfaces SAP ERP, POS system, banking core
    Internal Private org. sources Selection + quality — informal, inconsistent Excel reports, Access DBs, shared drives
    Archived Operational system backups Deciding how far back to go; format obsolescence Year-end tapes, legacy system exports
    External Third-party vendors / public Relevance selection + integration Nielsen, census data, market benchmarks
    Example

    Real-world source data challenge at a retail chain

    Production : POS transaction DB (Oracle), CRM (Salesforce), Inventory (SAP)
Internal   : Regional manager spreadsheets with hand-keyed promotions data
Archived   : 5 years of old POS data on magnetic tape (legacy DB2 format)
External   : Nielsen household spending reports, local weather API for seasonal analysis

ETL must handle: converting DB2 tape archives, cleaning manager spreadsheets
(typos, inconsistent date formats), reconciling Oracle/SAP customer IDs,
and mapping Nielsen geographic codes to internal store codes.
    Why is production data described as having a “disparity” problem?

    Even within a single company, operational systems are built over decades using different technologies from different vendors. The result: different DBMS engines, hardware, network interfaces, data formats, and field naming conventions — all describing the same business entities in incompatible ways. The DW must reconcile all these disparities during extraction and transformation.

    What decision must be made about archived data, and what factors influence it?

    The key decision is how much historical data to include. Factors: (1) Business need — how far back do analysts need to go for trend analysis? (2) Format feasibility — can old backup formats even be read today? (3) Cost — restoring and converting old archives is expensive. (4) Data quality — older data may have more errors. A pragmatic decision is 3–5 years unless there is a specific business requirement for more.

    Hard: If external data uses different geographic codes than your internal data, how would you resolve this in the ETL pipeline?

    Classic surrogate key / lookup table problem. Steps: (1) Create a mapping table translating external codes (e.g., Nielsen DMA codes) to internal codes (e.g., store region IDs). (2) During transformation, join the external data to this mapping table. (3) For unmapped codes, handle with a default “Unknown” dimension member or flag for manual review. (4) Keep the mapping table versioned, since external agencies sometimes change their coding schemes.

    Key Takeaways

    • Four source types: production (OLTP), internal (private), archived (historical backup), external (third-party)
    • Production data’s main challenge is disparity — multiple formats, platforms, interfaces
    • Internal data requires careful selection — not all informal data is worth incorporating
    • Archived data raises the “how far back?” question — balance history vs. feasibility and cost
    • External data must be selected for relevance and then carefully integrated with internal keys

    3Target System Qualities

    What the data warehouse must deliver — the five characteristics of good strategic information

    Building a DW is pointless if the output — the strategic information — is poor quality. The slides identify five key characteristics that the target DW system must satisfy to be useful. Think of these as the quality criteria your DW must meet.

    Definition
    Strategic Information: Information extracted or discovered from large quantities of data that helps executives and knowledge workers make decisions about the organisation’s direction and growth. It is the output of the data warehousing process and must meet specific quality standards to be trustworthy.

    The 5 Qualities of Strategic Information

    Quality What it means DW Design Implication
    Integrated Data from all sources is reconciled into a single, unified view ETL pipeline must resolve naming conflicts, unit inconsistencies, and key mismatches
    Data Integrity Data is accurate, complete, and consistent — faithfully represents the real world Data cleansing, validation rules, referential integrity checks during staging
    Credible Users trust the data and rely on it for decisions Data lineage tracking, audit logs, transparent transformation rules
    Accessible Authorised users can get to the data they need without technical barriers OLAP tools, self-service BI frontends, proper indexing, role-based access control
    Timely Data is up-to-date enough for the decisions being made Appropriate ETL scheduling — daily, weekly, or near-real-time as needed
    Pro Tip
    Credibility is the hardest to build and easiest to destroy. If analysts discover that the DW contradicts operational system numbers even once, they stop trusting it. Consistent, auditable, and well-documented transformations are essential. Document everything.
    Common Mistake
    Timely ≠ real-time. Many students assume a DW needs to be constantly updated. In practice, most DWs are refreshed in batch — nightly, weekly, or monthly — because real-time updates are expensive and most strategic decisions do not require second-by-second data.

    Source System vs Target System

    The source system is the extraction side — pulling data from operational sources with all their disparity issues. The target system is the DW itself — the environment that must satisfy the five qualities above. The staging area bridges the gap through transformation.

    Example

    Integrity vs Credibility — Spot the Difference

    Scenario A: DW correctly stores that Customer X made 50 purchases last year.
            The operational system also says 50. --> HIGH integrity.

Scenario B: An analyst believes the DW says 42, not 50, due to a past known bug.
            She goes to the operational system instead. --> LOW credibility.

Lesson: Integrity = correctness. Credibility = user trust.
        You can have high integrity but low credibility (after a past mistake).
        You cannot sustainably have high credibility without high integrity.
    A DW reports 10,000 active customers. The CRM says 12,000. Why might this happen and which is correct?

    Classic data integration / definition problem. Possible causes: (1) Different definitions of “active” — DW uses “purchased in last 12 months,” CRM uses “account not closed.” (2) ETL applied a filter the business is not aware of. (3) CRM includes duplicates. (4) ETL load is stale. Resolution requires checking data lineage and transformation rules. This is exactly why documented ETL rules and data dictionaries are essential for credibility.

    Why do organisations suffer from “data glut but knowledge scarcity”?

    Organisations accumulate vast transactional data across siloed operational systems, but this data is not accessible for strategic analysis — scattered across systems with different formats, inconsistent definitions, and no unified view. Knowledge workers drown in raw data but struggle to find meaningful, reliable information. DW solves this by integrating, cleaning, and making data accessible through analytical tools.

    Hard: How would you design an ETL pipeline to ensure data integrity when merging customer records from three separate source systems?

    (1) Assign a master customer surrogate key in the DW independent of source system keys. (2) Build an identity resolution module that matches customers across systems using deterministic rules (same email, same name+address) and probabilistic matching for uncertain cases. (3) Implement validation checks at each stage — null checks, referential integrity, range checks. (4) Use an error staging table to quarantine records that fail validation. (5) Log all transformation decisions for audit purposes. (6) Run reconciliation counts before and after load to confirm totals are consistent.

    Key Takeaways

    • Strategic information must be: integrated, accurate (integrity), credible, accessible, and timely
    • Credibility is user trust — once broken, it is hard to rebuild; document all transformations
    • Timely does not mean real-time — most DWs use batch refresh cycles
    • Source system = extraction challenge (disparity); Target system = quality delivery challenge
    • DW architecture must be designed to satisfy all five qualities simultaneously

    4Data Staging & ETL

    The transformation engine — extracting, cleaning, and loading data into the warehouse

    Data staging is the prep kitchen of the data warehouse. Raw ingredients (source data) come in messy and incompatible; they are washed, chopped, and combined into something clean and consistent before being served to the warehouse. The staging area is a separate, intermediate data environment — not part of the source systems, not yet part of the warehouse.

    Definition
    Data Staging: An intermediate area where data is prepared (extracted, transformed, and cleansed) before being loaded into the data warehouse. It acts as a buffer and transformation server between source systems and the DW.
    Definition
    ETL (Extract, Transform, Load): The three-step process at the heart of data staging.

    Extract — Pull data from source systems (production, internal, archived, external).
    Transform — Clean, reformat, reconcile, aggregate, and enrich the data. The most complex and time-consuming step.
    Load — Insert the transformed, clean data into the DW storage.

    Extraction in Detail

    • Full extraction — pull all data every time (simple but expensive)
    • Incremental extraction — pull only records changed since the last load (efficient but needs change-tracking via timestamps or CDC)
    • Log-based extraction — read the source DB transaction log to capture changes (minimal impact on source, complex to implement)

    Transformation in Detail

    The staging area — sometimes called the data transformation server — performs:

    • Data cleansing — fix errors, handle nulls, standardise formats (dates: “01/05/2024” vs “2024-05-01” vs “1 May 2024”)
    • Data integration — reconcile records from different sources
    • Data aggregation — roll up daily sales to monthly totals
    • Surrogate key generation — assign warehouse-specific keys independent of source keys
    • Business rule application — derived calculations (profit = revenue − cost)
    • Denormalisation — reshape 3NF source data into star/snowflake schema

    Loading in Detail

    After transformation, data is loaded into the warehouse as either a full refresh (replace everything) or an incremental (delta) load (append/update only changed records). Most production DWs use incremental loads to keep load windows manageable.

    Pro Tip
    The staging area must be separate from both source and DW. Never load directly from source to DW. The staging area lets you fail safely, re-run transformations, audit intermediate results, and isolate the DW from source availability issues.
    Example

    A simple ETL pipeline in pseudocode

    -- EXTRACT
SELECT customer_id, cust_name, email, purchase_date, amount
FROM src_crm.transactions
WHERE updated_at > @last_load_timestamp;

-- TRANSFORM (in staging)
UPDATE stg.transactions SET
  cust_name     = TRIM(UPPER(cust_name)),      -- standardise case
  email         = LOWER(email),                -- standardise format
  purchase_date = CAST(purchase_date AS DATE), -- fix data type
  amount        = ROUND(amount, 2)             -- normalise precision
WHERE cust_name IS NOT NULL AND amount > 0;   -- reject nulls / invalid

-- LOAD
INSERT INTO dw.fact_sales (surr_key, customer_sk, date_sk, amount)
SELECT NEXT_VAL(surr_seq), d_cust.sk, d_date.sk, stg.amount
FROM stg.transactions stg
JOIN dw.dim_customer d_cust ON stg.customer_id = d_cust.source_id
JOIN dw.dim_date     d_date ON stg.purchase_date = d_date.full_date;
    Common Mistake
    Underestimating transformation complexity. In practice, transformation accounts for 60–80% of total ETL development effort. “Just move the data” quickly turns into hundreds of business rules to handle edge cases in real, messy source data.
    What is the difference between full extraction and incremental extraction?

    Full extraction pulls all data from the source every time. Simple but very expensive for large datasets. Incremental extraction pulls only records changed since the last extraction (using timestamps, version numbers, or CDC). Much more efficient but requires the source system to reliably support change tracking.

    Why must the staging area be separate from both the source systems and the DW?

    (1) Isolation — heavy transformation operations do not impact source system performance. (2) Failure recovery — if a transformation step fails, you can rerun from staging data without re-extracting from source. (3) Auditability — staging lets you inspect intermediate data to diagnose data quality issues. (4) Decoupling — the DW does not need to be down while staging is running.

    Hard: Your ETL pipeline takes 14 hours to run but your load window is 8 hours. What strategies could reduce ETL runtime?

    Parallelism: Extract from multiple sources simultaneously. Incremental loads: Switch from full to delta extraction to reduce data volume. Pushdown transformation: Perform transformations in the source or target DBMS using native SQL (databases are faster at set-based operations). Partitioning: Partition large staging tables and process partitions in parallel. Indexing strategy: Drop indexes before bulk load, rebuild after. Hardware scaling: Move ETL to a more powerful server or cloud-based distributed compute (e.g., Spark). Cache lookup tables: Load frequently-joined reference data into memory to avoid repeated DB hits.

    Key Takeaways

    • Staging = the intermediate transformation area — a buffer and transformation server
    • ETL = Extract → Transform (clean, reconcile, restructure) → Load into DW
    • Transformation is the most complex step: cleansing, integration, aggregation, surrogate keys, business rules
    • Staging must be separate from both source and DW to enable isolation, recovery, and auditing
    • Incremental (delta) loads are preferred over full loads for performance in production DWs

    5DW Building Blocks & Components

    The architecture of a complete data warehouse — five key components and how they fit together

    A data warehouse is not one thing — it is five interconnected components working in concert. Understanding the building blocks of DW architecture is fundamental, since everything else (ETL design, query optimisation, governance) hangs off this structure.

    Definition
    DW Building Blocks: The five key architectural components of a data warehouse environment: (1) Data Source, (2) Data Staging, (3) Data Storage, (4) Information and Delivery, (5) Management and Control.
    # Component Role Key Technologies
    1 Data Source All input data — production, internal, archived, external OLTP DBs, flat files, APIs, external feeds
    2 Data Staging ETL — extract, transform, load data Informatica, SSIS, Talend, custom scripts
    3 Data Storage Separate repository with its own DBMS, hardware, admin tools RDBMS or MDDBMS, columnar DBs
    4 Information & Delivery Tools to access, query, and present DW data to end users OLAP cubes, Power BI, Tableau, ad-hoc query tools
    5 Management & Control Orchestrates all other components — ETL scheduling, user access, batch updates, metadata interaction Airflow, access management, monitoring tools

    Data Storage in Detail

    The data storage layer is a completely separate repository from source systems. It has its own:

    • DBMS — either RDBMS (relational/SQL) or MDDBMS (multi-dimensional OLAP cubes)
    • Hardware and Software — optimised for large, complex read-heavy queries
    • Administration Tools — backup/recovery, performance monitoring, index management

    Metadata — The Hidden Component

    Metadata is data about data in the DW — similar to the data dictionary and data catalog in a DBMS. It describes: where data came from (lineage), how it was transformed, what each field means (business definitions), when data was last refreshed, and who has access to what.

    Pro Tip
    Management and Control interacts with Metadata. The orchestration layer uses metadata to know what to run, when, and for whom. Without good metadata, the DW is a black box — nobody knows where the numbers come from or whether to trust them.
    Example

    Architecture Flow (from slides)

    Operational Data  (IT Users)
       |
       v  [Data Transformation / ETL]
Enterprise Warehouse + Integrated Data Marts
       |
       v  [Replication]
Dependent Data Marts / Departmental Warehouses
       |
       v  [BI Tools / Delivery]
Business Users
    What is the difference between RDBMS and MDDBMS in a DW context?

    An RDBMS stores data in tables and uses SQL. In a DW this means star/snowflake schema with fact and dimension tables. An MDDBMS stores data in pre-aggregated cubes organised by dimensions (Time x Product x Region), enabling very fast OLAP operations. RDBMS offers more flexibility; MDDBMS offers faster pre-built analytics. Modern cloud DWs (BigQuery, Snowflake, Redshift) are relational with columnar storage that gives many MDDBMS-like performance benefits.

    Why does Management and Control need to interact with Metadata?

    Management and Control orchestrates ETL jobs, information delivery, user access, and batch updates. To do this intelligently, it needs metadata: which ETL jobs depend on which sources? What is the refresh schedule? Which users have permission to query what? What was the last successful load time? Without metadata, the orchestration layer must hardcode all of this, making the system brittle and opaque.

    Hard: How would you ensure the Management and Control component handles an ETL failure gracefully without corrupting the warehouse?

    Key patterns: (1) Transactional loading — wrap each load step in a transaction; rollback on failure, preserving the last good state. (2) Checkpointing — record the last successfully completed ETL step in metadata; restart from checkpoint on failure. (3) Error tables — route bad records to a separate error staging table rather than failing the whole pipeline. (4) Alerting — send failure notifications immediately. (5) Idempotent loads — design load operations so re-running produces the same result with no duplicates. (6) Load audit table — record every load attempt (start, end, records processed, status).

    Key Takeaways

    • Five components: Data Source → Staging (ETL) → Storage → Information Delivery → Management & Control
    • Data Storage is a completely separate repository with its own DBMS, hardware, and admin tools
    • Metadata (data about data) is the connective tissue enabling lineage, governance, and orchestration
    • Management & Control oversees ETL, delivery, access, and batch updates — interacts with metadata
    • Information Delivery tools (OLAP, BI dashboards) are how end users consume the DW

    6Data Warehouse vs Data Marts

    Enterprise-wide vs departmental — the DW/DM relationship and the top-down vs bottom-up debate

    Once you understand what a DW is, the next question is: build one big warehouse, or a set of smaller, departmental data marts? This is one of the most debated design decisions in DW architecture.

    Definition
    Data Mart: A focused subset of the data warehouse scoped to a specific business function, department, or subject area (e.g., Sales DM, HR DM, Finance DM). It contains a subset of the enterprise data relevant to that department’s needs.
    Definition
    Dependent Data Mart: Populated from the central enterprise data warehouse — a logical subset of the overall DW, not a standalone system. This is the preferred architecture (Kimball’s approach).

    Independent Data Mart: Built directly from source systems without going through a central DW. Fast to build initially but creates “information silos” and consistency problems.

    Top-Down vs Bottom-Up Approach

    Aspect Top-Down (Inmon) Bottom-Up (Kimball)
    Start with Enterprise-wide DW first, then derive marts Build data marts one at a time, conforming to a shared architecture
    Time to first value Long — enterprise DW takes years Short — first mart can deliver value in months
    Risk High upfront investment before any ROI Lower risk, iterative delivery
    Consistency High — single source of truth from day one Depends on how well marts are “conformed”
    Data Mart type Dependent (derived from central DW) Dependent (logical subsets, not independent)

    Kimball’s Practical Approach

    The slides highlight Kimball’s practical approach as the recommended middle path:

    1. Plan and define requirements at the overall corporate level
    2. Create the architecture for a complete enterprise warehouse
    3. Conform and standardise the data content (shared dimension definitions)
    4. Implement one data mart at a time — delivering business value incrementally

    In this approach each data mart is a logical subset of the overall DW — they are all dependent data marts drawing from the central enterprise warehouse. This gives Kimball’s speed-to-value with Inmon’s consistency.

    Pro Tip
    “Conformed dimensions” are the key to making Kimball’s approach work. If Sales DM and Marketing DM both have a “Customer” dimension, they must define “Customer” identically — same grain, same attributes, same keys. Otherwise cross-mart queries produce inconsistent numbers.
    Common Mistake
    Independent data marts seem attractive initially — fast to build, each department gets exactly what they want. But they become a nightmare: each mart has its own ETL, definitions, and quality issues. When the CFO asks “how many customers do we have?”, Sales says 100K, Marketing says 85K, Finance says 110K. Nobody can reconcile the numbers. This is the “independent mart anti-pattern.”
    Example

    Information Evolution — 5 Stages of DW Maturity (from slides) 

    Stage 1 - REPORT        : What happened?       (Primarily batch)
Stage 2 - ANALYZE       : Why did it happen?   (Ad-hoc queries grow)
Stage 3 - PREDICT       : What will happen?    (Analytical modelling)
Stage 4 - OPERATIONALIZE: What IS happening?   (Continuous update, time-sensitive)
Stage 5 - ACTIVATE      : What do you WANT?    (Event-based triggering)
    What is the difference between a dependent and independent data mart?

    A dependent data mart is populated from a central enterprise data warehouse — it is a consistent, auditable subset. An independent data mart is built directly from operational source systems, bypassing any central warehouse. Independent marts are faster to build but create data silos where departments have different (often conflicting) versions of the same facts.

    Why might an organisation choose bottom-up (Kimball) over top-down (Inmon)?

    Top-down requires a massive upfront investment — it can take 2–5 years before any business user sees value. Many organisations cannot justify this politically or financially. Kimball’s bottom-up approach delivers a working data mart in 3–6 months, proving ROI early. As long as marts are built to a shared architectural plan with conformed dimensions, the result is effectively an enterprise DW assembled incrementally.

    Hard: How do conformed dimensions solve the consistency problem when building multiple data marts incrementally?

    Conformed dimensions are dimension tables (Date, Customer, Product) defined identically across all data marts. When two marts share a conformed dimension, you can drill across both in a single query and get consistent results because “Customer” means the same thing in both. Implementation: (1) Define a “Bus Matrix” mapping each mart’s fact tables to shared dimensions. (2) Develop shared dimension tables centrally. (3) Enforce that each new mart uses the published shared dimensions. (4) Where a mart needs additional attributes, extend — do not fork. This is the essence of Kimball’s Dimensional Bus Architecture.

    Key Takeaways

    • Data mart = focused, departmental subset of DW (Sales, HR, Finance, etc.)
    • Dependent marts draw from the central DW; independent marts are built from source systems (anti-pattern)
    • Top-down (Inmon): enterprise DW first — consistent but slow; Bottom-up (Kimball): mart-by-mart — fast ROI, needs discipline
    • Kimball’s practical approach: plan enterprise-wide, build incrementally with conformed dimensions
    • Conformed dimensions are the glue that keeps multi-mart DWs consistent and queryable together

    7Business Intelligence (BI)

    What BI is, how it relates to DW, and its four core capabilities

    Data warehousing and Business Intelligence are two sides of the same coin. The DW provides the foundation; BI provides the application. You can have a DW without BI tools (just raw data access), but you cannot have meaningful BI without a solid data foundation — and that foundation is the DW.

    Definition
    Business Intelligence (BI): A process that adds value to business processes through monitoring performance indicators about the business environment and their impact on business strategy — helping define, refine, and improve the business model for profitable operations.

    What BI Entails (In Plain Terms)

    • Run simple queries — “How many units did we sell last quarter?”
    • Perform ‘what-if’ analyses — “If we drop price by 10%, what happens to margin?”
    • Interactively analyse results — drill down from region → country → store; slice by product category
    • Discover trends and apply them — “Sales always spike in Q4 — plan inventory accordingly”

    Desired Features of a DW to Support BI

    • Designed for analytical tasks (not transactional)
    • Data from multiple sources, integrated
    • Easy to use and conducive to long interactive sessions
    • Read-intensive data usage patterns
    • Users can run queries and get results online (OLAP)
    • Content updated periodically and stably
    • Ability for users to initiate reports themselves

    OLAP Response Time Requirements

    Query Type Target Response Time
    Simple OLAP queries (slice, dice, drill) A small number of seconds
    Complex query scripts / large list selections A small number of minutes
    Sophisticated modelling / data mining algorithms A small number of hours

    Achieving second-level OLAP response times often requires denormalisation, pre-aggregation (materialised views, OLAP cubes), and/or sampling.

    Pro Tip
    BI vs traditional reporting: Traditional MIS reporting gives you a fixed report designed weeks ago. BI allows interactive exploration — the user drives the analysis, drilling in and pivoting without waiting for IT to write a new report. This self-service capability is what makes BI genuinely transformative.
    How does BI differ from traditional MIS reporting?

    Traditional MIS reporting is batch-oriented, pre-defined, and IT-driven — someone designs a report template, schedules it to run, and managers receive it on a schedule. BI enables interactive data exploration by end-users themselves — they drill down, slice by different dimensions, and run ad-hoc queries without involving IT. The key shift is from IT-push to user-pull of analytical insight.

    What does OLAP stand for and why are interactive response times important?

    OLAP = Online Analytical Processing. Analytical queries (aggregations, drill-downs, slice-and-dice) run against the DW in near-real-time. Interactive response times matter because if a query takes 20 minutes, the user loses their train of thought, abandons exploration, and the BI tool becomes useless for discovery. The goal is to keep simple analytical queries in the seconds range.

    Hard: What technical techniques enable second-level OLAP response times on billions of rows?

    Pre-aggregation: Materialised views or OLAP cubes pre-compute common aggregations so queries read small result sets. Columnar storage: Store data column-by-column, dramatically reducing I/O for analytical queries touching only a few columns. Partitioning: Partition fact tables by date; most queries filter by date range, so only relevant partitions are scanned. Bitmap indexing: Efficient for low-cardinality dimensions (region, product category). Caching: Cache frequently-run query results. Sampling: Statistical sampling can give 95%+ accurate results in milliseconds on a fraction of the data.

    Key Takeaways

    • BI = the process of converting DW data into actionable business insight
    • Four core BI capabilities: simple queries, what-if analysis, interactive exploration, trend discovery
    • OLAP requires interactive (seconds) response times — achieved via denormalisation, cubes, columnar storage
    • DW is the foundation; BI tools are the application layer on top
    • BI enables self-service analytics — shifting from IT-push to user-pull of insight

    8Why is DW Hard? & Scalability

    The fundamental challenges of large-scale data warehousing and Amdahl’s Law

    Building a DW sounds conceptually simple — consolidate data, clean it, query it. So why do so many DW projects fail or run over budget? Because the execution is genuinely hard in ways that only appear when dealing with terabytes of data and hundreds of concurrent users.

    Core Challenges (from Slides)

    • No stable requirements — business questions evolve constantly; a DW designed for today’s questions must adapt to tomorrow’s
    • Familiar DB techniques break down — normalisation, OLTP indexing strategies all perform poorly at DSS scale
    • VLDB scale is hard to comprehend — techniques that work on 100 GB fail spectacularly on 100 TB
    • Non-linear performance impacts — doubling data size does not halve performance linearly; it often degrades exponentially
    • Complex deployment architectures — distributed systems, parallel processing, replication, failover
    • Rapidly changing product landscape — tools and platforms keep evolving
    Pro Tip
    “Hardware is the easyware… software is the hardware.” — If the software does not scale, it does not matter how much hardware you add. Optimise your software and algorithms first, then scale hardware. The reverse does not work.

    Amdahl’s Law

    Amdahl’s Law quantifies the theoretical maximum speedup achievable by parallelising a program. Critical for understanding why simply adding more processors does not always solve DW performance problems.

    Definition
    Amdahl’s Law: The speedup of a program using N parallel processors is limited by the fraction that must remain sequential.

    SpeedUp = 1 / (S + P/N)

    Where: S = sequential fraction, P = parallel fraction (S + P = 1), N = number of processors.
    The keys to parallel performance: (1) amount of parallelism and (2) overhead management.
    Example

    Amdahl’s Law Calculation

    Given: 10% sequential (S=0.1), 90% parallel (P=0.9), 4 processors (N=4)

SpeedUp = 1 / (0.1 + 0.9/4)
        = 1 / (0.1 + 0.225)
        = 1 / 0.325
        = 3.08x  (not 4x as you might hope)

With 100 processors:
SpeedUp = 1 / (0.1 + 0.9/100) = 1 / 0.109 = 9.17x

The sequential fraction (10%) caps the maximum speedup at 10x no matter
how many processors you add. This is the "Amdahl ceiling."

    Parallel Processing in DW — The Impact

    Approach Time to Read 1 TB
    Serial (1 task) ~1.2 days
    2 parallel tasks ~0.6 days
    100 parallel tasks <18 minutes

    Requirements for parallel efficiency: (a) even distribution of tasks (no data skew) and (b) hardware that can sustain the I/O levels. Adding 100 parallel processes to a single spinning disk gains nothing.

    Scalability Dimensions

    Scalability in DW is not just about data size. Design for all four dimensions independently:

    • Amount of Detailed Data — raw fact table rows
    • Complexity of Data Model — number of dimensions, hierarchy levels
    • Concurrent Users — 10 analysts vs 10,000 business users
    • Query Complexity — simple direct queries → multi-table joins → regression analysis → data mining
    Common Mistake
    Designing for today’s data volume and user count only. DW usage grows over time — more users, richer data, more complex queries. A design that works for 50 analysts on 500 GB today may collapse when 500 analysts hit 50 TB in 3 years. Always design with a scalability headroom of 10× or more.
    What does Amdahl’s Law tell us about the limits of parallelism?

    Even with unlimited processors, the maximum speedup is capped: SpeedUp ≤ 1/S. If 20% of a program is sequential, the maximum speedup is 5× — no matter how many processors you add. This means reducing the sequential fraction itself becomes the bottleneck as parallelism scales up. For DW, ETL coordination overhead, index rebuild steps, and commit operations (often sequential) become the real bottleneck.

    Why do performance impacts become non-linear at VLDB scale?

    At small scale, most operations fit in memory (buffer cache) and response times are dominated by CPU. At VLDB scale, data spills to disk — and disk I/O is orders of magnitude slower. Hash joins that worked in-memory now require multiple passes over disk. Sort operations require merge-sort over dozens of passes. Index lookups cause massive random I/O. Result: doubling data size might increase query time by 4–10× rather than 2×. VLDB requires completely different algorithmic and physical design strategies.

    Hard: If 15% of your ETL pipeline is sequential and you have 8 parallel workers, what is your speedup? What would you need to achieve a 10x speedup?

    Current speedup: SpeedUp = 1 / (0.15 + 0.85/8) = 1 / (0.15 + 0.106) = 1 / 0.256 = 3.9×.

    For 10× speedup: Need S ≤ 0.1 (10% or less sequential). Currently at 15%, must reduce the sequential fraction to ≤10% by identifying and parallelising coordination logic, locking, and commit operations. Even with S=0.10 and N=8: SpeedUp = 1/(0.10 + 0.90/8) = 4.8×. For a true 10×, you need both S ≤ 10% AND N ≈ 90+ parallel processors.

    Key Takeaways

    • DW is hard due to evolving requirements, VLDB scale, non-linear performance, and complex architectures
    • “Hardware is easyware” — software scalability comes first; hardware only amplifies good software design
    • Amdahl’s Law: SpeedUp = 1/(S + P/N) — sequential fractions cap the maximum parallel speedup
    • Parallel processing can reduce 1.2-day I/O to under 18 minutes — but requires even task distribution
    • Design for 4 scalability dimensions: data volume, model complexity, concurrent users, query complexity
