Lab Midterm: Sequential Query Guide & Master Cheatsheet

1Master Exam Execution Roadmap

The strict PostgreSQL execution order you must follow to avoid errors

In a Data Warehousing lab exam, the order in which you execute queries is strictly enforced by PostgreSQL. If you try to load the Fact table before the Dimension tables exist, your foreign keys fail. If you insert data into dimensions without checking for duplicates first, unique constraints crash. If you don't validate your data with reconciliation queries, you lose marks immediately.

⚡ The 10-Step Sequential Pipeline (Execution Order in pgAdmin)
STEP 01CREATE SCHEMAS
stg & dw
STEP 02STAGING DDL
Import CSVs
STEP 03DATA AUDIT
Find Defects
STEP 04DIMENSION DDL
Surrogate PKs
STEP 05CLEAN ETL LOAD
Deduplicate
STEP 06DIM_DATE
generate_series
STEP 07FACT DDL
Grain & FKs
STEP 08FACT ETL LOAD
Surrogate Map
STEP 09RECONCILIATION
Zero Orphans
STEP 10OLAP QUERIES
ROLLUP & CUBE
Why this order is non-negotiable: PostgreSQL builds a dependency tree. Fact tables hold Foreign Keys that point to Dimension tables. Therefore, Dimensions MUST be created and populated before the Fact table is loaded. Furthermore, Staging data is always dirty (duplicate rows, whitespace, inconsistent casing); you must profile and clean it during the dimension load so warehouse constraints are never violated.

Golden Rules for the Lab Exam

  • Rule 1 (Staging is Permissive): Never add PRIMARY KEY or FOREIGN KEY constraints to staging tables. Staging is just a raw loading dock — if a CSV has duplicates, constraints will cause the import to crash.
  • Rule 2 (Surrogate Keys in Warehouse): Every warehouse dimension gets an auto-incrementing surrogate primary key (e.g. INT GENERATED ALWAYS AS IDENTITY). The original business ID (e.g. customer_code) becomes a UNIQUE NOT NULL attribute.
  • Rule 3 (Clean on Load): Clean dirty strings (TRIM, INITCAP) and deduplicate (GROUP BY or DISTINCT) as you insert into dimensions.
  • Rule 4 (Surrogate Key Mapping): In the Fact ETL query, you join staging items to warehouse dimensions using natural/business keys, but you SELECT and INSERT the surrogate keys into the Fact table.
  • Rule 5 (Reconciliation is Mandatory): The lab manual explicitly states: "A fact table that loads but does not reconcile to the source is not complete." You must prove matching row counts and matching sums of measures.
Exam Strategy
Create a single clean SQL file in pgAdmin (e.g., LabMid_RollNo.sql). Add clear section headers using SQL comments (-- STEP 1: SCHEMAS, -- STEP 2: STAGING DDL). Run each section block by block and verify row counts before proceeding to the next.

Topic 1 Recap

  • Always execute: Schemas → Staging → Audit → Dimensions → DimDate → Fact → Reconciliation → OLAP.
  • Staging has NO constraints; Warehouse dimensions have Surrogate PKs + Unique Natural Keys.
  • Dimensions must exist before loading the Fact table so surrogate keys can be looked up.

2Lab 6: Schemas, Staging & Data Audit

Steps 1 to 3 — Isolating raw data, creating staging tables, and finding defects

STEP 01 OF 10DDL

Step 1: Create Staging and Warehouse Schemas

Always create two separate schemas. Staging holds the raw extracted CSV data; Warehouse holds the clean, curated star schema.

Why do this first? You cannot create tables without a target schema. Keeping staging separate prevents raw, dirty data from polluting your analytical models.
Query to Write
-- 1. Create separate schemas for staging and data warehouse
CREATE SCHEMA IF NOT EXISTS lab06_stg;
CREATE SCHEMA IF NOT EXISTS lab06_dw;
STEP 02 OF 10DDL

Step 2: Create Permissive Staging Tables & Load CSVs

Create staging tables matching the source CSV columns. Use permissive types like TEXT or generous VARCHAR. Do NOT define primary keys or foreign keys here!

Query to Write
-- 2. Staging Tables (Permissive, NO constraints so dirty CSV imports cleanly)
CREATE TABLE lab06_stg.stg_customers (
    customer_code TEXT,
    customer_name TEXT,
    customer_segment TEXT
);

CREATE TABLE lab06_stg.stg_products (
    product_code TEXT,
    product_name TEXT,
    category TEXT,
    brand TEXT,
    unit_price NUMERIC(12,2)
);

CREATE TABLE lab06_stg.stg_regions (
    region_code TEXT,
    region_name TEXT,
    service_area TEXT
);

CREATE TABLE lab06_stg.stg_orders (
    order_id INT,
    order_date DATE,
    customer_code TEXT,
    region_code TEXT,
    channel_name TEXT
);

CREATE TABLE lab06_stg.stg_order_items (
    line_id INT,
    order_id INT,
    product_code TEXT,
    quantity INT,
    unit_price NUMERIC(12,2),
    discount_pct NUMERIC(5,2)
);
pgAdmin Action
Right-click each table → Import/Export Data → Select CSV file → Format: csv, Header: Yes, Delimiter: , → Click OK.
Immediate Verification Query

Always verify row counts right after importing CSV files:

SELECT 'stg_customers' AS table_name, COUNT(*) AS total_rows FROM lab06_stg.stg_customers
UNION ALL
SELECT 'stg_products', COUNT(*) FROM lab06_stg.stg_products
UNION ALL
SELECT 'stg_regions', COUNT(*) FROM lab06_stg.stg_regions
UNION ALL
SELECT 'stg_orders', COUNT(*) FROM lab06_stg.stg_orders
UNION ALL
SELECT 'stg_order_items', COUNT(*) FROM lab06_stg.stg_order_items;
table_name | total_rows -----------------+------------ stg_customers | 104 -- contains duplicate codes! stg_products | 52 -- contains whitespace defects! stg_regions | 4 stg_orders | 1250 stg_order_items | 3469
STEP 03 OF 10AUDIT

Step 3: Staging Data Quality Profiling (The 5 Essential Audit Queries)

Lab instructors and exam rubrics always ask you to write queries that detect source defects. You must run these 5 queries before building dimensions:

Audit 3.1: Find Duplicate Business Keys

-- Find duplicate customer codes in staging
SELECT customer_code, COUNT(*) AS occurrence_count
FROM lab06_stg.stg_customers
GROUP BY customer_code
HAVING COUNT(*) > 1;
customer_code | occurrence_count --------------+------------------ CUST042 | 2 CUST089 | 2

Audit 3.2: Detect Leading or Trailing Whitespace

-- Detect dirty whitespace by comparing LENGTH with TRIM(LENGTH)
SELECT product_code, product_name, 
       LENGTH(product_name) - LENGTH(TRIM(product_name)) AS extra_spaces
FROM lab06_stg.stg_products
WHERE LENGTH(product_name) != LENGTH(TRIM(product_name));

Audit 3.3: Detect Inconsistent Text Casing

-- Look for segment casing issues (e.g., 'Corporate' vs 'corporate')
SELECT DISTINCT customer_segment, COUNT(*) AS count
FROM lab06_stg.stg_customers
GROUP BY customer_segment;
customer_segment | count -----------------+------- Corporate | 45 corporate | 3 -- defect: inconsistent casing! Consumer | 56

Audit 3.4: Detect NULLs in Mandatory Keys

-- Check if any required natural key is NULL
SELECT * 
FROM lab06_stg.stg_products 
WHERE product_code IS NULL OR TRIM(product_code) = '';

Audit 3.5: Detect Orphan Child Transactions in Staging

-- Check for order items whose parent order does not exist in staging
SELECT oi.line_id, oi.order_id
FROM lab06_stg.stg_order_items oi
LEFT JOIN lab06_stg.stg_orders o ON oi.order_id = o.order_id
WHERE o.order_id IS NULL;
-- In a clean dataset, this returns 0 rows.
Common Student Mistake
Never run DELETE or UPDATE directly on staging tables! The staging layer is an audit trail that proves what arrived from the source. Clean the data as you insert into the warehouse dimensions using SQL functions.

Practice Questions

Q1: Why should staging tables NEVER have foreign key constraints?

Answer: Staging tables are designed to receive raw, unprocessed data directly from source files. Real-world source extracts often contain out-of-order records, missing headers, or temporary orphans. If staging had foreign keys, the pgAdmin CSV import would immediately abort with a constraint violation error, preventing you from loading and analyzing the data.

Q2: What is the fastest query to test if a text column has hidden trailing spaces?

Answer: SELECT * FROM table WHERE column != TRIM(column);. If a string has leading or trailing spaces, its raw value is not equal to its trimmed value.

Q3: If a staging table has 104 rows but only 100 distinct customer codes, what will happen if you load it into a dimension table with a UNIQUE constraint without deduplicating?

Answer: PostgreSQL will terminate the INSERT query with an error: ERROR: duplicate key value violates unique constraint. You must deduplicate using DISTINCT or GROUP BY during the INSERT.

Topic 2 Recap

  • Create lab06_stg and lab06_dw schemas first.
  • Staging tables use permissive types and zero constraints.
  • Always run the 5 audit queries: duplicate keys, whitespace, casing variations, NULLs, and orphan child records.

3Lab 6: Dimensions & DimDate Generation

Steps 4 to 6 — Surrogate keys, cleaning ETL loads, and generating calendar dates

STEP 04 OF 10DDL

Step 4: Create Warehouse Dimension Tables with Surrogate PKs

Warehouse dimensions require a Surrogate Key as their Primary Key (usually an integer sequence) and a UNIQUE NOT NULL constraint on the original Business Key (natural key).

Why Surrogate Keys instead of Natural Keys? Natural keys from source systems (like customer_code = 'CUST-01') can change, get reused, or differ across merged operational databases. Surrogate keys insulate the warehouse from external operational changes, provide compact integer joins, and enable historical tracking (SCD Type 2).
Queries to Write (Dimension DDL)
-- 1. DimRegion
CREATE TABLE lab06_dw.dim_region (
    region_key INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    region_code VARCHAR(50) UNIQUE NOT NULL,
    region_name VARCHAR(100) NOT NULL,
    service_area VARCHAR(100)
);

-- 2. DimCustomer
CREATE TABLE lab06_dw.dim_customer (
    customer_key INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_code VARCHAR(50) UNIQUE NOT NULL,
    customer_name VARCHAR(150) NOT NULL,
    customer_segment VARCHAR(50) NOT NULL
);

-- 3. DimProduct
CREATE TABLE lab06_dw.dim_product (
    product_key INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_code VARCHAR(50) UNIQUE NOT NULL,
    product_name VARCHAR(150) NOT NULL,
    category VARCHAR(100) NOT NULL,
    brand VARCHAR(100) NOT NULL,
    unit_price NUMERIC(12,2)
);

-- 4. DimChannel
CREATE TABLE lab06_dw.dim_channel (
    channel_key INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    channel_name VARCHAR(50) UNIQUE NOT NULL
);
STEP 05 OF 10ETL LOAD

Step 5: Clean & Deduplicate During Dimension Load

We do not just copy staging data blindly. We apply data cleaning functions and deduplicate with GROUP BY or DISTINCT so the warehouse contains pristine, unique dimension records.

Queries to Write (Clean Dimension Loads)
-- Load DimRegion
INSERT INTO lab06_dw.dim_region (region_code, region_name, service_area)
SELECT 
    TRIM(region_code),
    TRIM(region_name),
    TRIM(service_area)
FROM lab06_stg.stg_regions
GROUP BY TRIM(region_code), TRIM(region_name), TRIM(service_area);

-- Load DimCustomer (Fix casing with INITCAP/UPPER, trim whitespace, deduplicate)
INSERT INTO lab06_dw.dim_customer (customer_code, customer_name, customer_segment)
SELECT 
    TRIM(customer_code),
    INITCAP(TRIM(customer_name)),
    INITCAP(TRIM(customer_segment))
FROM lab06_stg.stg_customers
WHERE customer_code IS NOT NULL
GROUP BY TRIM(customer_code), INITCAP(TRIM(customer_name)), INITCAP(TRIM(customer_segment));

-- Load DimProduct (Clean names, handle whitespace)
INSERT INTO lab06_dw.dim_product (product_code, product_name, category, brand, unit_price)
SELECT 
    TRIM(product_code),
    INITCAP(TRIM(product_name)),
    INITCAP(TRIM(category)),
    INITCAP(TRIM(brand)),
    MAX(unit_price) -- picks single valid price in case of duplicate codes
FROM lab06_stg.stg_products
WHERE product_code IS NOT NULL
GROUP BY TRIM(product_code), INITCAP(TRIM(product_name)), INITCAP(TRIM(category)), INITCAP(TRIM(brand));

-- Load DimChannel (Extracted from staging orders)
INSERT INTO lab06_dw.dim_channel (channel_name)
SELECT DISTINCT TRIM(channel_name)
FROM lab06_stg.stg_orders
WHERE channel_name IS NOT NULL;
Dimension Uniqueness Verification Query

Every dimension must be validated to prove total rows match distinct business keys:

SELECT 
    'dim_customer' AS dimension, 
    COUNT(*) AS total_rows, 
    COUNT(DISTINCT customer_code) AS unique_business_keys,
    CASE WHEN COUNT(*) = COUNT(DISTINCT customer_code) THEN 'PASS (1:1)' ELSE 'FAIL' END AS status
FROM lab06_dw.dim_customer
UNION ALL
SELECT 
    'dim_product', 
    COUNT(*), 
    COUNT(DISTINCT product_code),
    CASE WHEN COUNT(*) = COUNT(DISTINCT product_code) THEN 'PASS (1:1)' ELSE 'FAIL' END
FROM lab06_dw.dim_product;
dimension | total_rows | unique_business_keys | status --------------+------------+----------------------+----------- dim_customer | 100 | 100 | PASS (1:1) dim_product | 50 | 50 | PASS (1:1)
STEP 06 OF 10DDL + ETL

Step 6: Build & Populate DimDate using generate_series()

In analytical data warehouses, the Date dimension is never imported from a transactional CSV. It is pre-generated programmatically using PostgreSQL's built-in generate_series() function to cover all historical and future calendar dates.

Date Dimension DDL
CREATE TABLE lab06_dw.dim_date (
    date_key INT PRIMARY KEY,              -- e.g. 20261014
    full_date DATE UNIQUE NOT NULL,        -- e.g. '2026-10-14'
    day INT NOT NULL,                      -- 14
    month INT NOT NULL,                    -- 10
    month_name VARCHAR(20) NOT NULL,       -- 'October'
    quarter INT NOT NULL,                  -- 4
    year INT NOT NULL,                     -- 2026
    day_of_week VARCHAR(20) NOT NULL       -- 'Wednesday'
);
The Golden generate_series() Population Query
-- Generate calendar dates from 2024-01-01 to 2026-12-31 (1096 days)
INSERT INTO lab06_dw.dim_date (
    date_key, full_date, day, month, month_name, quarter, year, day_of_week
)
SELECT 
    TO_CHAR(d, 'YYYYMMDD')::INT AS date_key,
    d::DATE AS full_date,
    EXTRACT(DAY FROM d)::INT AS day,
    EXTRACT(MONTH FROM d)::INT AS month,
    TRIM(TO_CHAR(d, 'Month')) AS month_name,
    EXTRACT(QUARTER FROM d)::INT AS quarter,
    EXTRACT(YEAR FROM d)::INT AS year,
    TRIM(TO_CHAR(d, 'Day')) AS day_of_week
FROM generate_series('2024-01-01'::DATE, '2026-12-31'::DATE, '1 day'::INTERVAL) AS d;
Validate Date Coverage Against Staging Orders
-- Verify that DimDate covers the full range of orders in staging
SELECT 
    (SELECT MIN(order_date) FROM lab06_stg.stg_orders) AS min_order_date,
    (SELECT MIN(full_date) FROM lab06_dw.dim_date) AS min_calendar_date,
    (SELECT MAX(order_date) FROM lab06_stg.stg_orders) AS max_order_date,
    (SELECT MAX(full_date) FROM lab06_dw.dim_date) AS max_calendar_date;
min_order_date | min_calendar_date | max_order_date | max_calendar_date ---------------+-------------------+----------------+------------------- 2024-01-05 | 2024-01-01 | 2026-09-30 | 2026-12-31 -- Full Coverage!

Practice Questions

Q1: Why is date_key formatted as an integer YYYYMMDD rather than a DATE or SERIAL key?

Answer: An integer in YYYYMMDD format (e.g., 20261014) is a "smart surrogate key". It is compact (4 bytes), sorts chronologically without conversion, allows easy table partitioning by range, and lets humans immediately understand the date without joining to dim_date.

Q2: What happens if TO_CHAR(d, 'Month') is used without TRIM()?

Answer: PostgreSQL's TO_CHAR(..., 'Month') pads month names with trailing whitespace to match the length of the longest month ("September"). Without TRIM(), checking WHERE month_name = 'May' fails because the database contains 'May '!

Q3: Why must DimCustomer and DimProduct be populated BEFORE FactSales?

Answer: FactSales stores foreign keys (customer_key, product_key) referencing the surrogate primary keys of the dimension tables. If the dimension tables are empty, the surrogate keys don't exist yet, so the Fact table cannot be loaded without violating foreign key constraints.

Topic 3 Recap

  • Dimensions use surrogate primary keys (GENERATED ALWAYS AS IDENTITY) and unique natural keys.
  • Clean strings with TRIM(), INITCAP(), and deduplicate with GROUP BY on load.
  • DimDate is generated via generate_series('2024-01-01'::DATE, '2026-12-31'::DATE, '1 day'::INTERVAL).

4Lab 6: Fact Load & Full Reconciliation

Steps 7 to 10 — Surrogate mapping, calculating measures, and proving zero data loss

STEP 07 OF 10DDL

Step 7: Create the Fact Table DDL

Before writing the DDL, always write down the Fact Grain Statement:

Fact Grain Statement
One row in Fact Sales represents: One line item of a customer sales transaction.
Fact Table DDL
CREATE TABLE lab06_dw.fact_sales (
    -- 1. Fact Primary Key
    line_id INT PRIMARY KEY,

    -- 2. Degenerate Dimension (stored directly in fact table for drill-down & audit)
    order_id INT NOT NULL,

    -- 3. Dimension Foreign Keys (referencing warehouse surrogate primary keys)
    date_key INT NOT NULL REFERENCES lab06_dw.dim_date(date_key),
    customer_key INT NOT NULL REFERENCES lab06_dw.dim_customer(customer_key),
    product_key INT NOT NULL REFERENCES lab06_dw.dim_product(product_key),
    region_key INT NOT NULL REFERENCES lab06_dw.dim_region(region_key),
    channel_key INT NOT NULL REFERENCES lab06_dw.dim_channel(channel_key),

    -- 4. Numeric Measures
    quantity INT NOT NULL,
    unit_price_pkr NUMERIC(12,2) NOT NULL,
    discount_pct NUMERIC(5,2) DEFAULT 0,
    gross_revenue_pkr NUMERIC(12,2) NOT NULL,
    discount_amount_pkr NUMERIC(12,2) NOT NULL,
    net_revenue_pkr NUMERIC(12,2) NOT NULL
);
STEP 08 OF 10THE MASTER ETL QUERY

Step 8: Surrogate Key Mapping & Fact Table Population

This is the most critical query of the entire exam. You must join the staging transaction tables to the warehouse dimension tables on their natural/business keys, but insert the surrogate keys into the fact table.

How the Join Architecture Works:
  1. stg_order_items has the line measures (quantity, price, product_code).
  2. stg_orders has the order context (order_date, customer_code, region_code, channel_name). Join them on order_id.
  3. Join to each dim_* table on the trimmed business key (e.g. TRIM(o.customer_code) = c.customer_code).
  4. In the SELECT clause, pick c.customer_key, p.product_key, etc.
  5. Calculate measures: gross = qty * price, discount_amt = gross * (discount_pct / 100.0), net = gross - discount_amt.
The Golden Fact Load Query
INSERT INTO lab06_dw.fact_sales (
    line_id,
    order_id,
    date_key,
    customer_key,
    product_key,
    region_key,
    channel_key,
    quantity,
    unit_price_pkr,
    discount_pct,
    gross_revenue_pkr,
    discount_amount_pkr,
    net_revenue_pkr
)
SELECT 
    oi.line_id,
    o.order_id,
    TO_CHAR(o.order_date, 'YYYYMMDD')::INT AS date_key,
    c.customer_key,
    p.product_key,
    r.region_key,
    ch.channel_key,
    oi.quantity,
    oi.unit_price AS unit_price_pkr,
    COALESCE(oi.discount_pct, 0) AS discount_pct,
    -- Inline Measure Calculations:
    ROUND((oi.quantity * oi.unit_price)::NUMERIC, 2) AS gross_revenue_pkr,
    ROUND((oi.quantity * oi.unit_price * (COALESCE(oi.discount_pct, 0) / 100.0))::NUMERIC, 2) AS discount_amount_pkr,
    ROUND((oi.quantity * oi.unit_price * (1.0 - (COALESCE(oi.discount_pct, 0) / 100.0)))::NUMERIC, 2) AS net_revenue_pkr
FROM lab06_stg.stg_order_items oi
JOIN lab06_stg.stg_orders o ON oi.order_id = o.order_id
JOIN lab06_dw.dim_customer c ON TRIM(o.customer_code) = c.customer_code
JOIN lab06_dw.dim_product p ON TRIM(oi.product_code) = p.product_code
JOIN lab06_dw.dim_region r ON TRIM(o.region_code) = r.region_code
JOIN lab06_dw.dim_channel ch ON TRIM(o.channel_name) = ch.channel_name;
STEP 09 OF 10RECONCILIATION

Step 9: Post-Load Reconciliation (Mandatory 4 Checks)

The exam marking rubric reserves 20% to 30% of marks for reconciliation. You must prove referential integrity and numerical fidelity.

Check 9.1: Zero-Orphan Verification Query

Verifies that every foreign key in fact_sales successfully matches an existing row in every dimension table:

SELECT 
    COUNT(*) FILTER (WHERE c.customer_key IS NULL) AS orphan_customers,
    COUNT(*) FILTER (WHERE p.product_key IS NULL) AS orphan_products,
    COUNT(*) FILTER (WHERE r.region_key IS NULL) AS orphan_regions,
    COUNT(*) FILTER (WHERE ch.channel_key IS NULL) AS orphan_channels,
    COUNT(*) FILTER (WHERE d.date_key IS NULL) AS orphan_dates
FROM lab06_dw.fact_sales f
LEFT JOIN lab06_dw.dim_customer c ON f.customer_key = c.customer_key
LEFT JOIN lab06_dw.dim_product p ON f.product_key = p.product_key
LEFT JOIN lab06_dw.dim_region r ON f.region_key = r.region_key
LEFT JOIN lab06_dw.dim_channel ch ON f.channel_key = ch.channel_key
LEFT JOIN lab06_dw.dim_date d ON f.date_key = d.date_key;
orphan_customers | orphan_products | orphan_regions | orphan_channels | orphan_dates -----------------+-----------------+----------------+-----------------+------------- 0 | 0 | 0 | 0 | 0 -- Zero Orphans!

Check 9.2: Grain / Row-Count Reconciliation

Proves no source transaction lines were lost or duplicated:

SELECT 
    (SELECT COUNT(*) FROM lab06_stg.stg_order_items) AS source_order_items_count,
    (SELECT COUNT(*) FROM lab06_dw.fact_sales) AS warehouse_fact_rows_count,
    CASE WHEN (SELECT COUNT(*) FROM lab06_stg.stg_order_items) = (SELECT COUNT(*) FROM lab06_dw.fact_sales)
         THEN 'PASS (Exact Match)' ELSE 'FAIL (Mismatch)' END AS status;
source_order_items_count | warehouse_fact_rows_count | status -------------------------+---------------------------+------------------- 3469 | 3469 | PASS (Exact Match)

Check 9.3: Measure Reconciliation (Numerical Integrity)

Step 10: Load-Failure Debugging (Troubleshooting Row Inflation)

A common exam challenge question: "A student reports that FactSales has 3,550 rows while the source has only 3,469 rows. Revenue is also higher than source! What went wrong and how do you diagnose it?"

The Root Cause: Cartesian Product on Duplicate Dimension Keys! If dim_customer or dim_product contains duplicate rows for the same business key (e.g. two rows for 'CUST042'), then when fact_sales joins on TRIM(customer_code) = c.customer_code, each transaction for that customer joins twice! This inflates both the row count and the total revenue.
Diagnostic Query to Find Inflating Dimension Keys
-- Check which dimension has duplicate business keys
SELECT customer_code, COUNT(*) AS duplicate_count
FROM lab06_dw.dim_customer
GROUP BY customer_code
HAVING COUNT(*) > 1;

-- If this returns rows, dimension uniqueness was NOT enforced!

Practice Questions

Q1: Why is order_id called a "Degenerate Dimension" in FactSales?

Answer: order_id is a dimension identifier (an invoice/order number) that has no separate descriptive table because all its attributes (customer, date, region) already belong to other dimensions. It is stored directly in the Fact table for tracking, grouping, and drilling down to raw transactions.

Q2: Why is row-count reconciliation alone NOT sufficient to prove an ETL load is correct?

Answer: An ETL query could lose 10 source rows and simultaneously duplicate 10 other rows due to an accidental join, resulting in the exact same total row count! Only Measure Reconciliation (comparing SUM(quantity) and SUM(revenue)) guarantees numerical accuracy.

Q3: In the Fact ETL query, why do we join staging items to staging orders before joining to dimensions?

Answer: Because the transactional data is split: stg_order_items has the product code, quantity, and price, but the customer code, order date, region, and channel are in stg_orders. Joining on order_id consolidates the transaction before mapping to dimensions.

Topic 4 Recap

  • Fact table grain: One row per order line item. Stores degenerate order_id, surrogate FKs, and measures.
  • ETL query joins staging order lines + staging orders to warehouse dimensions ON natural keys, selecting surrogate keys.
  • Reconcile 4 ways: Zero-orphan count, Exact row match, Exact measure sums, and Constraint failure demonstration.

A major exam rule in Lab 4: "Aggregate first, then apply Top-N logic. Do not rank individual transaction rows."

Practice Questions

Q1: Why should you NEVER extract the year or month by parsing the integer date_key in SQL?

Answer: Doing text or math parsing like LEFT(date_key::TEXT, 4) bypasses the dimensional model, prevents the query planner from using dimension indexes, and breaks if key conventions change. Always join to dim_date and filter on d.year = 2025.

Q2: What is the difference between Slicing and Dicing in OLAP?

Answer: Slice: Selecting a single dimension value (e.g. WHERE year = 2025). Dice: Selecting specific sub-ranges across two or more dimensions (e.g. WHERE year IN (2024, 2025) AND region IN ('Punjab', 'Sindh')).

Q3: When writing a Top-N query, why is LIMIT without GROUP BY incorrect?

Answer: Without GROUP BY, the query ranks raw individual transaction rows rather than the cumulative performance of the category or entity.

Topic 5 Recap

  • ROLAP executes relational joins between Fact table and Dimensions.
  • Always join to dim_date for time filtering; never manipulate date_key string.
  • Top-N requires GROUP BY before ORDER BY ... DESC LIMIT N.

6Lab 4: ROLLUP, CUBE & Subtotal Labeling

Hierarchical subtotals, cross-tabulations, and labeling NULLs with GROUPING()

Standard SQL GROUP BY only produces a single summary level. Management frequently demands simultaneous subtotals and grand totals. PostgreSQL provides ROLLUP and CUBE to generate all levels in a single query.

OLAP STEP 04HIERARCHY

Step 4: Hierarchical Subtotals with ROLLUP

ROLLUP(A, B, C) generates hierarchical subtotals from right to left ($N + 1$ grouping levels):

  • Level 3: (A, B, C) → Detailed individual rows
  • Level 2: (A, B, NULL) → Subtotal for B within A
  • Level 1: (A, NULL, NULL) → Subtotal for A
  • Level 0: (NULL, NULL, NULL) → Grand Total across all rows!
Order Matters in ROLLUP! ROLLUP(Region, Category, Product) rolls up from Product → Category → Region → Grand Total. If you wrote ROLLUP(Product, Category, Region), you would get Category subtotals within each Product, which makes no business sense!

Task 4.1: Product Hierarchy Rollup

-- Basic ROLLUP: Produces product detail, category subtotals, region subtotals, and grand total
SELECT 
    r.region_name,
    p.category,
    p.product_name,
    SUM(f.net_revenue_pkr) AS net_revenue
FROM lab04.fact_sales f
JOIN lab04.dim_region r ON f.region_id = r.region_id
JOIN lab04.dim_product p ON f.product_id = p.product_id
GROUP BY ROLLUP(r.region_name, p.category, p.product_name)
ORDER BY r.region_name, p.category, p.product_name;
OLAP STEP 05PROFESSIONAL SQL

Step 5: Label Subtotals Cleanly using GROUPING()

In standard ROLLUP output, rolled-up columns appear as NULL. To business managers, NULL looks like missing data or a bug. Instructors deduct marks if you leave NULLs unlabeled!

The GROUPING() Function
GROUPING(column) returns 1 if the column was rolled-up (it is a subtotal row), and returns 0 if the column is part of the regular grouping level.
The Golden Exam Query: Clean Subtotal Labeling
SELECT 
    -- 1. Region labeling
    CASE 
        WHEN GROUPING(r.region_name) = 1 THEN '>>> ALL REGIONS (GRAND TOTAL) <<<'
        ELSE r.region_name 
    END AS region,

    -- 2. Category labeling
    CASE 
        WHEN GROUPING(r.region_name) = 1 THEN '---'
        WHEN GROUPING(p.category) = 1 THEN '>> ' || r.region_name || ' Subtotal'
        ELSE p.category 
    END AS category,

    -- 3. Product labeling
    CASE 
        WHEN GROUPING(p.category) = 1 THEN '---'
        WHEN GROUPING(p.product_name) = 1 THEN '> ' || p.category || ' Subtotal'
        ELSE p.product_name 
    END AS product,

    -- 4. Revenue measure
    SUM(f.net_revenue_pkr) AS total_revenue
FROM lab04.fact_sales f
JOIN lab04.dim_region r ON f.region_id = r.region_id
JOIN lab04.dim_product p ON f.product_id = p.product_id
GROUP BY ROLLUP(r.region_name, p.category, p.product_name)
ORDER BY r.region_name NULLS LAST, p.category NULLS LAST, p.product_name NULLS LAST;
region | category | product | total_revenue ---------------------------------+-----------------------+-----------------------+-------------- Punjab | Electronics | Laptop Pro 15 | 1200000.00 Punjab | Electronics | Wireless Mouse | 150000.00 Punjab | Electronics | > Electronics Subtotal| 1350000.00 -- Cat Subtotal Punjab | Home Goods | Coffee Maker | 420000.00 Punjab | Home Goods | > Home Goods Subtotal | 420000.00 Punjab | >> Punjab Subtotal | --- | 1770000.00 -- Reg Subtotal >>> ALL REGIONS (GRAND TOTAL) <<<| --- | --- | 4500000.00 -- Grand Total
OLAP STEP 06CROSS-TAB

Step 6: Multi-Dimensional Cross-Tabulation with CUBE

While ROLLUP follows a strict hierarchy, CUBE generates ALL possible combinations of the grouped columns ($2^N$ grouping sets).

Two-Dimensional Cube (Region × Channel) → $2^2 = 4$ Combinations:

  • Combination 1: (Region, Channel) → Regular detailed sales
  • Combination 2: (Region, ALL Channels) → Regional total
  • Combination 3: (ALL Regions, Channel) → Channel total
  • Combination 4: (ALL Regions, ALL Channels) → Grand Total
2D CUBE Query with Row Classification
SELECT 
    COALESCE(r.region_name, 'ALL REGIONS') AS region,
    COALESCE(ch.channel_name, 'ALL CHANNELS') AS channel,
    SUM(f.net_revenue_pkr) AS total_revenue,
    -- Explain row type using GROUPING:
    CASE 
        WHEN GROUPING(r.region_name) = 1 AND GROUPING(ch.channel_name) = 1 THEN 'Grand Total'
        WHEN GROUPING(r.region_name) = 1 THEN 'Channel Subtotal (All Regions)'
        WHEN GROUPING(ch.channel_name) = 1 THEN 'Region Subtotal (All Channels)'
        ELSE 'Detailed Cell'
    END AS row_classification
FROM lab04.fact_sales f
JOIN lab04.dim_region r ON f.region_id = r.region_id
JOIN lab04.dim_channel ch ON f.channel_id = ch.channel_id
GROUP BY CUBE(r.region_name, ch.channel_name)
ORDER BY GROUPING(r.region_name), GROUPING(ch.channel_name);
Why 3D CUBE Explodes
A 3D cube like CUBE(Region, Channel, Category) generates $2^3 = 8$ grouping sets. If you have 4 regions, 3 channels, and 5 categories, the result has $(4 imes 3 imes 5) + (4 imes 3) + (4 imes 5) + (3 imes 5) + 4 + 3 + 5 + 1 = 118$ rows! CUBE grows exponentially with each added dimension.
OLAP STEP 07HIERARCHY NAVIGATION

Step 7: Drill-Down vs Roll-Up Operations in SQL

In analytical systems, users navigate between levels of detail:

  • Drill-Down: Moving from a coarser grain to a finer grain (adding more columns to GROUP BY). E.g. analyzing Year → Year + Quarter → Year + Quarter + Month.
  • Roll-Up: Moving from a finer grain to a coarser grain (removing columns from GROUP BY). E.g. collapsing Month → Quarter → Year.
Demonstrating Drill-Down in SQL
-- Level 1 (Executive Summary): Category level
SELECT p.category, SUM(f.net_revenue_pkr) AS revenue
FROM lab04.fact_sales f JOIN lab04.dim_product p ON f.product_id = p.product_id
GROUP BY p.category;

-- Level 2 (Drill-Down for Product Manager): Category + Individual Product
SELECT p.category, p.product_name, SUM(f.net_revenue_pkr) AS revenue
FROM lab04.fact_sales f JOIN lab04.dim_product p ON f.product_id = p.product_id
GROUP BY p.category, p.product_name;

Practice Questions

Q1: How many grouping sets are produced by GROUP BY ROLLUP(A, B, C)?

Answer: $N + 1 = 3 + 1 = 4$ grouping sets: (A, B, C), (A, B), (A), and ().

Q2: How many grouping sets are produced by GROUP BY CUBE(A, B, C)?

Answer: $2^N = 2^3 = 8$ grouping sets: (A, B, C), (A, B), (A, C), (B, C), (A), (B), (C), and ().

Q3: If GROUPING(r.region_name) returns 1, what does that mean?

Answer: It means region_name was aggregated out (collapsed) by the ROLLUP or CUBE operation. That specific row is a summary subtotal across all regions (or a grand total), rather than an individual region's data.

Topic 6 Recap

  • ROLLUP(A, B, C) generates hierarchical subtotals ($N+1$ levels, order matters!).
  • CUBE(A, B) generates all combinations ($2^N$ levels).
  • Always use GROUPING() with CASE WHEN to replace ugly NULL values with clear subtotal labels.
  • Drill-down adds columns to GROUP BY; Roll-up removes columns.

7Lab 4: MOLAP Simulation & Architectures

Physical pre-aggregation, storage compression, lost grain, and OLAP architectures

OLAP STEP 08PRE-AGGREGATION

Step 8: Simulate MOLAP using a Physical Summary Table

What is MOLAP? In Multidimensional OLAP, data is pre-computed and stored in summary arrays or pre-aggregated tables rather than detailed transaction rows. Queries return instantaneously because the database does not need to scan millions of rows or perform multi-table joins at query time.

Pre-Aggregated Table Grain
Grain: One row per Year + Month + Region + Category.
Query to Create and Populate Summary Table
CREATE TABLE lab04.agg_month_region_category AS
SELECT 
    d.year,
    d.month,
    r.region_name,
    p.category,
    SUM(f.net_revenue_pkr) AS total_net_revenue,
    SUM(f.quantity) AS total_quantity,
    COUNT(DISTINCT f.order_id) AS total_orders
FROM lab04.fact_sales f
JOIN lab04.dim_date d ON f.date_key = d.date_key
JOIN lab04.dim_region r ON f.region_id = r.region_id
JOIN lab04.dim_product p ON f.product_id = p.product_id
GROUP BY d.year, d.month, r.region_name, p.category;
Compression Ratio Query

Compute how much storage and row volume was compressed by pre-aggregating:

SELECT 
    (SELECT COUNT(*) FROM lab04.fact_sales) AS fact_rows,
    (SELECT COUNT(*) FROM lab04.agg_month_region_category) AS agg_rows,
    ROUND((SELECT COUNT(*) FROM lab04.fact_sales)::NUMERIC / 
          (SELECT COUNT(*) FROM lab04.agg_month_region_category), 2) AS compression_ratio;
fact_rows | agg_rows | compression_ratio ----------+----------+------------------ 3469 | 192 | 18.07 -- 18x fewer rows to scan!

Same Business Question, Two Storage Approaches

Compare answering: "Find 2025 monthly net revenue for Punjab Electronics":

Approach 1: Detailed ROLAP

Joins 4 tables, scans all 3,469 detailed order lines, groups on the fly:

SELECT d.month, SUM(f.net_revenue_pkr)
FROM lab04.fact_sales f
JOIN lab04.dim_date d ON f.date_key = d.date_key
JOIN lab04.dim_region r ON f.region_id = r.region_id

WHERE d.year = 2025 AND r.region_name = 'Punjab' AND p.category = 'Electronics'

Cost: 3 Joins + Large Scan

Approach 2: Pre-Aggregated MOLAP

Queries the pre-computed summary table directly with zero joins:

SELECT month, total_net_revenue
FROM lab04.agg_month_region_category
WHERE year = 2025 AND region_name = 'Punjab' AND category = 'Electronics';

Cost: 0 Joins + Scans only 12 rows!

The Trade-Off: Lost Detail / Lost Grain (Exam Favorite!)
Teacher's Question: "Write one business question that CAN be answered by the detailed fact table, but CANNOT be answered by agg_month_region_category. Explain what was lost."

Example Question: "Which customer bought the most goods in October 2025?" or "What percentage of sales came through the Mobile App channel?"
Explanation: During pre-aggregation, individual customer_id and channel_id were collapsed and discarded. The aggregate table only remembers (Year, Month, Region, Category). Any finer or orthogonal dimensional detail is permanently lost.

Master OLAP Architectures Comparison Table

Architecture Where Detail Lives Key Strength Key Limitation
ROLAP (Relational OLAP) Relational tables (Star / Snowflake schema) Handles massive data scale; allows unlimited drill-down to line-item detail. Slower query response; multi-table joins on large facts are compute-heavy.
MOLAP (Multidimensional OLAP) Pre-computed multi-dimensional cubes / summary tables Blazing fast query speed (0 joins, pre-calculated totals). Storage explosion; rigid structure; cannot drill down past the pre-aggregated grain.
HOLAP (Hybrid OLAP) Detailed rows in relational DB; frequent summaries in MOLAP cubes Best of both: fast dashboard KPIs with on-demand drill-down to detailed relational rows. Complex architectural overhead and synchronisation requirements.
DOLAP (Desktop OLAP) Small local extract stored on analyst's workstation / Excel / Power BI Allows offline self-service analysis without loading the central DW server. Limited data size; risk of data silos and stale un-synchronised reports.

Practice Questions

Q1: Why is an aggregate table considered a simulation of MOLAP?

Answer: Because true MOLAP engines store data in specialized multidimensional disk structures (arrays/cubes). An aggregate table in PostgreSQL simulates this by physically pre-computing and storing dimensional summaries so analytical queries avoid runtime joins and aggregation scans.

Q2: What is a Compression Ratio of 18.07 telling you?

Answer: It means that for every 18 transaction rows in the detailed fact table, only 1 summary row is stored in the aggregate table. The storage footprint and scan cost are compressed by ~94%.

Q3: In a HOLAP architecture, how would a dashboard query work when a user clicks "View Raw Invoices"?

Answer: The high-level KPI dashboard queries the pre-computed MOLAP cache for instant summary figures. When the user requests raw invoice lines, the HOLAP query engine transparently falls back to the underlying relational fact table (ROLAP) to retrieve the detailed transactions.

Topic 7 Recap

  • MOLAP pre-computes summaries for instant query response with 0 joins.
  • Pre-aggregation sacrifices detail: any dimension not in the GROUP BY cannot be queried.
  • Know the 4 architectures: ROLAP (relational), MOLAP (cubes), HOLAP (hybrid), DOLAP (desktop/offline).

Essential Viva Definitions (Answer in 1 Line)

Concept Exam Definition & One-Liner
Fact Grain The exact real-world event represented by a single row in the fact table. "One row represents one line item of a customer order."
Additive Measure Can be meaningfully summed across all dimensions (e.g. quantity, gross_revenue).
Semi-Additive Measure Can be summed across some dimensions (like customer or branch), but NOT across time (e.g. bank account balance, inventory snapshot — summing balance across 30 days gives a meaningless number!).
Non-Additive Measure Cannot be summed across any dimension (e.g. unit_price, profit_margin_pct, temperature). Must be averaged or re-calculated from component sums.
Conformed Dimension A standardized dimension that has the exact same meaning and keys across multiple fact tables in the enterprise (e.g. DimDate or DimCustomer shared between Sales and Inventory).
Degenerate Dimension A dimension identifier (like order_id or invoice_num) stored directly inside the fact table without a parent dimension table.
Factless Fact Table A fact table that contains only foreign keys and no numeric measures, used to record events (e.g. student attendance) or coverage conditions (e.g. products on promotion).
Star vs Snowflake Star: Dimensions are denormalized (Category is in Product table); fewer joins, faster queries. Snowflake: Dimensions are normalized into sub-tables (Product → Subcategory → Category); saves minimal storage but requires more joins.
The Top 7 Fatal Exam Mistakes to Avoid
  1. Inserting Fact before Dimensions: Foreign keys will throw constraint errors because surrogate keys do not exist yet.
  2. Adding PK/FK constraints to Staging: If source CSV has duplicate rows, the pgAdmin import crashes immediately.
  3. Forgetting to TRIM() text during loads: Strings with hidden trailing spaces fail join conditions ('CUST01 ' != 'CUST01'), causing missing fact rows!
  4. Parsing date_key instead of joining DimDate: Doing LEFT(date_key::TEXT, 4) instead of joining to dim_date loses marks.
  5. Applying LIMIT without GROUP BY for Top-N: Ranks single transactions instead of aggregated performance.
  6. Leaving NULLs in ROLLUP/CUBE: Forgetting GROUPING() and leaving confusing raw NULLs in the output.
  7. Assuming Row Count match means 100% success: Always verify Measure Reconciliation (sums of quantity and revenue).

5. Analytical Window Functions (Advanced Queries)

Teachers occasionally include a bonus question on ranking or running totals:

Rank Products by Revenue within each Region:

SELECT 
    r.region_name,
    p.product_name,
    SUM(f.net_revenue_pkr) AS revenue,
    DENSE_RANK() OVER (
        PARTITION BY r.region_name 
        ORDER BY SUM(f.net_revenue_pkr) DESC
    ) AS regional_rank
FROM lab04.fact_sales f
JOIN lab04.dim_region r ON f.region_id = r.region_id
JOIN lab04.dim_product p ON f.product_id = p.product_id
GROUP BY r.region_name, p.product_name;

Cumulative Running Total of Revenue by Month:

SELECT 
    d.year,
    d.month,
    SUM(f.net_revenue_pkr) AS monthly_revenue,
    SUM(SUM(f.net_revenue_pkr)) OVER (
        PARTITION BY d.year 
        ORDER BY d.month 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_yearly_revenue
FROM lab04.fact_sales f
JOIN lab04.dim_date d ON f.date_key = d.date_key
GROUP BY d.year, d.month
ORDER BY d.year, d.month;
