Volcano / Iterator Model Goetz Graefe

Every operator implements three standardized procedural methods:

  • open(): Allocates buffers and initializes child streams.
  • next(): Pulls one data tuple (granule) on-demand.
  • close(): Cleans up state and deallocates memory.

Win: Demand-driven pipelining in a single OS process—avoids writing intermediate results to temporary disk files.

Buffer Management in DSS LRU Fails

Buffer Thrashing: A 50 GB table scanned through a 4 GB RAM pool under standard OS LRU will continuously evict pages without a single cache hit.

  • Fix/Unfix Semantics: Pin hot pages (e.g. hash tables) in RAM.
  • Read-Ahead (Track-at-a-Crack): Asynchronous prefetching matches disk bus speed with CPU execution.

Execution Tree Topologies

Left-Deep Tree
(⋈) / \ (⋈) (R3) / \ (R1) (R2)
Rule: Right child is always a base leaf.
Pros: Minimal memory footprint; outer relation streams through. Standard in OLTP.
Right-Deep Tree
(⋈) / \ (R1) (⋈) / \ (R2) (R3)
Rule: Left child is always a base leaf.
Pros: Builds multiple hash tables in parallel memory across dimension tables.
Bushy Tree
(⋈) / \ (⋈) (⋈) / \ / \ (R1)(R2) (R3)(R4)
Rule: Joins combine results of other joins.
Pros: Maximum inter-operator parallelism; critical for complex snowflake queries.
Benchmark Test
The "Guy Lohman Test": Can the operator join 3 inputs without materializing and storing the output of 2 of them? Pipelined iterators pass; blocking sort-partition passes fail.

Key Takeaways

  • Volcano iterators stream data tuple-by-tuple in a single process via open(), next(), and close().
  • Left-deep trees minimize memory; Right-deep trees enable parallel hash table building; Bushy trees maximize cluster parallelism.
  • Standard OS LRU causes buffer thrashing on bulk scans; DSS engines use page pinning and read-ahead forecasting.
Quick Quiz
Easy: What is the main performance benefit of the Volcano iterator model?

Answer: It provides demand-driven pipelining within a single process. Operators pass tuples via fast function calls, eliminating disk I/O for intermediate query results and avoiding heavy OS process-switching (IPC).

Medium: Why do Right-Deep trees suit parallel data warehouse joins?

Answer: Because every inner child is an independent base relation leaf (typically dimension tables). The engine can scan and build all in-memory hash tables concurrently before streaming the fact table through.

2Join Techniques: DSS vs. OLTP & Scalability

Nested loops, Boustrophedonism & Richard Winter's 3,800-Year Join Analysis

OLTP Joins: Point Seeks

  • High Selectivity: Fetches 1–10 rows (e.g. WHERE id = 42).
  • Access: Traverses B-tree root-to-leaf in 2–3 disk reads.
  • Resource: Kilobytes of memory; milliseconds to finish.

DSS Joins: Analytical Scans

  • Low Selectivity: Joins millions of rows across multi-year facts.
  • Access: Bulk sequential sweeps and large partition buckets.
  • Resource: Gigabytes of buffer cache and disk scratch space.

Nested Loop Join Family & Boustrophedonism

Naive NLJ O(R × S)

For each tuple in $R$, scans entire inner $S$. Disastrous on large tables without memory caching.

Block NLJ O(R×S / M)

Loads $M - K$ pages of $R$ into memory at once, scanning $S$ once per block. Cuts disk reads of $S$ by memory capacity factor.

Index NLJ Fast if R << S

Uses pre-existing index on inner table $S$. Fast only when outer table $R$ is small and index is memory-resident.

▶ Boustrophedonism: Alternating Scan Directions

Eliminates buffer pool waste by alternating scan order so the last read pages in RAM are immediately reused:

Outer Block 1:
Page 1 → Page 2 → Page 3 → Page 4 (In RAM)
Outer Block 2:
Page 4 (Cache Hit!) ← Page 3 ← Page 2 ← Page 1

Richard Winter's Case Study: 10M Customers × 100M Transactions

Database: 125 GB (Customer = 25 GB, Txns = 100 GB). Query finds transactions > $1,000 in 1999 (4M rows qualify). Assumes 50 reads/sec:

Winter's Scalability Laws
In the 125 GB dataset above, only 540 MB (< 1%) of data actually participates in the join!
Law 1: Filter & project early to isolate the < 1% participating data without scanning full tables.
Law 2: Operate on that subset with set-oriented linear algorithms ($O(N)$ Hash or Sort-Merge).

Key Takeaways

  • Naive NLJ explodes non-linearly: a 10,000× database size jump caused a 4-billion-fold disk I/O explosion.
  • Boustrophedonism scans inner tables alternately forwards and backwards to reuse RAM pages.
  • Only < 1% of analytical data typically participates in joins—scalability requires isolating this subset early.
Quick Quiz
Easy: How does Boustrophedonism save disk I/O in Block Nested Loop joins?

Answer: By alternating the scan direction (first $1 \to N$, next $N \to 1$), the next outer block immediately reuses the final pages of the inner table currently sitting in the buffer pool, avoiding a re-read from disk.

Medium: Why did Sort-Merge Join beat Indexed NLJ in Winter's study even though both performed ~15–16M reads?

Answer: Indexed NLJ performed 4 million random disk seeks (slow head movement), whereas Sort-Merge performed 15 million sequential reads at maximum bus bandwidth.

3Sort-Merge vs. Hash Joins & Graefe Duality

External 2-pass sorting, Hybrid hash partitions, recursive asymmetry & Bloom filters

Sort-Merge Join (SMJ)

1. Sort Phase ($O(N \log N)$): Both tables sorted on join key using external merge sort.

2. Merge Phase ($O(R + S)$): Two pointers scan through in lockstep.

Sort Elimination: If inputs are already ordered (clustered index or Teradata hash ordering), SMJ runs in purely linear time $O(R + S)$!

Hash Join Family

Classic: Builds hash table of small $R$ in RAM; streams probe $S$. Pure $O(R + S)$, zero disk scratch.

Grace: Partitions both tables to disk buckets $1..k$; joins bucket pairs in RAM.

Hybrid: Keeps Partition 0 in RAM, joining immediately while Partitions $1..k-1$ spill to disk.

Replacement Selection Formula
Quicksort vs. Replacement Selection (Run Generation):
Quicksort generates sorted runs of length $= M$ (memory size).
Replacement Selection uses a priority min-heap to produce runs averaging $2M$ (twice memory size!), cutting the number of merge passes on disk in half.
Critical Asymmetry
Why Hash Join Crushes SMJ when $|R| \ll |S|$: If partitions overflow, Hash Join partitions recursively. The recursion depth depends strictly on build table $R$: $$\text{Recursion Depth} \approx \log_K(R / K)$$ The probe table $S$ never increases recursion depth! SMJ, in contrast, must sort massive table $S$ with cost proportional to $\log(S / K)$.

Graefe's Divide-and-Conquer Duality

Dimension External Sorting Hash Partitioning
Divide Phase Physical: Slices fixed $M$-page chunks. Logical: Partitions by hash key $h(k)$.
Combine Phase Logical: Compares keys to merge. Physical: Concatenates bucket files.
I/O Pattern Sequential write, Random read. Random write, Sequential read.
"Interesting Orderings" Preserved Downstream GROUP BY needs no sort. Destroyed Unpredictable hash bucket order.
▶ Bloom Filters: Early Probe Rejection

A bit-vector filter is populated during the build phase of $R$. As probe rows from $S$ arrive, keys are checked before writing to disk partitions:

Probe Row Key → Hash($k$) → Bit = 0? → DISCARD IMMEDIATELY (Lossy Semijoin, saves disk I/O!)
Probe Row Key → Hash($k$) → Bit = 1? → Write to Partition Buffer for Join Match

Key Takeaways

  • Replacement selection generates runs averaging $2M$ (twice memory size), halving external merge passes.
  • Hybrid Hash Join keeps Partition 0 in RAM, drastically reducing I/O compared to Grace Hash Join.
  • Hash Join recursion depth depends strictly on build table $R$ ($\log_K(R/K)$), giving it an immense edge when $|R| \ll |S|$.
  • Graefe Duality: Sorting divides physically and combines logically; Hashing divides logically and combines physically.
Quick Quiz
Easy: What is an "Interesting Ordering" and which join algorithm preserves it?

Answer: An interesting ordering is output data that emerges pre-sorted by a key. Sort-Merge Join preserves interesting orderings, allowing subsequent joins, ORDER BY, or GROUP BY operations to execute without a fresh sort.

Medium: Why does Hash Join outperform Sort-Merge Join when joining a 10 MB dimension with a 500 GB fact table?

Answer: The 10 MB dimension fits completely in RAM as the build table. The 500 GB fact table streams through once as the probe relation without ever being partitioned, sorted, or written to disk. Sort-Merge would be forced to sort the entire 500 GB fact table across multiple disk passes.

4Query Optimization & Cost Estimation

CBO vs. RBO, Algebraic Pushdowns, and Cardinality Estimation Formulas

Cost-Based Optimizer (CBO) Mandatory in DW

Calculates mathematical cost using catalog histograms, NDV (Number of Distinct Values), and page counts. Correctly chooses bulk sequential scans and hash joins over slow index seeks for analytical queries.

Rule-Based Optimizer (RBO) Fails in DW

Uses rigid syntax heuristics (e.g. "always use an index"). Disastrous in DW where scanning 70% of a table via index seek creates millions of slow random disk reads.

▶ Heuristic Algebraic Rewrite: Selection Pushdown
BEFORE REWRITE (Naive):
σdate='2024' ( Customers ⋈ Orders )
Joins 100M rows first, then filters! High memory and slow I/O.
AFTER PUSHDOWN (σ pushed to leaf):
Customers ⋈ ( σdate='2024' (Orders) )
Filters down to 2M rows before joining! Massively faster.

Essential Cardinality & Cost Formulas

Cartesian Product

Card(R) × Card(S)

Upper bound on size if no join condition exists.

Equijoin Size Estimate

Card(R) × Card(S) / max(V(R,A), V(S,A))

Assumes uniform distribution and containment.

PK-FK Join Size

Card(Fact ⋈ Dim) = Card(Fact)

Every foreign key matches at most 1 primary key.

External Sort I/O Cost Formula
$$\text{Cost} = 2 \times \text{NCARD}(R) \times \left(1 + \lceil \log_{M-1}(\lceil \text{NCARD}(R)/M \rceil) \rceil\right)$$ Step 1 (Run generation) reads and writes once ($2 \times \text{NCARD}$). Each merge pass with fan-in $M-1$ reads and writes once.

Key Takeaways

  • CBO uses catalog statistics ($V(R,A)$, histograms) to prevent disastrous index choices in analytical workloads.
  • Selection and projection pushdowns prune intermediate data volume before joins take place.
  • BI query tools generate complex "ugly" SQL; enterprise DW engines rely on query rewrites to unnest subqueries.
Quick Quiz
Easy: Why is Selection Pushdown always prioritized during query optimization?

Answer: It filters rows directly on the base table before the join occurs, dramatically reducing intermediate row counts and memory consumption.

Medium: Table R has 200,000 rows with V(R,A) = 10,000. Table S has 300,000 rows with V(S,A) = 30,000. Estimate the equijoin cardinality.

Answer: $\text{Card} = \frac{200,000 \times 300,000}{\max(10,000, 30,000)} = \frac{6 \times 10^{10}}{30,000} = 2,000,000 \text{ tuples.}$

Surrogate Keys vs. Natural Keys

Natural operational keys change, get reused, or conflict across source mergers. ETL assigns synthetic integer Surrogate Keys to insulate the warehouse and support Slowly Changing Dimensions (SCD 1–3).

Traditional ETL vs. Modern ELT

ETL: Transforms data in a dedicated external server before loading.
ELT (Cloud DW): Loads raw data into the warehouse first; transforms in-place using MPP compute (Snowflake, BigQuery, dbt).

Key Takeaways

  • ETL accounts for 70%–80% of data warehouse project time and labor.
  • Data Staging Areas (DSA) isolate extraction and cleaning from production OLTP and end-user DW queries.
  • Log-Based CDC is the enterprise gold standard: zero impact on OLTP and 100% accurate change/delete capture.
  • Bulk loading drops indexes, streams data via direct-path append, and rebuilds indexes in parallel.
Quick Quiz
Easy: Why are surrogate keys used instead of operational natural keys in warehouse dimension tables?

Answer: Natural keys can change, be reused, or conflict when consolidating multiple sources. Surrogate keys provide stable, integer primary keys independent of source systems and allow multiple historical versions of rows (SCD Type 2).

Medium: Why is log-based CDC superior to trigger-based CDC in production environments?

Answer: Trigger-based CDC executes synchronously inside production write transactions, degrading OLTP application throughput. Log-based CDC asynchronously reads the database's write-ahead log (WAL) out-of-band with zero overhead on production transactions.

Master Exam Practice Quiz (5 High-Yield Problems)
Question 1: Explain Goetz Graefe's Divide-and-Conquer Duality between sorting and hashing.

Answer: Sorting performs physical division (arbitrary memory-sized runs) and logical combination (key-comparison merge). Hashing performs logical division (key-based hash partitioning) and physical combination (concatenating bucket results). Sorting preserves sorted key order for downstream aggregations, while hashing destroys it.

Question 2: In Richard Winter's case study, why did a 10,000× database scale jump cause a 4-billion-fold disk I/O explosion under Naive NLJ?

Answer: In the small test database, the entire inner customer table fit inside the RAM buffer pool (0 disk I/O during inner scans). In the enterprise warehouse, neither table fit in memory. For each qualifying transaction (4M rows), the engine performed a full 25 GB disk scan of the customer table, turning cached lookups into 6 Trillion physical disk reads.

Question 3: Why does Hash Join have a structural advantage over Sort-Merge when joining a small build table R with a massive probe table S?

Answer: Because the recursive partitioning depth in Hash Join depends strictly on the build table $R$ ($\log_K(R/K)$). Massive table $S$ simply streams through as the probe input. In contrast, Sort-Merge Join must sort both tables, incurring heavy $O(S \log S)$ external merge overhead on the massive relation.

Question 4: What are the trade-offs between Trigger-Based CDC and Log-Based CDC?

Answer: Trigger-based CDC runs synchronously inside application write transactions, degrading production OLTP performance and requiring maintenance when schemas change. Log-based CDC asynchronously scrapes the database's write-ahead log (WAL) with zero overhead on production applications while still capturing 100% of hard deletes.

Question 5: Why do database engineers drop non-clustered indexes before bulk loading a large fact table?

Answer: Loading rows with indexes active causes each inserted row to search, lock, and modify B-tree index structures, creating millions of random I/O operations and page splits. Dropping indexes allows fast sequential data appending; rebuilding the index at the end allows the engine to sort keys and construct the entire B-tree in a single, parallelized pass.
