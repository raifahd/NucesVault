OLAP Implementation Techniques

1OLAP Framework & Decision Support

Why traditional tools fail and why OLAP is the answer — the case for multidimensional analytical processing

Data warehouses are built to answer strategic questions. But storing data is only half the problem — querying it efficiently and flexibly is the other half. For decades, organisations tried to use report writers, ad-hoc SQL tools, and spreadsheets for this. Each one failed in a different way. Online Analytical Processing (OLAP) is the purpose-built solution for the analytical layer of a data warehouse architecture.

Why Traditional Tools Fail

  • Report writers: Provide formatted outputs from predefined queries. They cannot drill down into lower levels of dimension hierarchies, rotate rows and columns, or provide aggregate navigation. Once a report is formatted and run, the presentation is fixed.
  • Spreadsheets: Useful for “what-if” analysis and can perform some aggregations. But cumbersome for four or more dimensions — you cannot intuitively display four-dimensional data on a two-dimensional page. Complex analyses still generate massive system overhead.
  • SQL query tools: SQL vocabulary is “ill-suited for analyzing data and exploring relationships.” Even basic comparisons are difficult. Time-series analysis, cross-dimensional calculations, and complex aggregations require intricate SQL that is error-prone and slow. Each analysis session involves numerous consecutive queries, each likely invoking full table scans, multiple joins, aggregations, groupings, and sorting.
Definition
OLAP (Online Analytical Processing): A category of software tools and system architectures that enable analysts, executives, and managers to gain useful insights from data by supporting multidimensional analysis, drill-down and roll-up within each dimension, complex mathematical calculations and formulas, fast response times for highly interactive analysis sessions, and sophisticated presentation of result sets. The term was introduced by Dr. E. F. Codd (inventor of the relational model) in his paper “Providing On-Line Analytical Processing to User Analysts.”

OLAP: Basic Virtues (Per Textbook Ch. 15)

  • Enables analysts, executives, and managers to gain useful insights
  • Can reorganise metrics along several dimensions and allow data to be viewed from different perspectives
  • Supports multidimensional analysis
  • Is able to drill down or roll up within each dimension
  • Is capable of applying mathematical formulas and calculations to measures
  • Provides fast response, facilitating “speed-of-thought” analysis
  • Complements the use of other information delivery techniques such as data mining
  • Improves the comprehension of result sets through visual presentations using graphs and charts
  • Can be implemented on the Web
  • Designed for highly interactive analysis

Practice Questions
Easy: What problem does OLAP solve that SQL query tools cannot?

Answer: SQL is “ill-suited for analyzing data and exploring relationships.” Complex analysis—time-series comparisons, cross-dimensional calculations, multi-level aggregations—requires intricate SQL that is error-prone and expensive. OLAP abstracts this complexity, presenting data as multidimensional cubes and allowing analysts to drill down, roll up, and slice data interactively at “speed of thought” without writing SQL.

Medium: Distinguish between OLTP and OLAP on four dimensions. Use exact textbook terminology.

Answer (four key distinctions):

  • Basic motivation: OLTP — “Collect and input data”; OLAP — “Provide information.”
  • Data model: OLTP — “Design for data updates”; OLAP — “Design for queries.”
  • Update frequency: OLTP — “Very frequent”; OLAP — “Generally read-only.”
  • Data granularity: OLTP — “Detail only”; OLAP — “Detail and summary.”

2Multidimensional Analysis & Cubes

Dimensions, facts, hypercubes, and how OLAP represents data for analysis

At the heart of OLAP is the idea that business data can be modelled as a multidimensional space. Instead of rows and columns, you think in terms of dimensions (the axes of analysis) and facts (the numeric measures at the intersection of dimensions).

Definition
Dimension: A business perspective or viewpoint used to analyse measures. Each dimension has a set of attributes organised in one or more hierarchies. Examples: Product (Product Name → Sub-category → Category → Department), Time (Date → Month → Quarter → Year), Store (Store Name → City → Region → Country).
Definition
Fact / Measure: A numeric, quantifiable value stored in the fact table at the intersection of dimensions. Examples: Sales Amount, Units Sold, Profit Margin. Facts are the metrics analysts want to analyse along dimensions.

The Cube Metaphor

With three dimensions (Product, Time, Store), data can be visualised as a three-dimensional cube: X-axis = Products, Y-axis = Time, Z-axis = Stores. Any single cell holds a metric — e.g., Coats sold in January at the New York store = 550. On a screen, two dimensions appear as rows and columns; the third as a “page.”

Definition
Hypercube: A general metaphor for representing multidimensional data with more than three dimensions. In a Multidimensional Domain Structure (MDS) diagram, each dimension is shown as a straight line (axis). Four, five, or six lines form a hypercube representation. Display problem solved by combining dimensions: e.g., for 4 dimensions, Page = Store, Rows = Time, Columns = Product × Metrics combined.

3OLAP Operations

Drill-down, roll-up, drill-through, drill-across, slice-and-dice, pivot — with examples

OLAP systems expose a set of analytical operations that analysts use interactively. Understanding each operation precisely — and how it differs from the others — is a recurring exam topic.

Definition
Drill-Down: Moving from a summary level to a more detailed level within a dimension hierarchy. Technically, drill-down is a further selection of fact table rows — it narrows the selection. Example: Total sales by state → sales by zip code within California.
Definition
Roll-Up: The opposite of drill-down — moving from detail to a higher summary level within a hierarchy. Technically, roll-up is an expanding of the fact table row selection. Example: Sales by zip code → sales by state.
Definition
Drill-Through: Navigating from summary-level OLAP data all the way to the underlying individual raw records in the data warehouse. Drill-through escapes the cube entirely to fetch the raw rows. Example: A spike in returns in March → drill-through to see the 47 individual return transactions.
Definition
Drill-Across: Querying data across two or more separate fact tables (subject areas) that share a common dimension (a conformed dimension). Example: Analysing sales alongside inventory levels across the same product/time dimensions — these come from two different fact tables.
Definition
Slice-and-Dice: Selecting a “slice” of the data cube by fixing the value of one or more dimensions (slice), then selecting sub-ranges along multiple remaining dimensions simultaneously (dice) to produce a smaller sub-cube. Example: Slice on Store = New York and Time = Q1-2024; then dice on product sub-category within that segment.
Definition
Pivot (Rotate): Re-orienting the presentation of data by switching dimensions on the axes. Example: Swapping rows (Time) and columns (Product) so products appear as rows and months as columns. The underlying data does not change — only the presentation.
Common Mistake
Students confuse drill-down with drill-through. Drill-down stays within the cube/dimension hierarchy (e.g., Category → Sub-Category → Product). Drill-through breaks out of the cube and retrieves raw transaction rows from the warehouse. Also, drill-across crosses separate fact tables, not dimension hierarchy levels.
Example

A Typical OLAP Session (Textbook Fig. 15-3)

Step 1: High-level summary by product line (Clothing $12.8M, Electronics $16M, Video $21.2M, ...Total $87.5M)

Step 2 — Drill-down: Break totals out by year (1998, 1999, 2000)

Step 3 — Pivot: Rotate columns to rows so Year appears as rows, Product Line as columns

Practice Questions
Medium [Past Paper 2017]: Briefly discuss drill-across and slice-and-dice. Give an example for each.

Drill-across: An OLAP operation that queries data across two or more separate fact tables sharing common (conformed) dimensions. Enables integrated analysis of different business processes. Example: A retailer has separate fact tables for Sales and Inventory. Drill-across asks: “For the top-10 selling products in Q1, what was the average inventory level?” — crossing the Sales and Inventory fact tables using common Product and Time dimensions.

Slice-and-dice: Slice = fix a dimension value to extract a “plane” of the cube. Dice = restrict ranges along multiple remaining dimensions, producing a sub-cube. Example: Slice on Store = “New York.” Then dice on Product Category = “Electronics” AND Time = “Q2” to see only Q2 Electronics sales in New York.

Hard: Explain the difference between drill-down and drill-through. When would you use each?

Drill-down navigates within the cube’s dimensional hierarchy to a lower level of granularity. Data remains within the OLAP engine’s structure (pre-computed or dynamically aggregated). Use when you want to go from “total sales by country” to “sales by city” to “sales by store” — still aggregating fact table rows at different hierarchy levels.

Drill-through escapes the cube entirely and fetches individual raw rows from the underlying data warehouse or operational sources. Used when even the lowest dimension hierarchy level is still a summary and you need to see the actual transaction records. Example: A spike in customer returns in March at Store X → drill-through to retrieve and inspect the 47 individual return transactions. ROLAP supports drill-through more easily than MOLAP.

4MOLAP vs ROLAP vs HOLAP vs DOLAP

Physical implementation architectures for OLAP — choosing the right model

Once you decide to implement OLAP in your data warehouse, you must choose a physical architecture. There are four implementation models, each reflecting a different way to store and serve multidimensional data.

Definition
MOLAP (Multidimensional OLAP): OLAP implemented using specialised proprietary multidimensional database management systems (MDBMSs / MDDBs). Data is extracted from the relational data warehouse and stored in large multidimensional arrays (hypercubes). Cubes are pre-calculated and pre-fabricated. The OLAP engine resides on a special server; data is presented from the MDDB, not from the relational warehouse directly. Architecture: 3-tier (RDBMS server → MOLAP Engine + MDDB → Desktop Client).
Definition
ROLAP (Relational OLAP): OLAP features provided against the relational database directly. Data stays as rows and columns in the relational model. An analytical server creates virtual multidimensional cubes on the fly via complex SQL — no pre-fabricated cubes stored. A semantic metadata layer maps business dimensions to relational tables. True ROLAP: (1) supports all basic OLAP features, (2) stores data relationally, (3) supports aggregation. Architecture: 3-tier (RDBMS server → Analytical Server with OLAP Services → Desktop Client).
Definition
HOLAP (Hybrid OLAP): Combines strengths of ROLAP and MOLAP. Summary/aggregate data stored in MDDBs (MOLAP-style) for fast response; detailed data remains in the relational warehouse (ROLAP-style). Users get sub-second response for summary queries, drill-through to detail from the relational warehouse.
Definition
DOLAP (Desktop OLAP): A variation of ROLAP for portability. Multidimensional datasets are created and transferred to the user’s desktop machine. Only DOLAP software needed on that machine. Local analysis on the small downloaded cube; user queries server only when additional data is needed. Also called local hypercubing. DOLAP flow: (1) User issues a query; (2) Results stored in a small local MDDB; (3) User analyses locally; (4) If more data needed, query server again.

Pro Tip
Textbook Fig. 15-18: ROLAP vs. MOLAP choice chart has two axes — Query Performance (vertical) and Complexity of Analysis (horizontal). MOLAP dominates for high performance and high complexity; ROLAP covers large data volumes and ad-hoc drill-through. On a real exam: very fast response + complex multi-dimensional queries + pre-defined aggregates → MOLAP. Very large data + ad hoc drill-through + standard tools → ROLAP.

MOLAP Implementation Considerations

  1. Lack of standardisation: Each MOLAP vendor tool has its own client interface — no universal standard (unlike SQL). Vendor lock-in is a real risk.
  2. Scalability: OLAP is generally good for handling summary data, but not good for volumes of detailed data. MDDBs grow exponentially as dimensions are added. Sparsity problem: not all cells will have data (e.g., closed-Sunday store has null sales for all Sundays) — dense storage of sparse arrays is very wasteful. MOLAP uses sparse matrix technology to manage this.
Pro Tip
Textbook: “For some ROLAP tools, the multidimensional representation of data in a STAR schema arrangement is a prerequisite.” This is why OLAP and dimensional modeling go hand-in-hand. A properly designed star schema is the foundation for efficient ROLAP.
Example

Choosing MOLAP vs. ROLAP: Three Scenarios

Scenario A — Executive Dashboard: CEO needs a pre-defined dashboard showing weekly revenue by product line, region, and quarter. Queries are always the same, data volumes are moderate, sub-second response required. → MOLAP: Pre-calculated cubes deliver sub-second response. Limited query variety means no need for ad-hoc SQL flexibility.

Scenario B — Analyst Deep Dive: Data analyst needs to explore hundreds of millions of transaction records, write complex ad-hoc queries, and drill through to individual transaction detail for auditing. → ROLAP: Data volumes too large for MDDB; drill-through to relational warehouse essential; ad-hoc SQL capability needed.

Scenario C — Mixed Use: Executives want fast dashboards; analysts want drill-through detail. → HOLAP: Summaries in MDDB for executives; detail in relational warehouse for analysts.

Practice Questions
Medium [Past Paper 2023]: What are Partitioned Cubes? When would you use them in MOLAP?

Partitioned cubes are a technique in MOLAP where the multidimensional database is physically divided into separate, smaller sub-cubes (partitions) rather than stored as one monolithic cube. Each partition covers a specific slice of data (e.g., by time period: one partition per year). Use partitioned cubes when:

  • The overall cube is too large to fit in memory or on a single server
  • You want to rebuild only the relevant partition during batch updates (not the entire cube)
  • Data access patterns are time-partitioned (users mostly query the current year — only that partition needs fast storage)
  • You want to balance storage across multiple MDDB servers
Medium [Past Paper 2017]: What is the concept of a virtual cube? When would you consider forming one?

A virtual cube is a logical view of multidimensional data that appears as a cube to the user but is not physically stored as a pre-calculated cube. The OLAP engine constructs it dynamically from underlying relational data at query time. In ROLAP, all cubes are effectively virtual cubes.

Consider a virtual cube when: (1) Data volume is too large to pre-aggregate into a physical MDDB; (2) Query patterns are too unpredictable (ad hoc) to justify pre-building specific cube structures; (3) You need to combine data from multiple source systems without copying data into a separate MDDB.

Hard: A company has 50 million customer records and needs to analyse purchase patterns across 5 dimensions. They also need drill-through to individual transactions. Which OLAP model? What limitations would the other models have?

Recommended: ROLAP (or HOLAP as a secondary option).

Why ROLAP: (1) Data volume is massive — 50M customers across multiple dimensions = potentially billions of fact rows. MDDB cannot handle this scale. (2) Drill-through to individual transaction records is inherently a relational warehouse operation. (3) 5 dimensions creates a very sparse hypercube; ROLAP handles sparsity naturally.

Why not MOLAP: (1) MDDBs have scalability limits for this data volume. (2) Lack of standardisation — vendor lock-in. (3) Drill-through requires a separate RDBMS connection anyway. (4) Sparsity problem at this scale.

Why not DOLAP: 50 million customer records cannot be downloaded to a desktop machine.

5Star Schema Design & Aggregate Fact Tables

Designing the star schema for OLAP — base fact tables, aggregate tables, cardinality estimation

The star schema is the relational design that enables ROLAP and serves as the source for MOLAP cubes. The schema design — particularly the grain of the fact table and aggregate tables — critically affects OLAP performance.

Definition
Grain (Data Granularity): The level of detail in the fact table — exactly what one row represents. A base fact table should be at the lowest natural grain of all its dimensions. Example: “One row per product, per store, per day” is lower grain than “one row per product category, per city, per month.”
Formula
Max Fact Table Rows = D₁ × D₂ × D₃ × … where each Dᵢ is the number of distinct values at the grain level of that dimension. Actual row count will be lower for sparse fact tables.
Example

Cardinality Estimation [Past Paper 2017 Style]

Given: 10,000 products (200 sub-categories, 10 categories), 100 stores (10 cities, 2 countries), 2 years (≈730 days). Grain: one row per product per store per day.

Max base fact rows: 10,000 × 100 × 730 = 730,000,000 rows

Query 1 (5 products, 3 stores, 1 month ≈30 days): 5 × 3 × 30 = 450 rows

Query 2 (1 sub-category = 10,000/200 = 50 products, 1 store, 1 month): 50 × 1 × 30 = 1,500 rows

Query 3 (1 category = 1,000 products, 1 city = 10 stores, 1 month): 1,000 × 10 × 30 = 300,000 rows

Query 4 (1 category = 1,000 products, 1 country = 100 stores, 1 year = 365 days): 1,000 × 100 × 365 = 36,500,000 rows

Definition
Aggregate Fact Table: A fact table that stores pre-computed summary data at a higher level of granularity than the base fact table. Exists alongside (never replaces) the base fact table. Dramatically reduces the number of rows that must be scanned for common query patterns.
Example

Aggregate Table Savings [Past Paper 2017 Style]

Create an aggregate table at grain: sub-category × store × month.

Aggregate table size: 200 × 100 × 24 = 480,000 rows (vs. 730M in base)

Query 2 from aggregate: 1 × 1 × 1 = 1 row (vs. 1,500 from base) ✓

Query 3 from aggregate (1 category=10 sub-cats, 1 city=10 stores, 1 month): 10 × 10 × 1 = 100 rows (vs. 300,000) ✓

Query 4 from aggregate (10 sub-cats, 100 stores, 12 months): 10 × 100 × 12 = 12,000 rows (vs. 36.5M) ✓

Star Schema Advantages for OLAP

  1. Simple join paths: “Irrespective of the complexity of the query, every query is simply executed first by selecting rows from the dimension tables using the filters based on the query parameters and then finding the corresponding fact table rows.” No intermediary maze.
  2. Easy to understand: Matches how business users think — measures in centre, dimensions around it.
  3. Optimises navigation: Drill-down = further selection of fact table rows; roll-up = expanding the selection.
  4. Performance techniques: STARjoin (high-speed, single-pass, parallelisable, multi-table join) and STARindex (specialised index on fact table foreign keys to accelerate joins).
  5. ROLAP prerequisite: “For some ROLAP tools, the multidimensional representation of data in a STAR schema arrangement is a prerequisite.”
Common Mistake
Aggregate tables do NOT replace base detail data. From Brobst (Handout 2) and textbook: “Summary values should not replace the detailed data in the decision support environment. Ad-hoc and more sophisticated queries are almost guaranteed to require the detailed data for drill-through and discovery based analysis.”
Practice Questions
Medium [Past Paper 2023 style]: Dimensions: Semester (12, 6 academic years), Course (400, 10 schools), Student (5000, 5 batches). Grain: one row per student per course per semester. Estimate base fact table and two aggregate tables.

Base fact table: 12 × 400 × 5,000 = 24,000,000 rows

Aggregate Table 1 (grain: semester × offering school × batch): 12 × 10 × 5 = 600 rows

Aggregate Table 2 (grain: semester × batch): 12 × 5 = 60 rows

Student Dimension: Star schema = 5,000 rows (batch attrs denormalised in). Snowflake = 5,000 student rows + 5 batch rows = 5,005 total. (Exam answer for “star vs. snowflake rows”: Star = 5,000; Snowflake = 5,005.)

Hard [Past Paper 2018 style]: Identify full-additive, semi-additive, and non-additive facts in a registration fact table with facts: GPA, LetterGrade, RegistrationCount (always=1).

RegistrationCount (always=1): Fully additive — can be meaningfully summed across all dimensions (e.g., total registrations by school, by semester, by batch).

GPA: Semi-additive — can be averaged (AVG) across students/courses/semesters, but cannot be meaningfully summed (SUM of GPAs has no business meaning). Additive within some dimensions but not others.

LetterGrade: Non-additive — a categorical/ordinal attribute. Cannot be aggregated with SUM or AVG in any meaningful way. You can COUNT occurrences of a specific grade (COUNT WHERE LetterGrade = ‘A’), but this is not a direct aggregation of the fact itself.

6Topic Summary & Additional Practice

Dense recap of every key definition, distinction, and formula for the morning of the exam

OLAP Implementation Techniques — Complete Key Takeaways

  • OLAP exists because report writers, SQL, and spreadsheets cannot handle multidimensional, hierarchical, speed-of-thought analysis at scale
  • Dr. E. F. Codd coined “OLAP”; core virtues: multidimensional analysis, drill-down/roll-up, complex calculations, fast response
  • Hypercube = general model for 3+ dimensional data; MDS diagrams represent each dimension as a straight line
  • Operations: Drill-down (further row selection = more detail), Roll-up (expand selection = higher summary), Drill-through (exit cube → raw rows in warehouse), Drill-across (cross multiple fact tables via conformed dimensions), Slice (fix one dimension value), Dice (restrict ranges on multiple dimensions simultaneously), Pivot (rotate display axes)
  • MOLAP: Data in proprietary MDDB (pre-built arrays); fast response; moderate data volumes; limited standardisation; sparse matrix technology; OLAP engine on special server
  • ROLAP: Data stays in relational warehouse; analytical server creates virtual cubes on-the-fly via complex SQL; handles very large volumes; easy drill-through; star schema often a prerequisite
  • HOLAP: Summaries in MDDB + detail in RDBMS = best of both worlds
  • DOLAP: Variation of ROLAP; datasets downloaded to desktop machine; local analysis; good for mobile users
  • Base fact cardinality formula: D₁ × D₂ × … × Dᵢ (product of grain-level cardinalities)
  • Aggregate fact table: Pre-summarised at coarser grain; exists alongside (never replacing) base; size = product of coarser dimension cardinalities
  • Additive types: Fully additive (SUM across all dims), Semi-additive (SUM on some dims only — e.g., GPA → use AVG), Non-additive (categorical — e.g., LetterGrade, percentages)
  • MOLAP concern 1: Lack of standardisation (vendor lock-in)
  • MOLAP concern 2: Scalability — good for summary data, not large detail volumes
  • Star schema + OLAP: Simple join paths, STARjoin + STARindex performance techniques, required prerequisite for many ROLAP tools
Additional Practice Questions
Hard [Application]: Identify each OLAP operation: (1) Manager sees total revenue by product category. (2) Clicks Electronics to see revenue by product model. (3) Changes view to show revenue by quarter instead of product. (4) Sets filter to show only European stores. (5) Clicks $2.3M to view the individual transactions.

Step 1: Initial query — high-level summary (no specific OLAP operation)

Step 2: Drill-down — from Category level to Product Model level within the Product dimension hierarchy.

Step 3: Pivot (Rotate) — switching the analysis dimension from Product to Time (quarters), re-orienting the axes.

Step 4: Slice — fixing the Store dimension to “Europe” creates a slice through the cube.

Step 5: Drill-through — exiting the cube and retrieving individual raw transaction rows from the underlying data warehouse.

Hard [Application]: Financial firm: 2M accounts, 20 transaction types, 5 years daily data (1825 days). Analysts query "Total transaction volume by type by quarter." (a) Max base fact table size? (b) Aggregate table design and size? (c) Recommended OLAP model?

(a) Base fact table max rows: 2,000,000 × 20 × 1,825 = 73 billion rows (sparse in practice)

(b) Aggregate table grain: transaction_type × quarter. Size = 20 × (5 years × 4 quarters) = 20 × 20 = 400 rows. Reduces query scan from billions to 400 rows.

(c) MOLAP (or HOLAP): Query pattern is pre-defined and narrow (always “by type by quarter”). Pre-calculating these specific aggregations in an MDDB gives sub-second response on a 400-cell cube. Since analysts never need individual detail, drill-through is unnecessary. However, the raw data volume (73B rows) is too large for MOLAP; HOLAP is most realistic: aggregate cube in MDDB for standard queries, raw data in relational warehouse for rare drill-through.
