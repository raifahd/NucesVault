High Performance DSS Database Design

1 Review of Normalization (Database 101)

Revisiting 1NF, 2NF, and 3NF before breaking the rules

Before we can start denormalizing database structures for performance in a Data Warehouse, we must first understand the rules we are breaking. A solid grasp of Third Normal Form (3NF) ensures that we denormalize deliberately as an engineering decision, rather than by accident.

First Normal Form (1NF)

To comply with 1NF, the domain of each attribute in a relation must include only atomic (simple, indivisible) values. You shouldn't have to "decode" attribute values based on other attributes, nor should you glue multiple values into a single string.

Definition
Atomic Value: A value that cannot be further subdivided without losing its fundamental meaning in the business context.
Common Violations of 1NF
  • Value "redefines" within an attribute: e.g., A status of "L" means "lapsed" if policy type is "LTD", but "free look" if policy type is "LIF".
  • Multiple domains combined: e.g., Group type containing "LGE" (Large), "MED" (Medium), but also "ASO" (Administrative Services Only). Overlapping concepts mixed into one column.
  • Repeating groups: e.g., Keeping 12 columns for Jan_Bal, Feb_Bal, etc., instead of one row per month.
Example

Fixing Repeating Groups

Instead of a single account record with 12 monthly balance columns (which takes ~2.04 GB for 10M accounts over 3 years), create one row for each month of balance figures. While this normalizes the design (taking ~9.72 GB), appending new rows is up to 10x faster than updating buckets, and SQL queries become much simpler and less error-prone to maintain.

Second Normal Form (2NF)

To comply with 2NF, every non-prime attribute must be fully functionally dependent on the entire primary key. This applies to tables with composite primary keys.

A typical violation is when attributes describe only a part of the primary key. For instance, in an `Employee_x_Project` table with PK `(SSN, Project_Id)`, storing the `Employee_Nm` or `Project_Nm` violates 2NF because `Employee_Nm` only depends on `SSN`. The fix is to split the table into fundamental entities (`Employee`, `Project`) and an associative entity.

Third Normal Form (3NF)

To comply with 3NF, the table must be in 2NF, and every non-prime attribute must be non-transitively dependent on the primary key. Essentially, attributes should depend "on the key, the whole key, and nothing but the key".

Key Takeaways

  • 1NF: Attributes must be atomic. Avoid repeating groups and overloaded meanings.
  • 2NF: No partial dependencies on a composite primary key.
  • 3NF: No transitive dependencies; non-key attributes shouldn't depend on other non-key attributes.
  • Normalization reduces storage redundancies and anomalies but might introduce complex joins.
Practice Questions
Easy: What is a repeating group and which normal form does it violate?

Answer: A repeating group occurs when multiple values for the same attribute are stored in separate columns (e.g., Q1_Sales, Q2_Sales). It violates the First Normal Form (1NF).

Medium: Why is storing "Agent Name" inside an "Agent-Office Assignment" table (where PK is Agent_ID + Office_ID + Start_Date) a violation of 2NF?

Answer: "Agent Name" depends solely on the "Agent_ID", which is only a part of the composite primary key. This is a partial dependency, violating 2NF.

2 Pre-join Denormalization

Gluing tables together to avoid performance bottlenecks

In a decision support system (DSS), we sometimes bend the rules of normalization to deliver high performance. The goal is to provide maximum performance without sacrificing flexibility, using as few resources as possible.

Pre-join denormalization takes tables that are frequently joined and "glues" them together into a single table physically. This avoids the performance impact of frequent joins during query execution.

Pro Tip
Differences in performance (when not using indexes) depend on the RDBMS join plans available:
  • Sort-Merge Join: Savings equal the overhead of sorting the data.
  • Hash Join: Savings equal the recursive partitioning overhead.
  • Nested Loop Join: Savings equal the additional I/Os related to index access.
Tradeoffs
Pre-joining usually increases storage requirements significantly. For example, pre-joining a sales header (30 bytes) with sales detail (40 bytes) across billions of records can increase the raw data size by 24% or more. Furthermore, queries that just want to count distinct sales (headers) will now require a COUNT(DISTINCT sale_id) on the detail table, which forces a costly sort operation.

Key Takeaways

  • Pre-join denormalization combines frequently joined tables into one.
  • It eliminates costly join overhead at runtime.
  • It significantly inflates storage space due to data redundancy.
  • It can degrade the performance of queries that only need to aggregate the "parent" table's data due to forced distinct sorts.
Practice Questions
Medium: What is the primary performance penalty introduced by pre-join denormalization when counting parent entities?

Answer: Because the parent data is repeated for every child record, counting the parent entities requires a COUNT(DISTINCT parent_id), which forces the database to perform a costly sort or hash operation.

3 Column Replication or Movement

A targeted alternative to full pre-joins

Instead of pre-joining entire tables, we can take just the columns that are frequently accessed via large-scale joins and replicate (or move) them into the detail table(s). This is essentially a limited form of pre-join denormalization.

Example

Healthcare Claim Detail

Moving the member_id from the claim_header table down to the claim_detail table. This adds a few extra bytes per row on the detail table, but allows many queries to avoid joining the header table altogether just to group by member.

Table Co-location

Replicating columns can also facilitate co-location of commonly joined tables. For instance, by bringing customer_id down into a deeply nested transaction table, the RDBMS can co-locate transactions on the same disk partitions as the customer, making three-table joins execute much faster.

Considerations
  • Scanning the transaction table will take longer because the rows are wider (e.g., adding 10% more bytes means full table scans take 10% longer).
  • If the replicated key changes, updates must cascade down to billions of transaction rows.
  • You must include the replicated key in the join condition to ensure the optimizer recognizes the co-location.

4 Pre-aggregation

Storing pre-computed summaries for instant access

Pre-aggregation involves taking aggregate values that are frequently used in decision-making (e.g., sums, counts, averages) and pre-computing them into physical summary tables.

This can provide massive performance advantages by avoiding the on-the-fly aggregation of billions of detailed rows. However, maintaining these aggregates introduces significant overhead.

Definition
Pre-aggregation: The process of computing and storing aggregated metrics (like monthly sales per store) in a separate table during the ETL process, rather than calculating them at query time.
Pro Tip
Standardized definitions are critical! Business users must agree on exactly what the aggregate means (e.g., does "monthly" mean accounting period, calendar month, or billing cycle?). The definition must remain stable to provide value in historical analysis.

Maintenance Strategies

You can maintain aggregates via a transactional update strategy (updating the summary row whenever a detail row arrives) or a re-build strategy (dropping and recalculating the whole summary). The cost of updating an existing aggregate row is typically 10x higher than bulk-inserting a new detail row. Thus, an aggregate table must be queried many times per day to justify its maintenance overhead.

Critical Rule
Aggregates should never replace detailed data. Summary tables enhance performance for pre-defined views, but detailed data is always required for drill-down, discovery-based, and ad-hoc analysis.

Key Takeaways

  • Pre-aggregation dramatically speeds up high-level dashboard queries.
  • Requires strict business agreement on metric definitions.
  • Maintenance (ETL) cost is high; only build aggregates that are heavily used.
  • Never delete the detailed data; summaries exist alongside details.
Practice Questions
Hard: Compare the update cost of pre-aggregated data vs normalized detail data.

Answer: Updating an existing aggregate row is highly expensive (involving read-locks, mathematical updates, and writes, often 10x more costly) compared to simply bulk-loading/appending new rows into a normalized detail table. Therefore, aggregates are best re-built in batch if the underlying data changes frequently.
