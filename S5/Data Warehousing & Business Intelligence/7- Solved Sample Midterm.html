2Q1 — Short Answer (15 marks)

Five 3-mark sub-questions covering all four mid-exam topics

Question Paper

Q1 (15 points). Give appropriate answers to the following questions very briefly:

(a) What is the main difference between a dependent data mart and an independent data mart? (3 marks)

(b) Differentiate between pre-join denormalization and column replication denormalization techniques. (3 marks)

(c) Briefly describe the following OLAP analytical operations: Drill-down, Drill-across, and Slice-and-dice. (3 marks)

(d) What is the concept of a factless fact table? Give an example. (3 marks)

(e) How does a snowflake schema differ from a star schema? Name one advantage and one disadvantage of the star schema. (3 marks)

✓ Show Worked Solution — Q1(a): Dependent vs. Independent Data Mart
Worked Solution

Dependent data mart: A data mart that receives its data from the central enterprise data warehouse. The DW is built first; the data mart draws its data from the DW. This ensures consistency — the data mart’s data is cleansed, transformed, and integrated at the DW level before being passed down. All dependent data marts in an organisation will have a consistent view of the data.

Independent data mart: A data mart built without a central enterprise data warehouse. Data is extracted directly from the operational source systems and loaded into the data mart. There is no shared, central data repository. Multiple independent data marts tend to produce inconsistent data — different marts may use different definitions, transformations, and cleansing rules, leading to “data silos” and reports that do not reconcile.

Key difference: Dependent data marts get their data from the central DW (ensuring consistency and a single version of truth); independent data marts get data directly from operational sources (cheaper to build but prone to inconsistency across the enterprise).

Reference: Ch. 2 — DW Architecture and Data Marts

✓ Show Worked Solution — Q1(b): Pre-Join vs. Column Replication Denormalization
Worked Solution

Pre-join denormalization: A physical data modeling technique that eliminates a join between two frequently joined tables by merging them into a single combined table. The join is performed once during the ETL load process, and the denormalized combined table is stored in the DSS database. This eliminates the runtime join overhead at query time, improving query performance significantly for queries that would otherwise always join the two tables.

Example: SALES and SALES_DETAIL are always joined in queries. Pre-join denormalization merges them into SALES_COMBINED, eliminating the join at query time.

Column replication (column movement) denormalization: A technique where selected columns from a parent table are copied (replicated) into a child table to avoid a join for queries that only need those specific columns. Unlike pre-join denormalization, the full parent table is not merged — only the most frequently needed columns are replicated.

Example: A query always joins PRODUCT to SALES_DETAIL just to get PRODUCT_CATEGORY. Column replication adds PRODUCT_CATEGORY as a column directly in SALES_DETAIL, eliminating the join for that query.

Key difference: Pre-join merges entire tables; column replication copies specific columns from a parent into a child table. Column replication is less extreme and produces a smaller storage overhead.

Reference: Handout 2 — Designing High Performance DSS Databases

✓ Show Worked Solution — Q1(c): Drill-Down, Drill-Across, Slice-and-Dice
Worked Solution

Drill-down: Moving from a higher summary level to a more detailed level within a dimension hierarchy. Technically, drill-down is a further selection of fact table rows — narrowing the result set to more granular data. Example: From total sales by country → total sales by city → total sales by individual store.

Drill-across: Querying data across two or more separate fact tables (different business process subject areas) that share common conformed dimensions. Enables integrated multi-subject analysis. Example: Analysing Sales data alongside Inventory data across the same Product and Time dimensions — these come from two separate fact tables but the conformed dimensions allow cross-comparison.

Slice-and-dice: Selecting a “slice” of the data cube by fixing the value of one dimension (Slice), then restricting ranges along multiple other dimensions simultaneously to produce a smaller sub-cube (Dice). Example: Slice on Store = “New York” (fix the Store dimension), then dice on Product Category = “Electronics” AND Time = “Q2 2024” to produce a targeted sub-cube of New York Electronics sales in Q2 2024.

Reference: Ch. 15 — OLAP in the Data Warehouse

✓ Show Worked Solution — Q1(d): Factless Fact Table
Worked Solution

A factless fact table is a fact table that does not contain any numeric measures. It consists only of the concatenated primary key (foreign keys to dimension tables). The presence of a row in the factless fact table represents that a business event occurred, or that a particular relationship/coverage exists.

Factless fact tables arise in two situations:

  1. Event tracking: When the business wants to record that an event happened, but there is no natural numeric measurement. Example: A student attendance fact table with keys for Student, Course, Date, Room, and Professor — each row records that a student attended that course. Attendance could be coded as “1” in every row, but that is redundant; the row’s presence is the fact.
  2. Coverage tracking: Recording which combinations of dimensions are “eligible” without a transaction. Example: A promotion coverage fact table recording which products are covered by which promotions in which stores — tracking possibility, not actuals.

Reference: Ch. 10 — Principles of Dimensional Modeling

✓ Show Worked Solution — Q1(e): Snowflake vs. Star Schema
Worked Solution

Snowflake schema vs. star schema: In a star schema, dimension tables are denormalised — all attributes including all hierarchy levels are stored flat in a single table per dimension. In a snowflake schema, dimension tables are normalised — hierarchy levels are broken out into separate sub-dimension tables connected by foreign keys, creating a snowflake-like structure. The fact table still sits at the centre, but dimension tables now have their own child tables.

Example: In a star schema, the Product dimension has one table with (ProductKey, ProductName, SubCategory, Category, Department). In a snowflake, this becomes: Product → SubCategory → Category → Department as four separate tables.

One advantage of the star schema: Simpler join paths — every dimension table has a direct, single-hop relationship to the fact table. Queries are faster because they involve fewer joins.

One disadvantage of the star schema: Data redundancy — the denormalised dimension tables repeat higher-level hierarchy values for every lower-level member (e.g., the same Category and Department description is stored in every product row in that category), increasing storage cost and requiring ETL to ensure consistency.

Reference: Ch. 10, 11 — Dimensional Modeling; Ch. 15 — OLAP

✓ Show Worked Solution — Q2(b): Additive Classification
Worked Solution
FactTypeJustification
AdmissionCount (always=1) Fully Additive Can be meaningfully summed across all dimensions. SUM gives total number of admissions by any combination of patient, diagnosis, doctor, or time period. No dimension restriction on SUM.
TreatmentCost Fully Additive Can be meaningfully summed across all dimensions. Total treatment cost by department, by diagnosis category, by year, or any combination is a valid and meaningful business metric.
LengthOfStay (days) Semi-Additive Can be summed across patients (total patient-days in a department), but averaging (AVG) is more meaningful than summing for most analytical purposes (average stay by diagnosis). Importantly, summing across time periods may be misleading — if the same patient has multiple admissions, adding their stays across time is valid, but averaging gives more insight. Classify as semi-additive because it cannot be aggregated the same way across all dimension combinations without careful consideration.
Note
Some instructors classify LengthOfStay as fully additive (you can meaningfully sum total patient-days). The key point for the exam: it is not non-additive (it is numeric) and Query 1 asks for average (AVG), suggesting semi-additive is the safer answer. Always state your justification clearly.

5Q4 — Pre-Join Denormalization (7 marks)

Calculate storage cost of pre-join denormalization — the quantitative design question

Question Paper

Q4 (7 points). Consider the following normalized data structure:

ORDERS(OrderID, CustomerID, OrderDate, StoreID, ...)
ORDER_DETAIL(DetailID, OrderID, ProductID, Quantity, UnitPrice, ...)

Assumptions:

  • There are 1 million orders in ORDERS and 8 million rows in ORDER_DETAIL
  • Record length of both ORDERS and ORDER_DETAIL is the same: 120 bytes
  • Each column in both tables (including PK/FK columns) is the same size: 12 bytes

Most frequent query: SELECT * FROM ORDERS O JOIN ORDER_DETAIL D ON O.OrderID = D.OrderID

(a) Identify the performance problem with this query and explain why pre-join denormalization would help. (2 marks)

(b) Show the denormalized data structure (which columns go where). (2 marks)

(c) Evaluate the additional storage cost (as a percentage) for the denormalized data structure compared to the original two-table structure. (3 marks)

✓ Show Worked Solution — Q4(a): Performance Problem
Worked Solution

Performance problem: The query joins 1 million ORDERS rows to 8 million ORDER_DETAIL rows on OrderID. In a DSS/DW environment, this join is performed at query time every time the query runs. This requires:

  • Scanning all 1,000,000 rows of ORDERS
  • Scanning all 8,000,000 rows of ORDER_DETAIL
  • Performing a join operation to match rows on OrderID
  • Sorting and merging the results

For a DSS environment where this is a frequently run analytical query, this join overhead significantly increases query response time, undermining the “speed-of-thought” analytical requirement.

Why pre-join denormalization helps: Pre-join denormalization performs the join once during the ETL load process and stores the combined (joined) result as a single flat table. At query time, no join is needed — the query simply scans the single flat table. This eliminates all join overhead for this frequent query pattern.

✓ Show Worked Solution — Q4(b): Denormalized Structure
Worked Solution

Pre-join denormalization approach: Merge ORDERS into ORDER_DETAIL. For each row in ORDER_DETAIL, the corresponding ORDERS attributes are copied in. The resulting ORDERS_COMBINED table contains:

ORDERS_COMBINED(
  -- From ORDER_DETAIL:
  DetailID, OrderID, ProductID, Quantity, UnitPrice, [other ORDER_DETAIL columns]
  -- From ORDERS (columns replicated for each ORDER_DETAIL row):
  CustomerID, OrderDate, StoreID, [other ORDERS columns]
)

Row count: 8,000,000 rows (same as ORDER_DETAIL -- one ORDERS row expands
           into all its matching ORDER_DETAIL rows; the average order has
           8,000,000 / 1,000,000 = 8 detail lines per order)

Note: The ORDERS table’s primary key (OrderID) is still present as a column in ORDERS_COMBINED but is no longer a FK reference — its data is embedded directly in each row.

✓ Show Worked Solution — Q4(c): Additional Storage Cost Calculation
Worked Solution

Step 1: Determine number of columns in each table.

Record length = 120 bytes; each column = 12 bytes. So columns per table = 120 / 12 = 10 columns per table.

Step 2: Calculate original storage.

  • ORDERS: 1,000,000 rows × 120 bytes = 120,000,000 bytes (120 MB)
  • ORDER_DETAIL: 8,000,000 rows × 120 bytes = 960,000,000 bytes (960 MB)
  • Total original: 120,000,000 + 960,000,000 = 1,080,000,000 bytes (1,080 MB)

Step 3: Calculate denormalized table storage.

ORDERS_COMBINED merges ORDERS columns into ORDER_DETAIL rows. The merged table has ORDER_DETAIL’s columns plus ORDERS’ non-redundant columns.

Note: OrderID is already in ORDER_DETAIL (as the FK), so we do not need to add it again from ORDERS. Therefore: additional columns from ORDERS = 10 - 1 (OrderID already present) = 9 new columns replicated.

New record length = (10 + 9) columns × 12 bytes = 19 × 12 = 228 bytes per row

ORDERS_COMBINED: 8,000,000 rows × 228 bytes = 1,824,000,000 bytes

Step 4: Calculate storage overhead.

Denormalized total = 1,824,000,000 bytes (ORDERS_COMBINED replaces both original tables for this query pattern)

Additional storage = 1,824,000,000 — 1,080,000,000 = 744,000,000 bytes

Additional storage % = (744,000,000 / 1,080,000,000) × 100 = 68.89% ≈ 69% additional storage

Pro Tip
Some variations of this question (like Past Paper 2017 Q1) ask you to keep the original tables alongside the denormalized one (for queries that don’t need the join). In that case: total storage = original tables + denormalized table = 1,080 MB + 1,824 MB — but additional cost = 1,824 MB. Read the question carefully to know if both are kept or if the originals are replaced.

The exact Past Paper 2017 Q1 setup had: 2M sales, 20M details, 100 bytes each, 10 bytes/column = 10 columns each. OrderID column already in DETAIL = 9 new columns from SALES. New record = 190 bytes. New table = 20M × 190 = 3,800 MB. Original = 2M × 100 + 20M × 100 = 2,200 MB. Additional = (3,800 - 2,200) / 2,200 × 100 = 72.7% additional.

Final 5-Minute Review Drill
Quick fire: What formula gives the maximum rows in a base fact table?

Max rows = D₁ × D₂ × … × Dᵢ (product of the cardinalities at the grain level of each dimension)

Quick fire: What is the difference between MOLAP and ROLAP in one sentence each?

MOLAP: Data is stored in proprietary multidimensional arrays (MDDBs); pre-calculated cubes are served from a special OLAP server, delivering fast response for complex analysis.

ROLAP: Data remains in relational tables in the warehouse; an analytical server creates virtual cubes on the fly by translating user queries into complex SQL directed at the relational DBMS.

Quick fire: What are the three SCD types in one line each?

Type 1: Overwrite — no history kept; for error corrections.

Type 2: New row + new surrogate key — full history kept; for real business events.

Type 3: New column (“old value”) — one prior value kept; for one-time reclassifications.

Quick fire: What is a surrogate key and why do we use it?

A surrogate key is a system-generated sequence number used as the primary key of a dimension table. It has no built-in meaning. We use it because natural/production keys often have embedded meanings that change over time, or they get reused for different entities — both of which corrupt historical analysis. Surrogate keys remain stable regardless of operational system changes.

Quick fire: Fact table is "deep"; dimension table is "wide." What does this mean?

Fact table is “deep”: Very many rows (billions), few columns (just FK columns + numeric measures).

Dimension table is “wide”: Very many columns (all hierarchy levels and descriptive attributes, potentially 100+), relatively few rows (thousands to millions).
