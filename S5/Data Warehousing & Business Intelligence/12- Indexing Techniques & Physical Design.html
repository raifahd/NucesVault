Indexing Techniques & Physical Design

1Indexing Fundamentals: B-Tree vs. Hash Indexing

Disk I/O minimization, search mechanics, and range query trade-offs.

Disk I/O is the slowest operation in database systems. The goal of indexing is simple: reduce the number of block I/Os required to find records.

Definition
Database Index: An auxiliary data structure mapping search-key values to physical row addresses (ROWIDs).
Library Analogy: Like a library card catalog that points directly to a shelf rather than walking through every aisle (full table scan).

OLTP vs. Data Warehouse Workloads

  • OLTP: High concurrency, tiny lookups ($S \approx 0.000005\%$), single-row inserts/updates $\rightarrow$ B-Trees excel.
  • Data Warehouse (DSS): Large analytical scans across thousands/millions of rows. Unclustered single indexes often perform worse than a full table scan due to random I/O. Bulk loading also suffers heavy write amplification from index maintenance.

B-Tree Indexing ($O(\log n)$)

  • Balanced hierarchical tree with Root, Branch, and Leaf nodes.
  • Leaf nodes store sorted (Key, ROWID) pairs and are connected via a doubly-linked list.
  • Strength: Excels at point lookups, range queries (BETWEEN, >, <), prefix matches (LIKE 'A%'), and sorted output (ORDER BY).
Example

B-Tree Leaf Range Scan

For WHERE order_date BETWEEN '2024-01-01' AND '2024-01-31':

1. Traverse Root → Leaf for '2024-01-01' in O(log n) steps.
2. Follow doubly-linked leaf pointers sequentially until '2024-01-31'.
3. Zero tree re-traversals needed!
Pro Tip: Range Query Optimization
B-Trees navigate root-to-leaf once, then walk horizontally across leaf blocks. Hash indexes cannot do this and force a full table scan on any range predicate.

Hash Indexing ($O(1)$)

  • Passes key through a hash function: $\text{Hash}(Key) \rightarrow \text{Bucket ID} \rightarrow \text{ROWIDs}$.
  • Keys are not stored in sorted order, but ROWIDs within each bucket are sorted for sequential disk reading.
  • Strength: Instant single-I/O point lookup for exact equality (WHERE id = 1234).
Critical Exam Trap: Hash Range Queries
Hash indexes fail completely on range queries, inequalities, and sorting (>, <, BETWEEN, ORDER BY). Contiguous keys hash to random buckets. Any range predicate triggers a full table scan!
Feature B-Tree Index Hash Index
Complexity $O(\log n)$ block traversals $O(1)$ constant time
Key Ordering Strictly sorted throughout Unsorted / pseudo-random
Point Lookups (=) Fast ($2-4$ block reads) Extremely fast ($1$ block read)
Range Queries & Sorting Native and efficient Unsupported (triggers full scan)
Practice Questions
Easy: How do B-tree and Hash indexes differ regarding key ordering?

Answer: B-Trees store keys in strict sorted order across all levels with linked leaves. Hash indexes store keys in unsorted, pseudo-random order determined by hash calculations (though ROWIDs inside buckets are sorted).

Medium: Why does a query with BETWEEN '2024-01-01' AND '2024-01-31' fail to use a Hash index?

Answer: Hashing randomizes key locations across storage buckets; contiguous dates do not hash to contiguous buckets. A hash index cannot evaluate inequalities or ranges, forcing the optimizer to use a full table scan.

Hard: When would a Hash index be preferred over a B-Tree in a DW fact table?

Answer: Only when access is strictly limited to exact equality point lookups or equi-joins on a surrogate key, where $O(1)$ single-I/O access beats B-Tree's $O(\log n)$ multi-level traversal.

Key Takeaways: Topic 1

  • B-Trees maintain sorted order and linked leaves—ideal for range queries, point lookups, and sorting.
  • Hash indexes provide $O(1)$ direct point lookups but fail completely on range queries.
  • In DW, single traditional indexes rarely beat sequential scans due to block clustering.

2Primary & Secondary Indexing: Teradata MPP

UPI, NUPI, USI, and NUSI mechanics, AMP co-location, and data skew traps.

In MPP systems (e.g. Teradata), data is partitioned across parallel processors called AMPs (Access Module Processors).

Definition
Primary Index (PI): The column(s) hashed to determine which physical AMP and disk block stores each row. Only one PI per table.

1. Primary Index: UPI vs. NUPI

  • UPI (Unique Primary Index): Guarantees uniqueness. Retrieval is a guaranteed 1-AMP, 1-I/O operation.
  • NUPI (Non-Unique Primary Index): Duplicate keys hash to the exact same AMP. 1-AMP operation (1 I/O if all duplicate rows fit in one block).
High-Yield Exam Concept: Why PI is "FREE"
Teradata uses a hash-based file system. The Primary Index is the physical placement mechanism. It requires 0 bytes of extra storage and 0 index-build time.
Common Trap: Data Skew on NUPI
Never choose a low-cardinality column (e.g. status or country) as NUPI. In a 100-AMP cluster, a column with 4 values causes 4 AMPs to run out of spool space while 96 AMPs sit idle at 0% CPU!
Case Study

Financial Transaction Table Dilemma

CREATE TABLE tx (tx_id, account_id, tx_amt, tx_dt, tx_cd) PRIMARY INDEX (???);
  • If queries filter by account: Choose account_id as NUPI for 1-AMP lookups.
  • If account activity is skewed: (e.g., corporate accounts with 100,000+ txns), account_id creates hot AMPs. Solution: Choose tx_id as UPI (100% even row distribution) and add a secondary index on account_id.

2. Secondary Index: USI vs. NUSI

Secondary indexes are stored in separate subtables. They are NOT free (consume storage and slow down ETL loads). Up to 32 per table.

  • NUSI (Non-Unique Secondary Index):
    • Co-located: Index entries reside on the same AMP as the base row.
    • All-AMP Parallel: Every AMP scans its local NUSI in parallel (zero inter-AMP network traffic).
    • Rule of thumb: Only use NUSI if Selected Rows < Total Table Blocks.
  • USI (Unique Secondary Index):
    • 2-AMP Operation: Partitioned by USI key $\rightarrow$ AMP 1 reads USI subtable to get ROWID $\rightarrow$ sends BYNET message to AMP 2 holding base row.
    • Use Case: Unique point lookups, or eliminating all-AMP join spool redistribution (e.g., joining order_header with order_detail).
Index Type Storage AMPs Involved Co-located? Primary Use Case
UPI Free (0 B) 1 AMP (1 I/O) Yes (Is base data) Primary key, perfect uniform row distribution
NUPI Free (0 B) 1 AMP (1 I/O if 1 block) Yes (Is base data) Frequent join/retrieval column (check for skew!)
USI Subtable 2 AMPs (Cross-BYNET) No (Hashed by USI) Alternate unique keys, eliminating join spool redistribution
NUSI Subtable All AMPs parallel Yes (Same AMP) High selectivity filters (Selected Rows < Blocks)
Practice Questions
Easy: Why is a Teradata Primary Index considered "free"?

Answer: Teradata uses a hash-based file system where the Primary Index defines row placement on disk directly. No auxiliary subtable or separate index tree is created, meaning 0 additional storage and 0 index build time.

Medium: Contrast how NUSI and USI execute across AMPs.

Answer: A NUSI is co-located on the same AMP as the base data; all AMPs scan their local subtable in parallel (1-AMP per row, zero network hop). A USI is partitioned by the USI key, requiring a 2-AMP operation (AMP 1 reads USI subtable, sends BYNET message to AMP 2 to fetch the base row).

Hard: Why does defining a USI on order_header(order_id) speed up joins with order_detail(PI: order_id) when order_header has PI customer_id?

Answer: Since tables have different PIs, joining them normally requires redistributing intermediate spool across all AMPs. The USI subtable is partitioned on order_id, matching order_detail's partitioning and allowing a direct join without expensive all-AMP spool redistribution.

Key Takeaways: Topic 2

  • UPI guarantees 1-AMP, 1-I/O access with zero storage cost.
  • NUPI places duplicate keys on the same AMP—watch out for hot AMP data skew.
  • NUSI is co-located and executes in parallel across all AMPs; use only if selected rows < table blocks.
  • USI is a 2-AMP cross-network operation that prevents all-AMP scans and join spool copying.

3Selectivity Math & Break-Even Analysis

The 20M customer benchmark, break-even selectivity (<2%), and multi-index combining.

Definition
Selectivity ($S$): Ratio of matching rows to total table rows: $S = \frac{\text{Rows Selected}}{\text{Total Rows}}$. (Lower $S$ = higher filtering power).

The 20M Customer Benchmark

Demographics & Block Calculations
• $N = 20,000,000 \text{ rows}$ | Row $= 128 \text{ B}$ | Block $= 64 \text{ KB}$ | ROWID $= 8 \text{ B}$
• Rows per Block: $\lfloor 65,536 / 128 \rfloor = \mathbf{512 \text{ rows/block}}$
• Total Blocks ($B_{total}$): $\lceil 20,000,000 / 512 \rceil = \mathbf{39,063 \text{ blocks}}$
• RIDs per Block: $\lfloor 65,536 / 8 \rfloor = \mathbf{8,192 \text{ RIDs/block}}$

Full Scan vs. Single Index (4% Selectivity)

  • Full Table Scan: Always reads exactly $\mathbf{39,063 \text{ blocks}}$ (constant cost, unaffected by query demographics).
  • Single Index on 4% Selectivity ($800,000 \text{ rows}$):
    • Index RID blocks to read: $800,000 / 8,192 = \mathbf{99 \text{ blocks}}$.
    • Base table blocks touched: $\frac{800,000 \text{ rows}}{39,063 \text{ blocks}} \approx 20.5 \text{ rows/block} \rightarrow$ every single block contains matching rows!
    • Total I/O $= 39,063 + 99 = \mathbf{39,162 \text{ I/Os}}$ (Worse than full table scan!).
Rule of Thumb: Break-Even Selectivity
An unclustered single index is justified ONLY when $\text{Selected Rows} < B_{total}$. For typical tables, break-even selectivity is strictly $S < 2\%$. Single indexes on DW attributes ($S = 5\%-20\%$) always degrade performance!

Solution: Combining Multiple Indexes (RID List ANDing)

Example

4 Combined Predicates

State (12%) $\times$ Education (4%) $\times$ Occupation (6%) $\times$ Hobby (5%):

Combined S = 0.12 * 0.04 * 0.06 * 0.05 = 0.00144% → 288 matching rows.
Index RID Blocks: State(297) + Edu(99) + Occ(149) + Hobby(124) = 669 I/Os.
Base Table Blocks for 288 rows: ≤ 288 I/Os.
Total I/O = 669 + 288 = 957 I/Os (vs. 39,063 for scan → 40x speedup!).
Super-Optimization: Index-Only Reads
If a query only counts rows (SELECT COUNT(*) ...), base table reads $= 0$. Total I/O drops to just **669 I/Os**!
Access Method Index I/O Base Table I/O Total I/O Verdict
Full Table Scan 0 39,063 39,063 Baseline constant
Single Index (4% S) 99 39,063 39,162 Slower than scan (+99 I/Os)
4 Combined Indexes 669 288 957 40x Faster than scan
Index-Only Read (COUNT) 669 0 669 58x Faster (Zero base reads)
Practice Questions
Easy: What is the typical break-even selectivity threshold for single unclustered B-tree indexes?

Answer: Less than 2% ($S < 2\%$). Above 2%, unclustered indexes touch nearly every base block while adding index-read overhead.

Medium: A table has 10M rows of 256 bytes with 64KB blocks. How many rows can a query select before a single index becomes inefficient?

Answer: Rows/block $= 65,536 / 256 = 256$. Total blocks $= 10,000,000 / 256 = 39,063$. An index is justified only when selected rows < total blocks, meaning fewer than 39,063 rows ($S < 0.39\%$).

Hard: Why does increasing row width (e.g. 128B to 512B) increase break-even selectivity percentage?

Answer: Fewer rows fit per block, distributing the table over more total blocks. This increases the probability that blocks will contain zero matching rows, allowing indexed access to remain competitive at higher selectivity percentages.

Key Takeaways: Topic 3

  • Full table scan I/O is constant ($B_{total}$); query demographics do not affect it.
  • Single unclustered indexes fail in DW because $S > 2\%$ touches virtually every base block.
  • Combining multiple low-selectivity indexes via RID list ANDing delivers 40x+ I/O reductions.
  • Index-only reads bypass the base table completely for aggregation queries.

4Advanced Indexing: Bitmaps, Composite & Covered

Static vs. dynamic bitmaps, false positive resolution, and the leading column rule.

Definition
Bitmap Index: Uses raw bit vectors where bit $n = 1$ if row $n$ matches a specific attribute value. Built for low-cardinality attributes and fast CPU bitwise logic.

1. Static Bitmap Indexes

  • One bitmap per distinct value; length = total table rows.
  • Storage Break-Even: $\approx \mathbf{64 \text{ distinct values}}$ uncompressed ($64 \times 1\text{ bit} = 64\text{ bits} = 8\text{-byte RID}$). With compression (WAH/Roaring), breaks even at thousands of values.
  • Performance: 4-predicate query scan takes only $\mathbf{240 \text{ I/Os}}$ (vs. 669 for RID lists $\rightarrow$ 2.8x faster).
  • Limitation: Poor for OLTP updates/deletes (requires shifting bit positions). Great for read-only DW append loads.

2. Dynamic Bitmap Indexes

  • Constructed in RAM on-the-fly during query execution from index scans to avoid RID sorting.
  • $(n-1)$ worst-selectivity indexes are hashed into RAM bitmaps and ANDed; best-selectivity index probes the result.
Exam Trap: Dynamic Bitmap False Positives
Hash collisions can cause two disparate rows to set the same bit position, falsely signaling a match.
Resolution: The RDBMS always re-validates predicates against the actual base row after fetching it, discarding false positives with zero data corruption.

3. Composite & Covered Indexes

  • Composite Index: Built on multiple columns: (col1, col2, col3).
    • The Leading Column Rule: The query WHERE clause must include the leading column. Omitting it forces an expensive Full Index Scan (2,500 I/Os vs 1 I/O)!
  • Covered Index: Contains all columns requested by a query (using INCLUDE for payload metrics).
    • Zero base table reads. Optimizers can join covered indexes directly to other tables without touching base data!
  • Clustered Index: Physically orders table rows on disk (max 1 per table). Reduces I/O from 39,162 to 1,662 I/Os for 4% selectivity queries.
Pro Tip: Covered Index Joins
When a query joins two tables and selects only columns present in a Covered Index, the optimizer joins the index directly, bypassing both base tables completely.
Example

Covered Index with INCLUDE Clause

CREATE UNIQUE INDEX acct_cov ON account (account_id, open_dt) 
INCLUDE (balance_amt);

-- Evaluated 100% out of the index without touching the account base table:
SELECT balance_amt FROM account WHERE account_id = 9021 AND open_dt > '2024-01-01';
Index Type Storage Update Cost Sweet Spot Key Benefit
Static Bitmap Disk Very High Low cardinality (< 64 unique) CPU bitwise AND/OR/NOT registers
Dynamic Bitmap RAM None (ephemeral) Runtime multi-index query Avoids expensive RID-list sorting
Composite B-Tree Disk Moderate Multiple co-queried columns 1-I/O tuple lookup (Leading column required!)
Covered Index Disk High (wide leaves) High-frequency queries Eliminates base table reads completely
Practice Questions
Easy: At what distinct value threshold does an uncompressed static bitmap break even with an 8-byte RID index?

Answer: Exactly 64 distinct values ($64 \times 1\text{ bit} = 64\text{ bits} = 8\text{ bytes}$).

Medium: What causes false positives in dynamic bitmaps and how does the engine prevent incorrect query results?

Answer: Hash collisions map different rows to the same bit position. The engine prevents incorrect results by re-evaluating all query predicates against the actual base row fetched from disk.

Hard: An index exists on (region, year, product_id). Why is WHERE year = 2024 slow while WHERE region = 'US' AND year = 2024 is fast?

Answer: The Leading Column Rule. The tree is sorted primarily by region. Omitting region prevents hierarchical navigation, forcing a full index scan across all leaf blocks.

Key Takeaways: Topic 4

  • Static bitmaps excel on low-cardinality attributes; break even at 64 unique values (thousands compressed).
  • Dynamic bitmaps combine traditional indexes in RAM; false positives are eliminated via base-row re-validation.
  • Composite indexes require the leading column in the WHERE clause to avoid full index scans.
  • Covered indexes eliminate base table I/O completely and support direct index-to-index joins.

5Physical Storage & Ponniah Chapter 18

The 7 design steps, PCTFREE/PCTUSED tuning, fact vs. dimension indexing, and RI suspension.

Definition
Physical Database Design: Translating the logical dimensional model into storage parameters, file structures, and indexing strategies optimized for hardware and query response times.

The 7-Step Physical Design Process

  1. Develop Standards: Strict naming conventions for tables, columns, indexes, and partitions.
  2. Create Aggregates Plan: Pre-calculate summaries at key hierarchy levels (80/20 rule).
  3. Determine Partitioning Scheme: Horizontal (by date) and vertical (wide dimensions).
  4. Establish Clustering Options: Physically co-locate related records for sequential prefetch.
  5. Prepare Indexing Strategy: Fact concatenated keys vs. dimension bitmap indexes.
  6. Assign Storage Structures: RAID levels, tablespaces, and file striping.
  7. Complete Physical Model: DDL, block parameters (PCTFREE, PCTUSED), and initialization settings.

Block Parameters: PCTFREE vs. PCTUSED

Parameter OLTP Setting Data Warehouse (DW) Setting & Rationale
PCTFREE High (20%–30%) Set AS LOW AS POSSIBLE (0%–5%)!
DW data is read-only / bulk-loaded. Setting it high wastes massive disk space and forces scans to read thousands of empty blocks.
PCTUSED Moderate (40%–50%) Set AS HIGH AS POSSIBLE (80%–90%)!
Virtually no deletes occur. Pack blocks to maximum capacity to maximize throughput during sequential table scans.
Exam Tip: The 3 "Never" Rules of DW Indexing
1. NEVER build bitmapped indexes on Fact tables (high cardinality breaks them).
2. NEVER set PCTFREE high (> 5%) in DW repositories (wastes massive storage).
3. NEVER leave referential integrity checks enabled during bulk ETL loading.

Fact vs. Dimension Indexing Strategy

  • Fact Tables:
    • Concatenated B-Tree index on the composite primary key.
    • Place the most heavily filtered dimension key first (leading column rule).
    • Index metric columns (e.g. amount) only if frequent range queries filter on them.
  • Dimension Tables:
    • Unique B-Tree on the surrogate primary key.
    • Static Bitmap Indexes on low-cardinality attributes (gender, status, region).
    • Composite B-Trees on drill-down hierarchies: (country, state, city).
Pro Tip: Disable Referential Integrity (RI) During Bulk Load
Data is already cleansed and verified in the staging area. Checking RI row-by-row during bulk load is redundant and causes severe performance penalties. Suspend RI during load!
Example

Data Array Denormalization for Time-Series

Store 12 monthly balance columns inside one customer row (intentional 1NF violation):

CREATE TABLE cust_monthly_bal (
    cust_id   DECIMAL(10,0) PRIMARY KEY,
    year_num  SMALLINT NOT NULL,
    m_bal     DECIMAL(15,2)[12] -- bal_01 through bal_12
);

Slashes row count by 12x, eliminates 11 self-joins, and answers annual trend queries in 1 read!

Practice Questions
Easy: Why should PCTFREE be set to 0–5% in a data warehouse?

Answer: DW records are historical and read-only; they do not expand through in-place updates. High PCTFREE leaves empty space in every block, bloating table size and slowing full scans.

Medium: Why should referential integrity (RI) checks be suspended during DW loading?

Answer: Relational integrity is already verified in the Data Staging Area during ETL transformation. Runtime RI verification during bulk load adds massive locking and CPU overhead.

Hard: How should the concatenated primary key on a Fact table be ordered among Store, Date, and Product?

Answer: Place the most frequently filtered dimension first (typically DateKey or ProductKey). This satisfies the Leading Column Rule, allowing the B-Tree to navigate directly for time-range and product queries.

Key Takeaways: Topic 5

  • The 7-step physical design process bridges logical schemas and physical hardware.
  • Set PCTFREE low (0-5%) and PCTUSED high (80-90%) to eliminate wasted space.
  • Fact tables use concatenated B-Trees with heavily filtered dimensions first; never use bitmaps on facts.
  • Dimension tables use unique B-Trees on surrogate keys and bitmaps on low-selectivity attributes.
  • Suspend RI checking during bulk ETL loading.

Exam Tip: Calculation Steps
1. $\text{Rows/Block} = \lfloor \text{BlockSize} / \text{RowWidth} \rfloor$
2. $\text{Total Blocks} = \lceil \text{TotalRows} / \text{RowsPerBlock} \rceil$
3. $\text{Selected Rows} = \text{TotalRows} \times S$
4. If $\text{Selected Rows} \ge \text{Total Blocks}$, base table I/O $=$ **Total Blocks**!
Common Student Mistake in Calculations
Do not assume base table I/Os equal matching rows. If $800,000$ rows match across $39,063$ blocks, every block contains matching rows, so base I/O is all $39,063$ blocks!
Worked Problem

Full Scan vs. Single Index

Table: 5M rows, 256B rows, 32KB block, 8B RID, Selectivity $S = 3\%$.

1. Rows/Block = 32,768 / 256 = 128 rows/block.
2. Total Blocks = 5,000,000 / 128 = 39,063 blocks (Full scan = 39,063 I/Os).
3. Selected Rows = 5,000,000 * 0.03 = 150,000 rows.
4. RIDs/Block = 32,768 / 8 = 4,096 RIDs/block.
5. Index Blocks = 150,000 / 4,096 = 37 blocks.
6. Base Blocks = 150,000 / 39,063 = ~3.8 rows/block → All 39,063 blocks touched!
Total Index I/O = 39,063 + 37 = 39,100 I/Os. Full scan (39,063) WINS!

High-Yield Exam MCQs

Q1. Why is a Primary Index (PI) considered "free" in Teradata?
  • A) It is cached in RAM buffer pool
  • ✓ B) Teradata uses a hash-based file system where the PI defines row placement on disk without creating a subtable
  • C) Teradata builds the index asynchronously in the background
  • D) It uses compressed B-Tree leaves
Explanation: Row addresses are derived mathematically from hashing the PI column directly. No secondary index structure is constructed.
Q2. Accessing a row via a Teradata Unique Secondary Index (USI) requires:
  • A) A single-AMP operation because USI is co-located with base data
  • ✓ B) A two-AMP operation involving a message across the BYNET
  • C) An all-AMP broadcast scan
  • D) Zero AMP operations
Explanation: USI subtables are partitioned by the secondary key. AMP 1 reads the USI subtable to get the ROWID and sends a message across the BYNET to AMP 2 to read the base row.
Q3. For a table with 512 rows per block, what is the approximate break-even selectivity of an unclustered single index?
  • A) 25%
  • B) 10%
  • ✓ C) Less than 2%
  • D) 50%
Explanation: At >2% selectivity, matching rows scatter across virtually every physical block in the table, making indexed access slower than a sequential scan.
Q4. How do Dynamic Bitmap indexes resolve false positives?
  • A) By using 512-bit SHA hashing
  • ✓ B) By re-validating all query predicates against the actual base table row after fetching it
  • C) By rolling back uncommitted transactions
  • D) Dynamic bitmaps cannot produce false positives
Explanation: Hash collisions in memory bitmaps can falsely turn bits ON. The RDBMS re-evaluates the query predicates against the fetched base row to guarantee accuracy.
Q5. A composite index exists on (state, education, hobby). Why does WHERE education = 'G' trigger a full index scan?
  • A) Education is a low-cardinality column
  • ✓ B) The Leading Column Rule: the index is sorted primarily by state; omitting state prevents hierarchical navigation
  • C) Composite indexes require all columns in the WHERE clause
  • D) The query lacks an ORDER BY clause
Explanation: The high-order column (state) must be constrained to navigate down the B-Tree; otherwise, the engine must scan all leaf blocks.
Q6. What are the recommended settings for PCTFREE and PCTUSED in a Data Warehouse?
  • A) PCTFREE 30%, PCTUSED 40%
  • B) PCTFREE 50%, PCTUSED 50%
  • ✓ C) PCTFREE 0%–5%, PCTUSED 80%–90%
  • D) PCTFREE 20%, PCTUSED 40%
Explanation: DW data is read-only and historical (low PCTFREE prevents empty space waste; high PCTUSED packs blocks tightly for fast scans).
Q7. Where should Bitmapped Indexes be deployed in a Star Schema?
  • A) On the composite primary key of the Fact table
  • B) On metric columns inside the Fact table
  • ✓ C) On low-cardinality descriptive columns in Dimension tables
  • D) On fact table surrogate keys
Explanation: Bitmaps are designed for low-cardinality data with repeated values. Fact tables have millions of high-cardinality rows and should never use bitmaps.
Q8. What is the benefit of a Covered Index?
  • A) Compresses data using run-length encoding
  • ✓ B) Satisfies queries completely out of the index, eliminating all base table I/O
  • C) Enforces unique constraints across tables
  • D) Decreases the size of index leaf blocks
Explanation: Because all requested columns exist in the index leaf blocks, the engine never touches base table blocks.
Final Review Practice Questions
Easy: Which block parameter directly controls empty space waste during full table scans in a DW?

Answer: PCTFREE. Setting it too high reserves empty space for updates that never happen, forcing scans to read empty space.

Medium: Why does NUSI in Teradata require an all-AMP scan?

Answer: NUSI entries are co-located on the same AMP as base data. Rows are distributed across all AMPs by Primary Index, so matching values could reside on any AMP, requiring all AMPs to scan their local NUSI in parallel.

Hard: Why does adding 15 B-Tree indexes to a 500M-row Fact table cause batch load failure?

Answer: Every inserted row must update and rebalance all 15 B-Tree hierarchies, causing massive random I/O, leaf splits, and lock contention that blows past the ETL window.

Master Quiz Preparation Checklist

  • Teradata: UPI (1 AMP, free), NUPI (1 AMP, free, skew risk), USI (2 AMPs, BYNET), NUSI (All AMPs parallel, co-located).
  • Selectivity: Break-even is strictly < 2%. Single indexes fail in DW; combine multiple indexes with RID ANDing.
  • Bitmaps: Break-even at 64 unique values; dynamic bitmaps resolve false positives via base row re-validation.
  • Physical Design: PCTFREE low (0-5%), PCTUSED high (80-90%). Suspend RI checks during load. Never put bitmaps on Fact tables!
