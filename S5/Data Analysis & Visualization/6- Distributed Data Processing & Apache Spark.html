Module 6 — Distributed Data Processing & Apache Spark

Based on Learning Spark, 2nd Edition — Chapters 1, 2 & 3

1Why Distributed Computing?

The hardware wall that forced a paradigm shift

For decades, the answer to "my program is too slow" was simple: buy a faster CPU. Processors kept doubling in speed every two years (Moore's Law). But around 2005, physicists hit a wall — you can only push electrons through silicon so fast before you melt the chip. Clock speeds plateaued. The only way forward was more cores — and eventually, more machines. This is the origin story of modern distributed computing.

Definition
Distributed Computing: A model where a computational task is split across multiple interconnected machines (nodes), each working on a part of the problem simultaneously. The results are combined to produce a final answer. Think of it as 1,000 people each solving one piece of a million-piece puzzle simultaneously, rather than one person doing it alone.

The Big Data Problem — The 3 Vs

Modern data sources (social media, IoT sensors, logs, genomics) produce data at scales that simply cannot fit on a single machine. Big Data is characterized by three dimensions:

📊 Yesterday's Data

  • Megabytes → Gigabytes
  • Fits on a single hard drive
  • Single-machine SQL databases
  • Nightly batch processing
  • Structured relational data

🌊 Today's Data (Big Data)

  • Terabytes → Petabytes → Exabytes
  • Distributed across thousands of disks
  • Distributed engines (Spark, Flink)
  • Real-time streaming + batch
  • Structured + Semi + Unstructured
Definition
The 3 Vs of Big Data:
  • Volume: The sheer amount of data generated (terabytes/day from a single social platform).
  • Velocity: The speed at which data arrives (real-time stock ticks, live sensor streams).
  • Variety: The diversity of data formats (JSON logs, images, videos, structured tables).

Scale-Up vs. Scale-Out

The key insight that enabled modern Big Data processing was using commodity hardware — cheap, off-the-shelf machines — instead of expensive supercomputers. Instead of one $10M server, you buy 1,000 $10K servers and coordinate them with software. This is called horizontal scaling (scale-out) as opposed to vertical scaling (scale-up).

Aspect Scale-Up (Vertical) Scale-Out (Horizontal)
Approach Bigger, more powerful single machine More machines working together
Cost Exponentially expensive Cheap commodity hardware
Fault Tolerance Single point of failure Redundant — node failures are routine
Elasticity Hard to add/remove capacity Add/remove nodes dynamically
Example Oracle RAC, IBM mainframe Hadoop cluster, Spark on cloud
Key Insight
In a distributed cluster, node failures are not exceptions — they are expected. At scale, if you have 10,000 machines and each has a 0.1% daily failure rate, you expect 10 machines to fail every day. The system must be designed to tolerate this gracefully without losing data or crashing computations.

Key Takeaways

  • CPU clock speed plateaued ~2005, forcing a shift to parallel and distributed computing.
  • Big Data (3 Vs: Volume, Velocity, Variety) cannot be processed on a single machine.
  • Horizontal scaling (commodity clusters) is cheaper and more fault-tolerant than vertical scaling.
  • Distributed systems treat node failures as routine events, not exceptional errors.

2MapReduce & Distributed File Systems

Google's 2004 blueprint that changed data engineering forever

In 2004, Google published a landmark paper describing MapReduce — a programming model for processing massive datasets across thousands of machines. That same year they published the Google File System (GFS), describing how to reliably store petabytes of data across cheap hardware. Together, these two ideas became the foundation of the entire Big Data ecosystem.

Distributed File Systems (DFS)

Definition
Distributed File System (DFS): A file system that stores data across multiple networked machines but presents a single unified namespace to users and applications. Files are split into fixed-size blocks (e.g., 128 MB in HDFS) and distributed across nodes, with each block replicated (usually 3x) for fault tolerance.

HDFS Architecture — NameNode + DataNodes

🗂️ NameNode (Master)
Stores ONLY metadata: which blocks live on which DataNodes. No actual file data here.
↕ metadata lookups (clients ask "where is block X?")
💾 DataNode 1
Blocks A, D, G
💾 DataNode 2
Blocks A, B, E
💾 DataNode 3
Blocks B, C, F
💾 DataNode 4
Blocks C, D, G

Block A is stored on DataNodes 1 and 2 (2x replication shown). If DataNode 1 fails, Block A is still readable from DataNode 2.

Three Core DFS Properties
  • Block Replication: Each block stored on multiple nodes (default 3x in HDFS). Fault-tolerant storage.
  • Data Locality: Move compute TO the data (not data to compute). Processing runs on the node holding the block — no costly network transfer.
  • Write Once, Read Many (WORM): Files are written once and read many times. HDFS is optimized for large sequential reads, not random writes.

The MapReduce Programming Model

MapReduce breaks any large computation into two phases: a Map phase and a Reduce phase. The key insight is that these phases are embarrassingly parallelizable — each mapper and reducer can run completely independently on different machines.

Definition
Map Function: Takes an input key-value pair and produces a set of intermediate key-value pairs. Intuition: Apply a transformation to every single record, independently.

Reduce Function: Takes all intermediate values for the same key and merges them. Intuition: Aggregate/summarize all records sharing a property.
Classic Example: Word Count

Counting word frequencies across millions of documents

-- Input (each line is a record) --
"the quick brown fox"
"the fox jumped"

-- MAP phase: each word becomes ("word", 1) --
Mapper 1: ("the", 1), ("quick", 1), ("brown", 1), ("fox", 1)
Mapper 2: ("the", 1), ("fox", 1), ("jumped", 1)

-- SHUFFLE phase: group all values by key across all mappers --
"brown"  → [1]
"fox"    → [1, 1]
"jumped" → [1]
"quick"  → [1]
"the"    → [1, 1]

-- REDUCE phase: sum values for each key --
"brown"  → 1
"fox"    → 2
"jumped" → 1
"quick"  → 1
"the"    → 2

This scales to billions of documents — just add more mappers on more machines.

Why MapReduce Was Eventually Replaced

The Disk I/O Problem — MapReduce's Fatal Flaw
Every MapReduce job writes intermediate results to HDFS (disk) after the shuffle. For iterative algorithms (ML training with 100+ iterations): each iteration reads from disk, processes, writes to disk, and the next reads again. 100 iterations = 200 disk I/O operations on intermediate data. Disk is 100-1000x slower than RAM. Spark eliminates this by keeping intermediate data in memory (RAM).
Other MapReduce Limitations
  • Two-phase rigidity: Complex algorithms must be awkwardly chained into multiple Map→Reduce jobs.
  • No native streaming: Inherently batch-oriented; real-time processing requires a separate system.
  • Verbose API: Even simple operations require hundreds of lines of Java boilerplate.
  • No in-memory caching: Frequently-accessed datasets re-read from disk on every job.

Key Takeaways

  • DFS splits files into replicated blocks across nodes — fault-tolerant distributed storage.
  • Data locality (move compute to data) is a core performance principle in distributed systems.
  • MapReduce = Map → Shuffle → Reduce. Embarrassingly parallel, simple model.
  • MapReduce's fatal flaw: intermediate data written to disk after every phase — catastrophic for iterative workloads.

3DAGs & Hadoop

How execution plans are represented and the full Hadoop ecosystem

Directed Acyclic Graphs (DAGs)

Definition
Directed Acyclic Graph (DAG): A graph where nodes represent operations and edges represent data dependencies. Directed = edges have a direction (data flows forward). Acyclic = no cycles — no circular dependencies. The engine sees the entire execution plan before running anything, enabling global optimizations impossible in MapReduce's rigid two-phase model.

Example DAG: filter → join → groupBy → count

📂 Read CSV (sales)
📂 Read JSON (products)
↓             ↓
🔍 filter(year=2024)
🏷️ select(id, category)
↓             ↓
🔗 join(sales.productId = products.id)
↓
📊 groupBy(category)
↓
✅ count() → Write Results

The engine can optimize: push filter before join (smaller join input), fuse consecutive narrow ops, prune unread partitions.

DAG Optimizations the Engine Can Apply
  • Predicate pushdown: Apply filters as early as possible (before joins) to reduce data size entering expensive operations.
  • Stage fusion: Combine consecutive narrow transformations into a single execution stage — no intermediate serialization.
  • Partition pruning: Skip reading partitions not needed by the query entirely.

Apache Hadoop — The Full Stack

Hadoop was the open-source implementation of Google's GFS + MapReduce papers, created by Doug Cutting at Yahoo! in 2006. It became the dominant Big Data platform for nearly a decade.

Hadoop's Achilles Heel
  • All intermediate data written to HDFS (disk) → 10-100x slower than in-memory processing.
  • No support for streaming data — batch processing only.
  • Very complex to program (deep Java expertise needed even for simple tasks).
  • Poor support for iterative ML algorithms.
Hadoop MapReduce is now largely replaced by Apache Spark as the de-facto distributed engine, though HDFS and YARN remain popular.

Key Takeaways

  • A DAG represents a computation as a graph of operations, enabling the engine to optimize the full plan before executing.
  • Hadoop = HDFS (storage) + MapReduce (compute) + YARN (resource management).
  • DAG-based engines are fundamentally more flexible and optimizable than MapReduce's rigid two-phase model.

4Single Machine vs. Distributed — Paradigm Shift

How your mental model must change when writing distributed code

Moving from single-machine programming (Python scripts, SQL on a laptop) to distributed computing isn't just about using different tools — it requires a fundamentally different mental model. Things that "just work" on one machine become nuanced challenges at scale.

🖥️ Single Machine Thinking

  • Data fits in memory / one disk
  • Sequential or multi-threaded execution
  • Shared memory between threads
  • Failures are rare — restart and retry
  • Latency: nanoseconds (cache) to ms (disk)
  • One log file, one stack trace
  • Ordering is deterministic

🌐 Distributed Thinking

  • Data partitioned across many nodes
  • Massively parallel execution
  • No shared memory — network messaging
  • Node failures happen daily — must self-heal
  • Latency: milliseconds to seconds (network)
  • Logs from 1000s of executors
  • Ordering is non-deterministic by default

Key Paradigm Shifts Explained

1. Data Partitioning Instead of Looping

On a single machine, you iterate over data with a for loop. In a distributed system, data is partitioned across nodes. Each node processes its own partition simultaneously. You write transformations that apply to one partition; the engine applies it to all partitions in parallel.

Paradigm Shift — Single Machine vs. Spark

Filtering a 1 TB dataset

# Single Machine (Pandas) — sequential, crashes if file > RAM
import pandas as pd
df = pd.read_csv("huge_file.csv")          # FAILS if 1TB file
result = df[df["country"] == "PK"]

# Distributed (PySpark) — 1000 machines each filter their partition
from pyspark.sql import SparkSession
spark = SparkSession.builder.getOrCreate()
df = spark.read.csv("hdfs://huge_file.csv")   # lazy — reads nothing yet
result = df.filter(df["country"] == "PK")     # lazy — builds a DAG node
result.show()                                 # ACTION — triggers full execution

2. Shuffles — The Distributed Bottleneck

Definition
Shuffle: The process of redistributing data across partitions — sending data over the network so records with the same key end up on the same node. Triggered by: groupBy, join, orderBy, distinct. Shuffles are the most expensive operation in distributed systems — minimize them!

3. Fault Tolerance via Lineage

Definition
Lineage (RDD Lineage): The recorded sequence of transformations applied to create a dataset. If a partition is lost (executor crash), Spark re-executes only the lineage transformations needed to rebuild that specific partition — not the entire job. This is Spark's primary fault tolerance mechanism, as opposed to data replication.

4. Lazy Evaluation

Spark doesn't execute transformations immediately. It builds a DAG of the full computation plan. Only when you trigger an action does execution begin — enabling Catalyst to optimize the entire plan holistically before any byte of data is moved.

Transformation 1
read → filter
+
Transformation 2
join → select
+
Transformation 3
groupBy → agg
→
ACTION
.count() triggers ALL
The Big Mental Shift — Declarative over Imperative
Stop thinking procedurally ("do step 1, then step 2"). Think declaratively: "describe the transformation I want, let Spark figure out how to execute it efficiently." DataFrames are declarative (SQL-like). RDDs are imperative (you specify each step manually). This is why DataFrames allow global optimization while RDDs don't.

Key Takeaways

  • Distributed systems partition data; operations run in parallel on each partition simultaneously.
  • Shuffles (cross-partition data movement) are the most expensive operations — minimize them.
  • Fault tolerance is handled via lineage — Spark recomputes lost partitions without full restart.
  • Lazy evaluation: transformations build a plan; only actions trigger execution, enabling global optimization.

5Apache Spark — A Closer Look

Architecture, abstractions, transformations, actions, and the execution model

Apache Spark was born at UC Berkeley's AMPLab in 2009 and open-sourced in 2010. Its core innovation: keep intermediate data in RAM between computation steps instead of writing to disk. This made it up to 100x faster than Hadoop MapReduce for iterative algorithms and interactive queries. It also unified five previously separate systems into one engine.

Definition
Apache Spark: A unified, open-source analytics engine for large-scale data processing. Provides in-memory distributed computation with a unified API for batch, streaming, SQL, machine learning, and graph processing — all on one cluster runtime.

RDDs vs. DataFrames

Definition
RDD (Resilient Distributed Dataset): Spark's lowest-level abstraction. An immutable, partitioned collection of records distributed across cluster nodes. "Resilient" because it uses lineage for fault recovery. RDDs give fine-grained control but are opaque to the Catalyst optimizer — it cannot optimize them.
Definition
DataFrame: A distributed collection of data organized into named, typed columns — like a SQL table, but potentially billions of rows across a cluster. DataFrames use Catalyst and Tungsten, making them significantly faster than raw RDDs for most structured workloads.

RDD

  • Low-level, unstructured records
  • Full manual control
  • Type-safe in Scala/Java
  • No schema, no optimizer
  • Use for: custom serialization, legacy code, complex UDFs

DataFrame / Dataset

  • High-level, named columns
  • Catalyst optimizer + Tungsten engine
  • Python / R / Scala / Java support
  • Schema-aware, SQL-queryable
  • Use for: SQL, ETL pipelines, ML, analytics
Pro Tip — Always Prefer DataFrames
In modern Spark (2.x+), always prefer DataFrames over RDDs unless you have a specific reason. DataFrames use Catalyst which generates code often faster than hand-written RDD code. The optimizer understands join/filter semantics and can reorder them. RDD operations are opaque black boxes to the optimizer — it cannot improve them.

Transformations vs. Actions

Definition
Transformation: An operation that returns a new DataFrame/RDD. Lazy — adds a step to the logical plan, nothing executes. Examples: filter(), select(), groupBy(), join(), withColumn().

Action: An operation that triggers the actual DAG computation. Returns a result to the driver or writes to storage. Examples: show(), count(), collect(), write(), first(), take(n).
Operation What it does Type
filter() / where() Keep rows matching condition Narrow Transformation (no shuffle)
select() / drop() Choose or remove columns Narrow Transformation
withColumn() Add or transform a column Narrow Transformation
groupBy().agg() Group rows by key, aggregate values Wide Transformation (shuffle!)
join() Join two DataFrames on a key Wide Transformation (shuffle!)
orderBy() / sort() Sort all rows globally Wide Transformation (shuffle!)
distinct() Remove duplicate rows Wide Transformation (shuffle!)
cache() / persist() Store DataFrame in memory after first compute Optimization hint
show() / count() / collect() Trigger full DAG execution, return result Action
Narrow vs. Wide — Critical Distinction
  • Narrow Transformation: Output partition depends on exactly ONE input partition. No network transfer. Fast (runs locally per node). Example: filter, select, map.
  • Wide Transformation (Shuffle): Output partition may depend on MULTIPLE input partitions from DIFFERENT nodes. Requires network transfer. Creates a new Stage boundary. Example: groupBy, join, orderBy.
Spark divides the DAG into Stages at each shuffle boundary. Within a stage, all tasks run fully in parallel. Between stages, data must be shuffled over the network — a synchronization barrier.

Catalyst Optimizer Pipeline

When you write a DataFrame query, Spark doesn't execute it directly. It goes through a sophisticated optimization pipeline before a single byte of data is touched:

1. Unresolved Logical Plan
→ Catalog resolves table/column names and types
2. Resolved Logical Plan
→ Catalyst applies rule-based optimizations (predicate pushdown, constant folding)
3. Optimized Logical Plan
→ Physical planning: generate multiple candidate physical strategies
4. Physical Plans
→ Cost model picks the best plan (e.g., broadcast join vs. sort-merge join)
5. Execute!
→ Tungsten generates optimized JVM bytecode. Runs on cluster.
PySpark — Complete Example

Full SparkSession workflow (Learning Spark Chapters 2 & 3 style)

from pyspark.sql import SparkSession
from pyspark.sql.functions import col, count, avg

# 1. Create a SparkSession — single entry point
spark = SparkSession.builder \
    .appName("FlightAnalysis") \
    .config("spark.executor.memory", "4g") \
    .getOrCreate()

# 2. Read CSV into a DataFrame (LAZY — no data is read yet)
df = spark.read \
    .option("header", True) \
    .option("inferSchema", True) \
    .csv("hdfs:///data/flights.csv")

# 3. Inspect schema (this triggers a small scan for type inference)
df.printSchema()
# root
#  |-- date: string
#  |-- airline: string
#  |-- origin: string
#  |-- dest: string
#  |-- delay: integer

# 4. Chain LAZY transformations — NOTHING RUNS YET
result = (
    df
    .filter(col("delay") > 0)                    # narrow: filter within partition
    .select("airline", "origin", "dest", "delay") # narrow: drop columns
    .groupBy("airline")                            # wide: SHUFFLE by airline
    .agg(
        count("*").alias("total_flights"),
        avg("delay").alias("avg_delay_min")
    )
    .orderBy(col("avg_delay_min").desc())          # wide: SHUFFLE for global sort
)

# 5. .show() is an ACTION — triggers full DAG execution NOW
result.show(10)

# 6. Cache a heavy DataFrame used multiple times
df.cache()    # after next action, df is stored in RAM on all executors

# 7. Write results (also an ACTION)
result.write.mode("overwrite").parquet("hdfs:///output/airline_stats")

# Clean up
df.unpersist()  # free the RAM

PySpark Performance Nuance
With DataFrame/SQL operations, Python and Scala have nearly identical performance — both compile to the same JVM bytecode via Tungsten. The gap appears only with Python UDFs: each UDF call serializes rows from JVM to Python process and back — 10-100x overhead. Solution: use Pandas UDFs (vectorized) which batch-serialize entire columns using Apache Arrow, amortizing the overhead across thousands of rows.

Key Takeaways

  • Spark stores intermediate data in RAM — up to 100x faster than Hadoop MapReduce for iterative workloads.
  • Unified stack: SQL, Streaming, MLlib, GraphX — one engine replaces five separate systems.
  • DataFrames are preferred: schema-aware, Catalyst-optimized, language-agnostic.
  • Transformations = lazy (build plan). Actions = trigger execution. Wide transformations cause shuffles.
  • Catalyst rewrites your logical plan into an optimized physical plan before execution.
  • Hierarchy: Application → Job (per action) → Stage (per shuffle boundary) → Task (per partition).

6🎯 Quiz & Review

12 questions across 5 sections — Easy, Medium, Hard, and Tricky

Try to answer each question before expanding the solution. Pay close attention to the tricky questions — they test conceptual depth, not just recall.

📌 Section A: Distributed Computing Fundamentals

Easy What are the "3 Vs" of Big Data? Give a real-world example of each.

Answer:

  • Volume: Enormous amount of data. Example: Facebook generates ~4 petabytes of new data per day from posts, likes, and messages.
  • Velocity: Speed at which new data arrives. Example: Twitter processes ~6,000 tweets per second; financial exchanges process millions of trades per second.
  • Variety: Different types and formats of data. Example: A hospital has structured EHR records (SQL tables), semi-structured doctor's notes (JSON), and unstructured MRI scans (images) — all needing different processing pipelines.
Easy Why did physical limits of CPUs around 2005 force the adoption of distributed computing?

Answer: Around 2005, CPU manufacturers hit the power wall — increasing clock speeds further caused excessive heat generation. Electrons moving through transistors at higher frequencies produce heat that can't be safely dissipated. This caused clock speeds to plateau. Moore's Law continued but in the form of more cores per chip, not faster cores. For truly massive data processing, even multi-core chips on a single machine are insufficient — requiring multiple interconnected machines (distributed computing).

Medium Compare horizontal (scale-out) vs. vertical (scale-up) scaling. When would you prefer each?

Vertical scaling (upgrade one machine): Better for workloads that are hard to parallelize — single-threaded legacy apps, databases with complex transactions that can't be sharded. Simpler architecture but exponentially expensive and creates a single point of failure.

Horizontal scaling (add more machines): Better for workloads that can be naturally partitioned — web requests, batch data processing, ML training. Cheaper, fault-tolerant, elastic (add/remove nodes dynamically). Requires software designed to work across machines.

Rule of thumb: In the Big Data regime (TBs+), horizontal scaling is essentially mandatory — no single machine can hold the data, let alone process it efficiently.

📌 Section B: MapReduce & Distributed File Systems

Easy In MapReduce, what is the role of the Shuffle phase, and which two phases does it connect?

Answer: The Shuffle phase sits between the Map phase and the Reduce phase. Its role is to collect all intermediate key-value pairs from all mappers across all machines, sort them by key, and group all values with the same key together. This ensures each reducer receives all values for its assigned keys — which may have come from many different mappers on different machines. Without the shuffle, no reducer would have complete data for any key.

Medium Explain "data locality" in HDFS. Why is moving compute to data more efficient than moving data to compute?

Answer: Data locality means scheduling computation on the node that already holds the data block. In HDFS, each 128 MB block is stored on a specific DataNode. If the processing task is scheduled on that same DataNode, no data moves over the network — it's read from local disk into local RAM.

The alternative (moving data to compute): sending 128 MB over a 1 Gbps network takes ~1 second per block. With millions of blocks and thousands of tasks, this would saturate the network and slow every job catastrophically. Local disk I/O is typically 3-10x faster than network I/O in a cluster. Hence: "move the code to the data, not the data to the code."

Hard A MapReduce ML training loop runs 200 iterations. How many disk operations occur on intermediate data? Why does this make MapReduce unsuitable for ML?

Answer: Per iteration: Map reads input (1 disk read), writes intermediate output (1 disk write), Reduce reads intermediate (1 disk read), writes final output (1 disk write) = 4 disk I/Os per iteration.

For 200 iterations: 200 × 4 = 800 disk I/O operations on intermediate model data.

Why this is disastrous for ML:

  • Disk I/O is 100-1000x slower than RAM.
  • Between iterations, you need current model parameters in memory. MapReduce must write/read them to/from disk every time.
  • Spark solves this by keeping the training dataset and model state cached in RAM across all 200 iterations — only 1 initial disk read, 1 final write. The 198 intermediate iterations read from RAM at memory speed.

📌 Section C: DAGs & Hadoop

Easy What does DAG stand for? What do nodes and edges represent in a Spark execution DAG?

DAG = Directed Acyclic Graph.

  • Nodes: operations/transformations (e.g., filter, groupBy, join).
  • Edges: data dependencies — edge from A to B means "B depends on A's output; data flows A → B".
  • Directed: edges have direction (data flows forward only).
  • Acyclic: no cycles — a computation cannot depend on its own output. Guarantees the computation can always terminate.
Tricky YARN in Hadoop and Spark's Cluster Manager play similar roles but are NOT the same thing. Explain the difference and how they interact when running Spark on Hadoop.

YARN is Hadoop's general-purpose cluster resource manager. It manages the entire cluster's CPU and memory, allocating containers to any application type — not just Spark. It's cluster-level infrastructure.

Spark's Cluster Manager is the component within Spark that communicates with whatever underlying resource manager exists. Spark supports YARN, Kubernetes, Mesos, or its own Standalone mode.

When running Spark on Hadoop: Spark submits via --master yarn. YARN allocates JVM containers on worker nodes. Spark starts its Executor processes inside those YARN containers. YARN handles resource allocation; Spark handles task scheduling and execution within its allocated resources. They operate at different abstraction levels — YARN is the infrastructure, Spark is the application layer.

📌 Section D: Single vs. Distributed Paradigm

Medium What is lazy evaluation in Spark? What triggers actual execution, and what are the benefits of laziness?

Lazy evaluation: Spark does not execute transformations (filter, select, groupBy) when called. Each one adds a step to an internal logical plan. No data processing happens.

Execution is triggered only by an action: .show(), .count(), .collect(), .write(), .first(), .take(n).

Benefits:

  • Global optimization: Catalyst has the complete plan and can reorder operations (e.g., push filters before joins to reduce data early).
  • Stage fusion: Consecutive narrow transformations fused into one pass — avoids intermediate materializations.
  • Early termination: take(10) stops processing after finding 10 rows — doesn't scan the whole dataset.
Tricky A developer writes df.count(); df.count(). How many times does Spark actually process the data, and how do you fix it?

Answer: Spark processes the data twice — once per .count() action. Each action independently re-executes the full DAG from scratch (reading storage, applying all transformations, computing the result). The two calls have no awareness of each other.

Fix — use .cache():

df.cache()   # Mark DataFrame to store in RAM after first computation
df.count()   # First action: computes + stores result partitions in memory
df.count()   # Second action: reads from RAM — no recomputation!
df.unpersist()  # Free RAM when done

After cache(), the first action materializes the DataFrame into executor RAM. All subsequent actions read from RAM. Critical for DataFrames used in multiple downstream operations (e.g., fed into two different joins or filters).

📌 Section E: Apache Spark — Deep Dive

Medium Explain narrow vs. wide transformations with two examples each. What happens at the cluster level for each?

Narrow Transformation: Output partition depends on exactly ONE input partition. No network transfer needed.

  • filter(): each executor filters rows in its own partition — no other partition needed.
  • select(): each executor drops columns in its own partition.

At cluster level: each executor operates independently on its partition. Zero coordination between executors.

Wide Transformation (Shuffle): Output partition may need data from MULTIPLE input partitions on DIFFERENT nodes.

  • groupBy().agg(): all rows with the same key must be on the same executor — data from all partitions flows over the network.
  • join(): matching rows from both DataFrames must be co-located on the same executor.

At cluster level: all executors write their shuffle output to local disk, then other executors fetch the data they need over the network. Creates a stage boundary — a synchronization barrier where all Stage N tasks must complete before Stage N+1 begins. Wide transformations are the primary performance bottleneck in most Spark jobs.

Hard If a Spark executor crashes and loses 3 of 10 cached partitions, what exactly does Spark do to recover? How does this differ from HDFS's fault tolerance approach?

Spark's Lineage-Based Recovery:

  1. Scheduler detects executor failure via heartbeat timeout.
  2. Identifies which 3 partitions are missing.
  3. Walks the lineage DAG for each lost partition back to the original source (e.g., a Parquet file on HDFS).
  4. Schedules those 3 partition tasks on surviving executors, re-applying all lineage transformations to regenerate them.
  5. The other 7 partitions are unaffected and continue.

HDFS Replication vs. Spark Lineage:

  • HDFS replication: Proactive, eager fault tolerance. Stores 3 copies of every block before failures occur. On node failure, NameNode detects under-replication and re-replicates from surviving copies — instant recovery, no recomputation. Cost: 3x storage overhead.
  • Spark lineage: Reactive, lazy fault tolerance. No extra copies stored. On failure, recomputes lost partitions from scratch. Storage-efficient but recovery time increases with lineage length.

Trade-off: HDFS gives instant recovery with no recomputation cost but 3x storage. Spark lineage is memory-efficient but recovery requires recomputing. For very long lineages, use .checkpoint() to save to HDFS and break the lineage, capping maximum recovery cost.

  • Distributed computing arose from the Big Data 3 Vs (Volume, Velocity, Variety) and the ~2005 CPU clock speed plateau.
  • Scale-out (horizontal) with commodity hardware is cheaper and more fault-tolerant than scale-up (vertical).
  • DFS splits files into replicated blocks. Data locality = run compute on the node holding the block.
  • MapReduce: Map → Shuffle → Reduce. Parallelizable but disk-bound between every phase — catastrophic for iterative ML.
  • DAGs represent the full computation as a graph, enabling global optimizations: predicate pushdown, stage fusion, partition pruning.
  • Hadoop = HDFS + MapReduce + YARN. Still used for storage/resources; Spark has replaced MapReduce as compute engine.
  • Key paradigm shift: partitioned data, parallel execution, shuffles as bottleneck, lineage-based fault recovery, lazy evaluation.
  • Spark keeps intermediate data in RAM — up to 100x faster than MapReduce for iterative algorithms.
  • Unified Spark stack: SQL/DataFrames, Structured Streaming, MLlib, GraphX — one engine for everything.
  • DataFrames > RDDs: Catalyst-optimized, schema-aware, multi-language. Always prefer DataFrames.

7⚠️ The Role of RDDs & Spark Pitfalls to Avoid

Week 5 (15, 17 Sep) — Learning Spark 2nd Ed., Ch. 1–3

This topic ties together the Week 5 syllabus: RDDs vs. the high-level API, lazy evaluation in depth, and the classic pitfalls that trip up developers moving from single-machine to Spark programming. Think of it as your practical survival guide for writing good Spark code.

The Role of RDDs — Why They Still Matter

Even though DataFrames are almost always the right choice, RDDs are still Spark's foundational abstraction. Understanding them deeply explains why DataFrames work the way they do.

Definition
RDD (Resilient Distributed Dataset): Spark's original core abstraction (introduced in 2012 AMPLab paper). An immutable, partitioned collection of records distributed across nodes, with a recorded lineage for fault recovery. Three key properties:
  • Resilient: Fault-tolerant via lineage — lost partitions are recomputed, not stored redundantly.
  • Distributed: Partitions live on different executor nodes — parallel processing by default.
  • Dataset: A collection of records (can be any Python/Java/Scala object — RDDs are schema-free).

The Five RDD Properties (Internal)

PropertyDescriptionWhy It Matters
Partitions list Set of partition objects making up the dataset Determines parallelism — one task per partition
Compute function Function to compute the partition's data from parent RDDs Enables lazy evaluation and recomputation on failure
Dependencies list List of parent RDDs this RDD depends on The lineage graph used for fault recovery
Partitioner (optional) Hash or range partitioning scheme for key-value RDDs Determines how shuffles route records to partitions
Preferred locations (optional) Node preferences for data locality Allows scheduling tasks near their data (HDFS blocks)

When to Use RDDs vs DataFrames

Use RDDs when…

  • You need fine-grained control over partitioning (e.g., custom partitioner)
  • Working with unstructured data that has no schema (binary blobs, raw text)
  • Complex custom data types that DataFrames can't represent as columns
  • Using legacy Spark 1.x code that predates DataFrames
  • You need Python objects and can't express logic as DataFrame operations

Use DataFrames in all other cases

  • Structured / semi-structured data (CSV, JSON, Parquet, Avro, JDBC)
  • SQL queries, aggregations, joins, ETL pipelines
  • Machine learning with MLlib (operates on DataFrames)
  • Any multi-language team (Python, Scala, Java, R same API)
  • Anywhere performance matters — Catalyst optimizes DataFrames, not RDDs
The Optimizer Blindspot
When you use an RDD with a Python lambda (e.g., rdd.map(lambda x: x.upper())), Catalyst sees it as an opaque black box. It cannot look inside the lambda to reorder operations, push predicates, or fuse stages. The same logic expressed as a DataFrame operation (df.withColumn("col", upper(col("col")))) is fully transparent to Catalyst and can be combined, reordered, and compiled to efficient bytecode. This is why DataFrames consistently outperform equivalent RDD code even when the developer writes "optimal" RDD logic.

The Role of the High-Level API (DataFrames / Datasets / SQL)

Spark 2.0 unified three previously separate APIs — SparkContext (RDDs), SQLContext (DataFrames), and HiveContext — into a single SparkSession. The high-level API sits on top of the same RDD engine but adds a schema layer and Catalyst.

🗣️
User Code (Python, Scala, SQL, R)
You write DataFrame operations or SQL strings — declarative and human-readable
🔍
Catalyst Query Optimizer
Parses → resolves → rewrites → generates optimized physical plan
⚡
Tungsten Execution Engine
Generates JVM bytecode; manages memory off-heap; cache-aware binary processing
📦
RDD Engine (Spark Core)
Task scheduling, shuffle management, fault recovery — the actual distributed machinery
Key Insight — Why the High-Level API is Faster
The high-level API doesn't just add convenience — it adds semantic understanding. When Spark knows you're doing a groupBy + sum, it can choose the optimal join strategy, push filters early, and use vectorized SIMD operations via Tungsten. An equivalent RDD reduceByKey is fully opaque — Spark executes exactly what you wrote, with no chance to improve it.

Lazy Evaluation — Deep Dive

Lazy evaluation is the mechanism that makes all optimization possible. Here is the exact sequence of events when you write and execute a Spark program:

Lazy Evaluation — Step-by-Step Timeline

Step 1: df.filter(…).groupBy(…).agg(…)
You write Python/Scala code. Nothing happens in the cluster.
↓ builds
Step 2: Unresolved Logical Plan
A tree of AST nodes — column names unresolved. Still no cluster activity.
↓ Catalyst resolves schema
Step 3: Resolved Logical Plan
Column names and types validated against catalog. Errors surface here if column doesn't exist.
↓ Catalyst applies 60+ optimizations rules
Step 4: Optimized Logical Plan
Predicate pushdown, constant folding, column pruning, null propagation applied.
↓ Physical planner generates candidates
Step 5: Best Physical Plan Selected
Cost model chooses: broadcast join vs. sort-merge join, etc.
↓ ACTION called (.show(), .count(), .write()…)
Step 6: Tungsten Generates & Runs Code
JVM bytecode generated. Tasks dispatched to executors. Data processing begins NOW.
Exam Tip — Lazy vs. Eager
Transformations are LAZY: filter, select, groupBy, join, withColumn, map, flatMap, distinct, orderBy.
Actions are EAGER (trigger execution): show, count, collect, first, take(n), write, foreach, reduce, saveAsTextFile.
A common trick question: df.cache() is technically a transformation (lazy!) — the data is only actually cached after the next action triggers it.

⚠️ Spark Programming Pitfalls to Avoid

These are the most common mistakes developers make when moving from single-machine code to Spark. Each one either silently hurts performance or causes outright failures.

Pitfall 1 — Using collect() on Large DataFrames
df.collect() pulls all data from all executors back to the driver as a Python list. On a 10 TB DataFrame this means sending 10 TB over the network to one machine — crashing the driver with OutOfMemoryError.

Fix: Use df.show(n) to inspect a small sample, df.take(n) to get n rows, or df.write() to persist results to storage instead of collecting them to the driver.
Pitfall 2 — Calling Actions in a Loop
# BAD — triggers a full DAG execution 1000 times!
for i in range(1000):
    count = df.filter(col("id") == i).count()  # 1000 Spark jobs!

# GOOD — one job, filter once on all values
result = df.groupBy("id").count()  # one wide transformation
result.show()
Every action submits a new Spark job. A loop with 1000 actions = 1000 cluster round-trips. Always push the logic into a single DataFrame operation.
Pitfall 3 — Forgetting to Cache Reused DataFrames
# BAD — df computed TWICE from scratch
df = spark.read.parquet("huge_file").filter(col("active") == True)
count1 = df.count()       # full DAG execution #1
count2 = df.groupBy("region").count()  # full DAG execution #2

# GOOD — compute once, reuse from RAM
df = spark.read.parquet("huge_file").filter(col("active") == True).cache()
df.count()                # triggers computation + caches to RAM
df.groupBy("region").count()  # reads from RAM
Forgetting .cache() (or .persist()) on a DataFrame used in multiple downstream operations means Spark re-reads from storage and re-applies all transformations each time.
Pitfall 4 — Unnecessary Shuffles (Avoid groupBy when reduceByKey suffices)
groupBy collects all values for a key in one partition then aggregates. For simple aggregations (sum, count), Spark can pre-aggregate on each partition first (map-side combine) before the shuffle — dramatically reducing network data.

With DataFrames, use df.groupBy().agg(sum(…)) — Catalyst automatically applies partial aggregation. With RDDs, always use reduceByKey over groupByKey because groupByKey skips the map-side combine entirely.
Pitfall 5 — Python UDFs Kill Performance
# BAD — Python UDF: JVM → Python → JVM for every row
from pyspark.sql.functions import udf
from pyspark.sql.types import StringType

@udf(StringType())
def clean_name(name):
    return name.strip().lower()  # runs in Python process, row by row

df.withColumn("name", clean_name(col("name")))  # 10-100x slower!

# GOOD — use built-in Spark functions (JVM native)
from pyspark.sql.functions import lower, trim
df.withColumn("name", lower(trim(col("name"))))  # fully optimized by Catalyst
Spark's built-in functions (lower, trim, concat, regexp_replace, etc.) run natively in the JVM and are optimized by Tungsten. Python UDFs require serializing each row from JVM → Python interpreter → back to JVM. For unavoidable custom logic, use Pandas UDFs (vectorized UDFs) which transfer entire Arrow columnar batches, amortizing the serialization overhead.
Pitfall 6 — Data Skew (One Partition Does All the Work)
Data skew occurs when certain keys appear far more frequently than others, causing one executor to process 90% of the data while others are idle.

Symptom: In Spark UI, 99 tasks finish in 5 seconds, one task runs for 10 minutes. Common cause: Joining on a column with many NULLs or a dominant value (e.g., user_id where most records belong to one enterprise account).

Fixes: (1) Filter out null keys before joining. (2) Salt the key by appending a random number (e.g., "keyA_3"), then remove salt after join. (3) Broadcast the smaller table to avoid the shuffle entirely (broadcast(df_small)).
Pitfall 7 — Serialization & Closure Variables
When Spark serializes a task to send to executors, it captures the entire closure of your lambda or function — including any Python objects referenced from the outer scope. If you accidentally close over a SparkSession, a large dict, or a database connection, Spark will try to serialize and ship it to every executor, causing either serialization errors or massive overhead.

Fix: Keep closures minimal. Broadcast large lookup tables explicitly with spark.sparkContext.broadcast(my_dict) — Spark sends one copy per executor node, not one copy per task.

Practice Questions
EasyWhat does the "R" in RDD stand for, and what mechanism provides this property?

Answer: "Resilient" — meaning fault-tolerant. Spark achieves this through lineage: every RDD remembers the sequence of transformations that created it (its parent RDDs and operations). If a partition is lost due to executor failure, Spark re-executes the lineage from the last stable source (e.g., HDFS file) to regenerate only the lost partition — without restarting the entire job. This is Spark's primary fault tolerance mechanism, as opposed to HDFS which uses data replication.

MediumWhy is groupByKey() on an RDD worse than reduceByKey() for computing a sum? Trace what happens at the cluster level for each.

Answer:

groupByKey(): Shuffles ALL values for every key across the network to a single partition. Then, on the reducer, sums them. If key "A" appears 1 million times, all 1 million values are sent over the network before any addition occurs. Memory per reducer must hold all values for a key simultaneously.

reduceByKey(): First performs a map-side combine (partial aggregation) on each executor — adds up all values for key "A" within the local partition first, producing one partial sum per partition. Then, only the partial sums are shuffled over the network. Instead of sending 1 million values, you send just N partial sums (where N = number of partitions). Dramatically reduces network I/O and executor memory pressure.

DataFrames' groupBy().sum() automatically applies this optimization via Catalyst — one more reason to prefer DataFrames.

HardA Spark job reads a 500 GB Parquet file, applies 10 chained narrow transformations, then does a groupBy, then 5 more narrow transformations. How many stages does this job have? How many tasks per stage if the file has 4000 partitions and you set spark.sql.shuffle.partitions=200?

Answer:

Number of stages = 2 (one shuffle boundary = one stage boundary). Narrow transformations fuse together into single stages.

  • Stage 1: Read Parquet + 10 narrow transformations + write shuffle output. Number of tasks = 4000 (one per input partition).
  • Stage 2: Read shuffle data + groupBy aggregation + 5 narrow transformations + output. Number of tasks = 200 (set by spark.sql.shuffle.partitions, which controls the number of post-shuffle partitions).

Key insight: The number of tasks in Stage 1 is determined by the number of input partitions (Parquet file splits). The number of tasks in Stage 2 is determined by spark.sql.shuffle.partitions (default 200). This second number is often the biggest Spark tuning knob — too few and you have large, slow tasks; too many and you have too much scheduling overhead.

🎯 Tricky Exam-Style Questions

These questions are deliberately tricky — they test conceptual depth and the ability to apply multiple ideas together. Try each before expanding.

Section A — Data Concepts & EDA

TrickyA student removes all outliers from a dataset by deleting every row outside Q1−1.5×IQR. Their model performs worse than before. What likely went wrong, and how should outliers actually be handled?

Answer: Several things could have gone wrong:

  • Outliers weren't errors — they were valid extremes. In fraud detection, the outliers are the signal you want to predict. Removing them eliminates the rarest but most important examples.
  • The IQR rule is too aggressive for some distributions. For a right-skewed distribution (like salaries), Q3+1.5×IQR might remove perfectly valid high earners. The method assumes near-normality.
  • Removed too much data. If 15% of rows were "outliers", removing them creates a biased sample that no longer represents the real population the model will be deployed on.

Better approach: Investigate each outlier — is it a data entry error (fix it), a system anomaly (flag it), or a genuine extreme value (keep it)? Consider robust alternatives: Winsorization (cap values at a percentile rather than removing them), log transformation to compress the right tail, or use tree-based models that are naturally robust to outliers.

TrickyTwo variables have a Pearson correlation of 0.95. A student concludes they have a strong positive linear relationship. What critical assumptions might make this conclusion wrong?

Answer: Several assumptions could be violated:

  • Outliers inflate Pearson correlation. A single outlier can create a spuriously high r even when the bulk of data has no linear pattern (Anscombe's quartet — four datasets with identical statistics but completely different distributions).
  • Confounding variables (Simpson's paradox). Both variables might be driven by a hidden third variable (e.g., both age and salary correlate with years of experience — high r but not directly causal).
  • Spurious correlation. Per-capita cheese consumption correlates with deaths by bedsheet tangling. Both trend upward over time — it's a coincidence, not a relationship.
  • Non-linear relationships can show high Pearson r. A quadratic relationship where Pearson doesn't capture the true structure can still show high r in a limited range.
  • Correlation ≠ causation. Even a real linear relationship doesn't tell you which variable causes which — or whether both are effects of a common cause.

Always visualize with a scatter plot, check for outliers, and use domain knowledge before concluding anything from a correlation coefficient alone.

Section B — Data Architecture

TrickyA company uses a Data Lake. They discover that 40% of their data is wrong — columns were renamed upstream without notice, breaking all downstream pipelines silently. Which architectural evolution solves this, and how exactly?

Answer: A Delta Lakehouse with Schema Enforcement and Schema Evolution controls.

The problem (Data Lake weakness): Data Lakes are schema-on-read — you define the schema when you query, not when you write. If an upstream producer renames a column (e.g., user_id → userId), all existing Parquet files still work, but new files use the new name. Downstream queries silently read NULL for the renamed column — data quality degrades without any error.

Delta Lake solution:

  • Schema enforcement: Delta rejects any write whose schema doesn't match the table's schema — the upstream renaming would fail loudly at write time, immediately alerting the team.
  • Schema evolution: If a new column is intentionally added, mergeSchema=true allows it explicitly — you opt in, not opt out.
  • Audit log + Time Travel: Delta's transaction log records every change. You can query DESCRIBE HISTORY table to see when the schema changed and SELECT * FROM table VERSION AS OF 42 to read data before the corruption.

The Medallion architecture also helps: raw data lands in Bronze (untouched), Silver applies validation. A schema change breaks Silver, not Bronze — you can replay Bronze through corrected Silver logic.

HardExplain the difference between OLTP and OLAP databases with respect to normalization, query patterns, and indexing strategy. Why can't you use one system for both workloads efficiently?

OLTP (Online Transaction Processing):

  • Normalization: Highly normalized (3NF, BCNF) — no redundancy, each fact stored once. Enables fast writes/updates/deletes without anomalies.
  • Query pattern: Many small, targeted queries — "fetch this customer's order", "update this record". Millisecond latency, high concurrency (thousands of users).
  • Indexing: B-tree indexes on primary/foreign keys — optimized for point lookups and range queries on individual rows.
  • Storage: Row-oriented — an entire row (all columns) stored contiguously. Good for reading/writing whole records.

OLAP (Online Analytical Processing):

  • Normalization: Denormalized (star/snowflake schema) — dimensions pre-joined, redundancy accepted for query speed.
  • Query pattern: Few, complex, long-running scans — "sum all revenue by region for 2024". Touches millions/billions of rows, returns aggregates.
  • Indexing: Bitmap indexes, zone maps, partition pruning — optimized for filtering large scans on low-cardinality columns.
  • Storage: Columnar — each column stored separately. When aggregating one column of 1 billion rows, only that column is read (not all columns of all rows). 10-100× less I/O.

Why they can't share one system: Row storage is terrible for column scans. Normalized schemas require expensive joins for every analytical query. OLTP systems under heavy analytical queries starve real-time transactions of I/O bandwidth. OLAP denormalization makes transactional updates complex (update one fact = update multiple copies). Hence: separate OLTP (PostgreSQL, MySQL) → ETL → OLAP (Redshift, Snowflake, Spark) is the standard pattern.

Section C — Spark & Distributed Computing

TrickyA junior engineer says "I added a .cache() call to my DataFrame and my job became slower. Caching is supposed to speed things up — what went wrong?"

Answer: Caching has a cost — it's only beneficial when the DataFrame is actually reused.

Why caching hurt performance:

  • Only used once: If the DataFrame is only read once downstream, caching adds the cost of materializing and storing partitions in RAM for no benefit.
  • Memory pressure: Caching evicts other cached DataFrames or executor working memory. If the cluster doesn't have enough RAM, Spark spills the cached data to disk — slower than just reading the original source.
  • Serialization cost: For the default MEMORY_AND_DISK storage level, serializing partitions to store them takes CPU time upfront.
  • The DataFrame is cheap to recompute: If the lineage is short (e.g., just a small CSV read + one filter), recomputing it is faster than caching and deserializing.

When caching actually helps: The DataFrame has a long, expensive lineage AND is used in two or more downstream actions or joins. A good rule: only cache if you can measure a speedup with it vs. without it.

TrickyYou run df.filter(col("age") > 30).count() and then df.filter(col("age") > 30).show(5). How many times does Spark actually read the underlying file? What single change eliminates the redundant read?

Answer: Spark reads the file TWICE — once per action. Each action independently re-triggers the full DAG from the source:

  1. Action 1 (.count()): reads file → filters → counts. Returns result to driver. Discards all partitions.
  2. Action 2 (.show(5)): reads file AGAIN → filters AGAIN → returns 5 rows. Identical to step 1 except it returns rows instead of a count.

Fix:

filtered = df.filter(col("age") > 30).cache()
filtered.count()    # triggers computation, caches to RAM
filtered.show(5)    # reads from RAM — no file I/O!
filtered.unpersist()  # free RAM

After .cache(), the first action materializes the filtered partitions into executor RAM. The second action reads from RAM — no file I/O at all. This is critical when the source is a remote S3 bucket or slow HDFS cluster where each read costs real time and money.

HardA Spark job has Stage 1 with 100 tasks (all complete in 3 minutes) and Stage 2 with 100 tasks — 99 finish in 2 minutes but one task takes 25 minutes. The Spark UI shows a single task with 50 GB of shuffle read. Diagnose the exact problem and list three specific remedies.

Diagnosis: Classic Data Skew. Stage 1 completed a shuffle (wide transformation). Stage 2 starts reading shuffle data. One post-shuffle partition received 50 GB while others received ~500 MB each — one key is massively over-represented in the data. The entire Stage 2 is blocked until the skewed task finishes (all tasks in a stage must complete before the next stage starts).

Root cause investigation:

  • Check: df.groupBy("join_key").count().orderBy(col("count").desc()).show(20) — look for one key with millions of records while most have thousands.
  • Common culprits: NULL values all hash to same partition, one enterprise customer with millions of transactions, one dominant categorical value.

Three remedies:

  1. Filter nulls before joining: df.filter(col("join_key").isNotNull()) — if nulls are the skewed key, process them separately or drop them.
  2. Salting: Append a random number (0–N) to the skewed key before the shuffle: concat(col("key"), lit("_"), (rand() * 10).cast("int")). This distributes one hot key across 10 partitions. After aggregation, sum partial aggregates for each salt. Works for aggregations but requires more complex logic for joins.
  3. Broadcast join: If one table is small enough to fit in executor memory (<~8 GB), use df_large.join(broadcast(df_small), "key"). Spark sends a full copy of the small table to every executor, eliminating the shuffle entirely — no skew possible without a shuffle.
TrickyWhat's the difference between rdd.map() and rdd.flatMap()? Give a concrete example where flatMap is essential and map would fail to produce the correct result.

map(f): Applies function f to each element, producing exactly one output element per input element. The output RDD has the same number of elements as the input.

flatMap(f): Applies function f to each element, but f returns an iterable. Spark then flattens all the iterables into a single output. One input element can produce zero, one, or many output elements.

Example — Word Count tokenization:

# Input RDD:
rdd = sc.parallelize(["hello world", "spark is fast"])

# With map — gives LIST of lists (wrong for word count!)
rdd.map(lambda line: line.split(" ")).collect()
# → [["hello", "world"], ["spark", "is", "fast"]]  # 2 elements

# With flatMap — flattens to individual words (correct!)
rdd.flatMap(lambda line: line.split(" ")).collect()
# → ["hello", "world", "spark", "is", "fast"]  # 5 elements

For word count, you need individual words as RDD elements. map produces nested lists — you'd be counting 2 lists, not 5 words. flatMap flattens them into 5 separate elements, enabling the subsequent map(word → (word, 1)) and reduceByKey to work correctly.

HardA Spark application processes the same large DataFrame in two separate branches: Branch A does a join, Branch B does a groupBy. Both branches are then unioned. How many times is the source DataFrame computed, and how do you minimize redundant computation?

Without caching: 2 times. Each branch creates its own DAG path back to the source. When both DAGs are triggered (either by a single action on the union, or separate actions), Spark traces each branch independently back to the source file and reads + processes it twice — even though both branches start from the same logical DataFrame.

With caching: 1 time.

# BAD — source computed twice:
branch_a = df.join(other_df, "key")
branch_b = df.groupBy("category").count()
result = branch_a.union(branch_b)
result.show()  # df is read and processed twice!

# GOOD — cache the shared root:
df.cache()
branch_a = df.join(other_df, "key")
branch_b = df.groupBy("category").count()
result = branch_a.union(branch_b)
result.show()  # df is computed once, cached; both branches read from RAM

This is called the diamond dependency pattern — two paths in the DAG sharing a common ancestor. Catalyst doesn't automatically deduplicate common subexpressions across separate actions, so explicit caching of the shared DataFrame is essential.

Section D — Conceptual & Cross-Topic

TrickyExplain why Spark's fault tolerance is sometimes called "coarse-grained" vs. databases that offer "fine-grained" recovery. In which scenarios does Spark's approach become a liability?

Coarse-grained vs. Fine-grained fault tolerance:

Spark (coarse-grained): Fault tolerance operates at the partition level. The lineage records which transformation created a partition — not which individual records were modified. Recovery means re-running the entire transformation for the lost partition. You can't recover a single row — you recompute the whole partition.

RDBMS (fine-grained): Databases use write-ahead logs (WAL) that record every individual row-level change. Recovery = replay the WAL, row by row. Can recover one specific UPDATE from three days ago.

Why Spark's approach is fast: No per-row logging overhead, no WAL writes for every transformation. The lineage is essentially free — it's just a graph of function calls, not a data log.

When it becomes a liability:

  • Very long lineages: If the lineage chains through 50 transformations and one partition fails, recovering it means re-executing all 50 transformations on the source data — expensive.
  • Slow or unavailable source: If the original source (e.g., S3) is throttled or down, recovery fails.
  • Random writes / updates: Spark is read-heavy. It cannot do row-level updates. (Delta Lake adds this on top.)

Mitigation: Use .checkpoint() to materialize a DataFrame to HDFS/S3, breaking the lineage. Acts like a WAL snapshot — recovery re-starts from the checkpoint, not from the original source.

MediumThe Bronze-Silver-Gold medallion layers are analogous to stages in the Data Analysis Lifecycle. Map each medallion layer to its corresponding CRISP-DM phase.

Answer:

Medallion LayerCRISP-DM PhaseWhat Happens
Bronze (Raw) Data Understanding Ingest raw data as-is from source systems. No transformation — full fidelity audit trail. Equivalent to initial data collection and description.
Silver (Cleansed) Data Preparation Apply cleaning (remove nulls, fix types), joins, validation rules. This is the 80% of data science work — wrangling raw Bronze into analysis-ready form.
Gold (Aggregated) Modeling + Evaluation + Deployment Business-domain aggregations and curated tables ready for BI dashboards, ML features, and analytical reporting. Directly consumed by stakeholders.

The beauty of the medallion pattern: if a Silver cleaning rule is wrong, you can replay Bronze → Silver without losing the original data. Maps perfectly to CRISP-DM's iterative nature — go back to Data Preparation without losing Business Understanding context.
